# AI 评分全量公开、分轮执行与重新验证设计

日期：2026-07-13  
状态：待用户审核  
适用范围：Python 主评分流水线、Java 回调与报告 API、用户端评分结果页/全部待办页/评分依据页、多次路演对比与任务验收

## 1. 设计目标

建立一条可对账、可执行、可验证、可持续使用的 AI 评分闭环：

1. 第一次报告一次性公开所有已知失分原因，不通过隐藏问题制造后续使用。
2. 所有大于 0 的失分必须进入完整整改地图，不能只把大模型摘要称为“全部待办”。
3. 首页只展示本轮最值得先做的 3 项，完整待办页展示全部任务；“本轮”只表示执行顺序，不表示阶段分数目标。
4. 用户勾选完成不改变 AI 分数；只有下一次完整路演重新评分并通过规则验收后，分数才变化。
5. 用户始终只看到一个当前 AI 分数。任务状态、趋势和预测是解释信息，不是第二套评分。
6. 长期产品价值来自持续验证、回退检测、项目变化、赛事适配、高压训练和团队协作，不来自人为保留扣分项。

产品承诺：

> 一次看全问题，一轮只抓重点；是否真正提分，由下一次路演验证。

## 2. 已确认的产品原则

### 2.1 全量公开

- 所有正式计分观测点的表现差距、证据封顶差距和硬性处罚必须在首次报告中完整公开。
- 所有差距必须能对账到 `100 - 当前 AI 分数`。
- 所有可整改差距必须至少由一条任务承接。
- 无法立即确定改法的差距也不能消失，必须生成“待补证/待诊断”任务并说明缺少什么。

### 2.2 分轮执行

- 目标始终为 100 分，不设置“下一档 60/70/85”目标。
- 全部任务从第一天可见，不锁定、不延迟释放。
- 首页只推荐 3 项本轮优先任务，完整待办页展示本轮优先、后续待办、待验证、已验证和回退任务。
- 本轮优先只表示执行顺序，不表示完成后必然达到某个分数。

### 2.3 重新验证

- 用户标记任务“完成”只改变任务状态，不修改报告分数。
- 下一次上传必须重新走同一赛道、赛事、组别和规则版本对应的完整评分流程。
- 系统对每条历史任务给出：验证通过、部分通过、未通过、不可观测、出现回退或规则变化不可比。
- 实际分数以新一次路演为准，预测区间不直接写回正式分数。

### 2.4 满分诚实

- 若某次完整路演在当前规则和当前证据下确实达到 100 分，平台必须显示 100 分，不得为了留存人为压分。
- 达到高分后，产品价值转向稳定复现、随机追问、故障注入、规则变化、团队协作和下一场赛事准备。

### 2.5 方案选择与取舍

本设计拒绝两种极端方案：

- “全部平铺”：逐条展示所有失分但不建立根因、任务和覆盖关系，虽然透明，却会让用户无从下手，也无法解释任务重叠；
- “分批隐藏”：每次只释放部分问题，短期可能增加重复使用，但会破坏分数可信度，不能作为商业留存手段。

选择“全量账本 + 完整改改地图 + 本轮优先 + 下次验证”。代价是需要新增覆盖校验、任务图和跨轮验收数据，工程范围更大；收益是分数可解释、任务可执行、预测不重复、长期训练价值成立。

## 3. 非目标

本设计不做以下事情：

- 不承诺用户完成任务后一定增加指定分数。
- 不把“关联失分”包装成“保证可追回分数”。
- 不让大模型自由生成提分值。
- 不把多个任务的单项上限直接相加。
- 不在用户端展示“官方分、诊断分、训练分”等多套分数。
- 不依赖短期无法建立的黄金技术样本集才能上线。
- 不通过隐藏问题、延迟释放问题或人为制造新问题提高复购。

## 4. 概念模型

系统必须区分以下五类对象。

### 4.1 当前 AI 分数

本次路演基于当前规则、证据和现场表现得出的唯一正式 AI 分数。

### 4.2 失分账本 `Loss Ledger`

解释 `100 - 当前分` 的不可变事实快照。每一条账目表示一个计分观测点上的具体失分来源。

失分类型固定为：

- `performance_gap`：表现未达到满分档位；
- `evidence_limited`：证据等级导致上限封顶；
- `hard_violation`：命中明确处罚规则；
- `unresolved_gap`：规则确认存在差距，但当前证据不足以稳定归因，仅可作为兜底状态。

### 4.3 整改任务 `Remediation Task`

用户可以执行、提交和验证的任务。一条任务可覆盖多个失分账目，但必须保留覆盖映射。

### 4.4 本轮优先事项 `Current Priorities`

完整任务集合中建议最先处理的 3 项，只决定执行顺序，不改变满分目标，也不隐藏其余任务。

### 4.5 验收记录 `Verification Record`

下一次路演对历史任务的复核结果，用来说明哪些修改真实生效、哪些未生效、哪些出现回退。

## 5. 总体数据流

```text
赛事/赛道/组别规则
        ↓
证据提取 + 规则评分
        ↓
当前唯一 AI 分数 + 结构化观测点
        ↓
完整失分账本（必须对账到 100 - 当前分）
        ↓
根因归并与整改任务生成
        ↓
覆盖校验（所有失分必须被承接）
        ↓
单项情景复算 + 组合情景复算
        ↓
结果页前三项 + 全部待办 + 全部评分依据
        ↓
用户修改并重新路演
        ↓
重新评分 + 历史任务验收 + 趋势/回退分析
```

评分事实、任务生成和提分预测必须是三个独立模块。某一模块失败时，不得污染其他模块的权威数据。

## 6. 评分与失分对账

### 6.1 强制恒等式

对于可发布的正式报告：

```text
sum(lossLedger.points) = 100 - currentScore
```

允许一位小数舍入误差，最大绝对误差为 `0.1`。同时满足：

```text
performanceGap
+ evidenceLimitedGap
+ effectiveHardPenalty
= fullGap
```

追回记录不得重复进入当前失分账本。已经追回的处罚保留在历史记录中，但不计入本次 `fullGap`。

### 6.2 会话 26 的当前事实示例

```text
当前 AI 分数：49.5
表现差距：41.0
证据封顶差距：7.5
硬性处罚：2.0
完整差距：50.5
```

该示例说明：2.0 分是狭义处罚，另外 48.5 分是未达到满分档位或被证据封顶，不应全部叫作“惩罚”。但这 50.5 分都必须进入解释和整改覆盖。

## 7. 从失分账本生成完整整改地图

### 7.1 生成顺序

1. Python 规则引擎先生成完整 `lossLedger`，不依赖大模型行动计划。
2. 大模型基于账本生成根因、改法、训练方式和验收表达。
3. 系统使用结构化字段建立 `task -> lossItems` 映射。
4. 覆盖检查器找出未被任何任务承接的失分项。
5. 未覆盖项优先合并到相同根因任务；仍无法合并时生成一对一兜底任务。
6. 覆盖率达到 100% 后才允许把队列称为“全部待办”。

### 7.2 合并原则

允许合并的条件：

- 相同 `rootCauseKey`，且需要相同整改动作；
- 多个观测点依赖同一份证据或同一次演示修改；
- 一项前置修复天然解决多个观测点；
- 合并后仍能分别说明每个失分项的事实、分值和验收要求。

禁止仅因标题相似而合并。旧报告可使用文本相似度寻找候选，但只能作为兼容推断，并必须通过结构化观测点和规则情景确认。

### 7.3 兜底原则

若大模型输出失败、JSON 截断、结构化关联缺失或覆盖不足：

- 每个未覆盖 `lossItem` 自动生成一条确定性任务；
- 标题使用观测点名称和差距类型；
- 问题描述直接使用规则引擎事实；
- 验收标准使用规则配置中的最低可验证条件；
- 无法生成具体改法时标记为“待补证/待诊断”，但仍保留覆盖关系；
- 宁可任务较多，也不能让失分项消失。

## 8. 任务分值语义

每条正式计分任务必须同时区分两个数字。

### 8.1 关联差距 `coveredGapPoints`

该任务覆盖的当前失分账目之和。例如一条任务覆盖 O09、O10、O15，相关差距共 6.5 分，则展示：

> 覆盖 3 个评分观测点，关联当前差距 6.5 分。

这不是提分承诺。

### 8.2 保守提分区间 `scoreImpact`

使用当前规则做单项情景复算，表示下次完整路演达到任务验收标准时的保守变化区间。例如：

> 达到验收标准后，预计可提升 1.8～3.0 分。

单项区间不得超过其分值预算，也不得由大模型直接提供。

### 8.3 两类验收标准

每条正式任务同时保存：

- `minimumAcceptance`：产生保守预测所需的最低可验证状态；
- `fullScoreCriteria`：对应观测点达到满分档位的完整要求。

不设置“先到 60 分”之类的阶段目标，但必须从第一次报告就公开满分要求。达到最低验收并不等于达到满分档位。

### 8.4 整体预测

顶部整体预测定义为：

> 所有已知正式计分待办达到本轮验收标准，并在下一次完整路演中被观测到时，基于当前规则的组合情景预测。

整体预测必须同时应用全部任务情景后运行一次规则引擎，不得累加单项上限。最终实际分数仍以重新路演为准。

## 9. 优先级与分轮执行

优先级计算使用版本化策略，至少考虑：

1. 硬性处罚、安全、合规和演示故障风险；
2. 是否为其他任务的前置依赖；
3. 组合情景中的边际提分；
4. 是否同时覆盖多个失分项；
5. 预计修改成本和验证成本；
6. 是否存在较高回退风险。

结果页固定展示排序后的前 3 项。完整待办页从第一天展示全部任务，并按以下状态组织：

- 本轮优先；
- 后续待办；
- 处理中；
- 已提交，待下次路演验证；
- 验证通过；
- 部分通过；
- 验证未通过；
- 出现回退；
- 规则变化，不可直接比较。

“后续待办”不是隐藏、锁定或下一阶段才释放，只表示当前执行顺序靠后。

## 10. 重新验证状态机

### 10.1 任务状态

```text
not_started
  -> in_progress
  -> submitted
  -> awaiting_rerun
  -> verified | partial | failed | not_observable

verified -> regressed（后续路演再次出现问题）
任意状态 -> superseded（项目/规则变化后被新任务替代）
```

### 10.2 评分变化规则

- `submitted` 和 `awaiting_rerun` 不改变 AI 分数。
- 新路演完整评分后，系统才计算新分数。
- 验收记录解释分数变化，但不能直接对分数做加法。
- 若新路演修好一项但另一项变差，正式分数按本次全部观测重新计算。
- 若规则版本或赛道绑定变化，任务仍可验收，但分数趋势必须标记“规则变化，不可直接归因”。

### 10.3 验收结果

每条历史任务至少输出：

- 是否达到最低验收；
- 是否达到满分要求；
- 新证据位置；
- 对应观测点新旧状态；
- 是否出现回退；
- 不能验收时的原因；
- 本次分数变化中可解释的规则事实，不承诺任务与总分变化一一相等。


约束：

- `lossId` 是报告内不可变的账目实例标识，包含报告/会话身份，不能跨报告复用；

- `points > 0`；
- `scoreBudgetKey` 用于阻止重复提分预算；
- `hard_violation` 额外携带 `penaltyRuleCode`、`deductionId` 和 `maxRecoverablePoints`。

## 12. Python 主评分职责

新增或明确四个独立服务边界：

### 12.1 `LossLedgerService`

- 从规则执行结果生成完整账本；
- 生成报告内唯一 `lossId`、跨轮稳定 `lossKey` 和 `scoreBudgetKey`；
- 执行满分差距对账；
- 不依赖行动计划或前端状态。

### 12.2 `RemediationPlanner`

- 基于完整账本生成根因和整改任务；
- 接受大模型建议，但强制结构化关联；
- 合并共同根因；
- 为未覆盖账目生成确定性兜底任务；
- 输出完整任务图，不决定正式分数。

### 12.3 `CoverageValidator`

- 检查所有账目是否被覆盖；
- 检查账本是否对账；
- 检查未消歧的重复预算；
- 检查计分任务是否存在有效规则关联；
- 失败时触发兜底，不允许静默遗漏。

### 12.4 `ScoreImpactService`

- 沿用当前规则引擎做单项和组合情景复算；
- 接受 `coveredLossIds` 和验收状态，不接受大模型自由分值；
- 防止共享观测点、封顶和处罚重复计算；
- 生成版本化 `scoreImpact` 与 `scoreProjection`。

下一轮增加 `TaskVerificationService`，使用项目指纹、规则指纹、历史任务和新证据生成验收记录。

- `actionPlanJson` 继续承载完整 `RemediationTask[]`，保持旧前端兼容；
- 当前 Python 已生成 `lossLedger`，但 Java DTO 未正式接收，v3 改为显式 `lossLedgerJson`；
- Java 同时校验 HTTP 状态、业务码、JSON 可解析性和 `contractVersion`；
- 完成回调失败沿用自动重试和“结果回写失败”终态；
- Java 终态保护继续阻止旧进度覆盖完成报告。

## 14. Java 持久化设计

采用“报告快照 JSON + 跨轮结构化记录”的混合方式。

### 14.1 报告快照

## 15. 报告 API

用户报告 API 返回原始快照与解析对象：

```json
{
  "overallScore": 49.5,
  "lossLedgerJson": "[...]",
  "lossLedger": [],
  "actionPlanJson": "[...]",
  "actionPlan": [],
  "remediationTasks": [],
  "coverageSummaryJson": "{...}",
  "coverageSummary": {},
  "scoreProjectionJson": "{...}",
  "scoreProjection": {},
  "taskVerifications": [],
  "contractVersion": "ai-score-report-v3"
}
```

兼容要求：

- 历史报告缺失新字段时返回空数组/空对象，不抛 500；
- `actionPlan` 是报告生成时的不可变任务快照，`remediationTasks` 是叠加当前执行状态后的完整任务组合；
- 新前端优先使用 `remediationTasks`，只有历史报告才回退到 `actionPlan`；
- 历史报告的旧 6 条行动计划不得继续声称覆盖全部差距；
- 若 `coverageSummary.status != complete`，API 返回 `todoPortfolioStatus = incomplete`，前端使用“整改清单尚未完整生成”，不得显示“全部待办”；
- 新报告必须通过覆盖校验后才返回 `todoPortfolioStatus = complete`。

## 16. 前端页面结构

### 16.1 结果首页

顶部保持一个主分数和四个关键指标：

```text
AI评分：49.5 / 100
满分差距：50.5
已知整改达到本轮验收后的下次预测：{predictedScoreLower}～{predictedScoreUpper}
本轮优先：3项
```

预测区间必须在完整任务覆盖建立后重新做组合情景复算，不能继续沿用会话 26 当前仅覆盖部分任务时的 `56.6～60.0`。

在指标下增加完整性说明：

```text
本次{fullGap}分差距来自{observationCount}个计分观测点，
形成{lossItemCount}条失分账目，已合并为{taskCount}项整改任务，
覆盖{coveredGapPoints}/{fullGap}分差距。
```

会话 26 当前账本的真实基线为：15 个计分观测点、19 条失分账目、账目合计 50.5 分。合并后的任务数必须由新覆盖规划器计算，设计阶段不预设为 6、9 或其他固定数量。

首页展示前三项，每项显示：

- 标题和问题；
- 覆盖观测点数量；
- `关联当前差距 X 分`；
- `保守预计提升 X～Y 分`；
- 验收标准入口。

页面固定说明：

> 关联差距不是承诺提分。分数变化以重新路演后的完整评分为准。

### 16.2 全部待办页

页头显示：

- 失分观测点数量；
- 失分账目数量；
- 合并后任务数量；
- 差距覆盖值和覆盖率；
- 正式计分任务与额外训练建议数量。

任务筛选：

- 全部；
- 本轮优先；
- 后续待办；
- 待验证；
- 已验证；
- 未通过/回退；
- 额外训练建议。

任务列表不得只显示大模型原始 `action_plan`。新报告的数据源必须是 API 返回的 `remediationTasks` 完整任务组合；历史报告才允许回退到旧 `actionPlan`，并显示“历史整改摘要，覆盖未校验”。

任务详情显示：

- 为什么失分；
- 覆盖哪些观测点和失分账目；
- 每项当前分、满分和差距；
- 关联差距；
- 保守提分区间；
- 怎么改；
- 最低验收；
- 满分标准；
- 证据位置；
- 负责人、依赖和状态；
- 历次验收结果。

### 16.3 评分依据页

增加“完整失分账本”区域，逐条展示：

- 观测点；
- 当前分/满分；
- 表现差距；
- 证据封顶差距；
- 硬性处罚；
- 规则原因；
- 证据定位；
- 承接任务。

支持从失分账目跳转到任务，也支持从任务返回对应依据。

### 16.4 第二次及以后报告

结果页增加“本轮变化”而不增加第二个分数：

- 当前 AI 分数及相对上次变化；
- 已验证通过任务数；
- 未通过任务数；
- 回退任务数；
- 新发现问题数；
- 规则版本是否可比。

用户看到的仍然只有当前 AI 分数，趋势用于解释变化。

## 17. 用户体验与文案规范

用户第一次使用时必须形成三个明确认知：分数能对账、所有问题都已公开、现在先做哪三项。用户提交整改后必须明确知道“提交不等于加分”，并被引导重新路演。第二次及以后使用时，重点从重复列问题转向验证哪些修改生效、哪些未生效、哪些出现回退和哪些是新问题。

当用户进入高分区间时，不再人为制造基础问题，产品改为提供随机追问、临场压力、故障模拟、规则变化和稳定复现训练。如果本次确实达到 100 分，明确显示“当前规则下本次路演达到 100 分”，并提供保持与挑战能力，而不是降低分数留住用户。

### 17.1 推荐文案

推荐：

- `覆盖 3 个评分观测点，关联当前差距 6.5 分`；
- `达到验收标准后，预计可提升 1.8～3.0 分`；
- `最高可追回约 2.0 分`；
- `已提交，等待下一次路演验证`；
- `修改已完成，但本次录像未出现可验收场景`；
- `该建议当前无法与评分规则稳定关联，不计入提分预测`。

### 17.2 禁止文案

禁止：

- `完成后增加 6.5 分`；
- `保证拿回`；
- `下一阶段目标 60 分`；
- `还有部分问题暂不展示`；
- `完成任务后自动加分`。

## 18. 发布与失败处理

### 18.1 报告发布门槛

新报告必须同时满足：

- `abs(sum(lossLedger.points) - fullGap) <= 0.1`；
- `coverageRate == 1.0`；
- `uncoveredLossIds` 为空；
- `unresolvedDuplicateBudgetKeys` 为空；
- 正式计分任务均有规则关联；
- `ruleHash` 与 `scoringFingerprint` 一致；
- 所有 JSON 可完整解析。

### 18.2 降级策略

- 大模型任务生成失败：使用规则观测点一对一任务；
- 任务合并失败：不合并，保留一对一完整队列；
- 单项预测失败：任务保留，但不显示分数，整体预测标记不可用；
- 组合预测失败：主分和完整账本仍可发布，顶部预测显示“暂不可用”；
- 覆盖检查失败：自动补齐兜底任务；补齐仍失败时不得称“全部待办”；
- 回调失败：自动重试，并使用“结果回写失败”终态；
- 历史数据缺字段：保持可读，不伪造覆盖率和预测。

## 19. 测试策略

### 19.1 Python

- 账本点数严格对账到满分差距；
- 一个观测点同时存在表现差距和处罚时分别入账；
- 大模型只生成部分任务时自动补齐；
- 合并后所有 `lossId` 仍被覆盖；
- 同一预算被多个任务引用时组合预测不重复计算；
- 用户提交任务不改变分数；
- 新路演重新评分后生成验证记录；
- 规则版本变化时标记不可直接比较；
- JSON 截断时进入兜底，不发布不完整队列。

### 19.2 Java

- 回调新字段持久化和解析；
- 非法 JSON 返回空对象且保留错误状态；
- 终态保护；
- 幂等回调不重复创建任务和验收；
- 跨轮任务状态不修改历史报告快照；
- 历史报告兼容；
- 数据库迁移幂等。

### 19.3 前端

- 结果页只有一个 AI 分数；
- 首页只展示 3 项；
- 全部待办数量来自完整任务组合；
- 失分账目、任务数和覆盖差距一致；
- 关联差距与预计提升文案不混淆；
- 后续待办从第一天可见；
- 未关联建议不显示分数；
- 第二次报告正确展示验证、未通过和回退；
- 缺失新字段的历史报告不崩溃。

### 19.4 端到端验收

至少选择一份存在表现差距、证据封顶和硬性处罚的视频，验证：

1. `100 - AI分数` 与账本点数一致；
2. 所有账目都有任务承接；
3. 首页 3 项、全部待办完整；
4. 单项分值和组合预测不重复；
5. 标记完成不涨分；
6. 重放下一次视频后才产生新分数和验收记录；
7. 前后报告能解释已改善、未改善、新问题和回退。

## 23. 风险与控制

### 风险 1：任务数量过多

控制：全量公开但首页只显示 3 项；完整页按根因合并、状态和依赖组织，不隐藏。

### 风险 2：用户把关联差距当作可追回分

控制：固定区分“关联当前差距”和“保守预计提升”，禁止使用保证性文案。

### 风险 3：大模型合并错误

控制：覆盖基于报告内不可变 `lossId`，跨轮匹配使用稳定 `lossKey`；合并失败回退一对一，不允许账目丢失。

### 风险 4：第二次分数未提升引发不信任

控制：逐项说明验收结果、缺失证据、新问题和回退，不用“用户已完成”替代新视频事实。

### 风险 5：用户很快达到高分后不再使用

控制：产品价值随用户成熟度转向稳定复现、压力测试、规则适配和团队训练。真实 100 分必须承认，不能通过人为压分解决留存。

### 风险 6：跨规则版本趋势误导

控制：只有规则哈希和关键评分指纹一致时才做直接归因；否则显示“规则变化，不可直接比较”。

## 24. 验收结论

本设计完成后，系统必须能够明确回答四个问题：

1. 为什么是这个 AI 分数？
2. 每一分差距由什么事实产生？
3. 每个失分项由哪条任务承接，为什么任务数可以少于失分项数？
4. 用户修改后哪些真的生效，分数为什么变化或没有变化？

只有同时回答这四个问题，评分产品才形成可信的长期训练闭环。
