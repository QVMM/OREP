# AI评分回调可靠性与有限并发设计

## 背景

上传视频评分会话26的计算在21分22秒内完成，但最终回调携带的 `requiredFix` 为对象，Java DTO 将其声明为字符串，导致请求体反序列化失败。Java统一响应仍使用 HTTP 200 承载业务错误，而 Python 只判断 HTTP 状态，因此误判回调成功，页面永久停在95%。

同一任务的真实耗时主要来自两个串行阶段：11个ASR分片约7分23秒，110帧视觉分析约10分19秒。优化必须保留所有音频分片、全部选中帧、原始提示词和三阶段评分内容。

## 目标

1. Python与Java完成回调使用一致、可验证的字段类型。
2. Python同时校验HTTP状态和统一响应体业务码。
3. 完成回调失败自动重试，耗尽后明确进入 `result_writeback_failed`。
4. Java的 `completed`、`failed` 终态不被迟到的进度回调覆盖。
5. 会话26直接重放已保存结果，不重新执行视频分析。
6. ASR分片和视觉批次采用有限并发，完整保留输入与输出顺序。

## 方案选择

### 回调契约

采用Java现有传输契约作为规范：`requiredFix` 与 `acceptanceCriteria` 均为字符串。Python在 `_build_final_result` 出站边界进行规范化：

- 字符串保持不变；
- 字典优先组合 `title`、`action` 和验收条件为可读文本；
- 列表按换行连接；
- 其他标量转为字符串。

这样不扩大Java DTO类型，不把任意对象渗透到持久层，同时保留用户可读的整改信息。

### 回调确认与重试

新增独立的异步回调客户端，成功条件必须同时满足：

- HTTP为2xx；
- 响应体是JSON；
- `code == 200`。

进度回调只发送一次，失败记录日志但不阻塞主任务。完成回调最多3次，使用短指数退避。三次失败后发送最小兼容失败回调：

- `status=failed`
- `currentStage=result_writeback_failed`
- `errorMessage=结果回写失败：...`

如果失败状态本身也无法送达，保留明确错误日志，不能再记录“流水线完成”。

### Java终态状态机

状态规则如下：

- 当前为 `completed`：忽略后续 `scoring` 与 `failed`，允许幂等 `completed` 重放。
- 当前为 `failed`：忽略后续 `scoring`，允许 `completed` 重放恢复报告。
- 非终态：按正常规则接收进度、失败或完成。
- 非终态进度百分比只增不减。

这既阻止旧进度覆盖终态，也保留运维重放恢复能力。

### ASR有限并发

先按原有300秒规则生成全部分片，再用固定大小线程池并发识别，默认并发度3。每个分片独立调用Recognition；结果按分片索引排序后统一修正时间戳。单片失败仍沿用现有降级语义，不影响其他分片，临时文件最终统一清理。

### 视觉有限并发

仍按每批8帧构造原始多模态请求，默认并发度3。每批继续使用原有“批次失败后逐帧恢复”。并发完成后按批次起始索引排序合并，保证110帧时间顺序和聚合结果不变。进度按已完成帧数累计上报。

并发度通过环境变量控制：

- `ASR_CHUNK_MAX_WORKERS=3`
- `VIDEO_ANALYSIS_MAX_WORKERS=3`

## 数据完整性不变量

- 分片数、帧数、帧采样策略、批大小和提示词不变。
- 输出必须覆盖每个输入分片和每个选中帧。
- 合并结果必须按原始时间顺序排列。
- token使用量按所有并发任务求和。
- 任何批次恢复都不能静默丢弃失败项。

## 会话26恢复

使用 `uploads/results/result_26.json` 重新构造完成回调。重放前不修改会话数据；修复后的Java允许 `completed` 覆盖当前非终态或失败状态，并通过会话唯一键幂等写入报告。验证项目包括：报告存在、会话100%完成、15个观测点、1个独立扣分、15个证据锚点及最终权威分一致。

## 测试策略

- Python契约测试：字典型 `requiredFix` 被转为字符串且内容完整。
- Python回调测试：HTTP错误、非JSON、业务码错误、重试成功、重试耗尽和失败状态上报。
- Java状态机测试：completed/failed不被进度覆盖，failed允许completed恢复，进度不倒退。
- ASR并发测试：实际存在重叠执行、输出顺序和时间戳不变、全部分片被调用。
- 视觉并发测试：实际存在重叠执行、结果顺序不变、token求和和进度完整。
- 最终执行Python、Java全量评分相关测试以及真实会话26回放验证。

## 预期性能

在外部API限流和网络稳定的前提下，55分钟视频的预期时间由约21分钟降至10至14分钟。该数值是目标区间而非保证值；若供应商限流，线程池保持有限并发并由现有恢复逻辑保证完整性。
