# 协作工作台动效与多人邀请设计

日期：2026-07-30

## 1. 背景与目标

现有协作工作台已经具备悬浮入口、任务列表、任务详情和单人协作申请能力，但仍有两个明显问题：

1. 工作台打开、关闭、切换页面和刷新任务列表时反馈偏生硬，缺少连贯的空间关系。
2. 发起协作一次只能邀请一人，不适合需要多名成员共同参与的任务。

本次改造的目标是：

- 在不影响操作效率的前提下，为协作工作台补充克制、平滑、可降级的动效。
- 支持一次选择并邀请多名团队成员。
- 每名受邀成员仍拥有独立的接受、拒绝、执行、提交和状态流转。
- 后端批量创建保持原子性和幂等性，避免部分成功、重复任务和错误通知。

## 2. 范围

### 2.1 本次包含

- 学生端协作工作台的打开、关闭、视图切换、标签切换和任务列表入场动效。
- 学生端“发起协作”表单的多人选择、搜索、全选当前搜索结果、清空和选中结果展示。
- 新增批量创建协作申请接口。
- 批量创建的事务、幂等、权限校验、错误提示和通知投递。
- 相关后端、前端和端到端测试。

### 2.2 本次不包含

- 不创建“协作群组”或“协作批次”业务表。
- 不把多名受邀人绑定为必须共同接受或共同完成的单一任务。
- 不改造现有单人创建接口，旧调用继续兼容。
- 不加入循环闪烁、弹跳、粒子或大幅位移动效。
- 不改变协作任务现有的业务状态定义。

## 3. 产品语义

一次多人邀请是“批量发出多份独立协作申请”，不是创建一个多人共享任务。

示例：发起人选择甲、乙、丙三名成员后，系统创建三条协作申请：

- 甲可以接受，乙可以拒绝，丙可以暂不处理。
- 接受后，每名成员获得自己的协作任务和提交入口。
- 发起人可以分别查看三人的状态。
- 对仍处于待处理状态的邀请，发起人可以逐条撤回。
- 某一人的后续状态变化不会自动改变其他人的任务。

该语义与现有单人协作模型一致，可以直接复用既有任务详情、审核、反馈和提交能力。

## 4. 交互设计

### 4.1 工作台打开与关闭

- 打开：工作台从左下方向上移动少量距离并从 `0.985` 缩放至 `1`，同时淡入。
- 打开总时长：`220ms`，使用平滑减速曲线。
- 关闭：反向淡出、缩小并下移少量距离。
- 关闭总时长：`170ms`，使用平滑加速曲线。
- 桌面端变换原点为左下角，移动端为底部中心。
- 不使用弹簧回弹，避免工具型界面显得拖沓。

### 4.2 工作台内部视图切换

从任务列表进入“发起协作”或任务详情：

- 当前内容向左轻移并淡出。
- 新内容从右侧轻移进入并淡入。
- 返回列表时方向相反，帮助用户理解层级关系。
- 容器高度变化采用平滑过渡，避免界面突然跳动。
- 标题和主体使用同一个方向状态，避免标题与内容运动相反。

### 4.3 标签与任务列表

- 切换“待处理 / 进行中 / 我发起的 / 全部”时，旧列表快速淡出，新列表淡入。
- 新列表前 8 条任务按约 `20ms` 间隔依次入场。
- 第 9 条及之后不再增加延迟，避免长列表等待。
- 加载骨架、空状态和错误状态共用短淡入，不使用位移动效。
- 按钮只保留轻微按压反馈，不添加持续动画。

### 4.4 减少动态效果

当系统启用 `prefers-reduced-motion: reduce` 时：

- 打开、关闭和内部切换只保留近乎即时的透明度变化。
- 禁用缩放、位移、列表错峰和容器高度动画。
- 功能、焦点管理和信息层级不受影响。

### 4.5 多人选择器

“协作成员”从原生单选框改为可搜索的多选下拉面板：

- 输入框可按姓名、账号或团队角色搜索。
- 搜索结果使用复选框选择成员。
- 当前登录用户不出现在候选人中。
- 支持“全选当前搜索结果”和“清空全部”。
- 关闭选择器后，选中 1 至 2 人时显示成员标签；超过 2 人时折叠为“已选 N 人”。
- 点击标签上的删除按钮可移除对应成员。
- 按 `Esc`、点击面板外部或再次点击触发器可关闭面板。
- 至少选择 1 人，最多选择 50 人。
- 已选成员切换搜索词后仍然保留。
- 团队切换时清空已选成员，防止跨团队提交。

提交按钮根据人数显示：

- 未选择成员：“请选择协作成员”，按钮禁用。
- 已选择 1 人：“发送协作申请”。
- 已选择多人：“向 N 人发送协作申请”。

### 4.6 提交结果

提交成功后，表单区域切换为紧凑结果状态：

- 标题：“已向 N 人发送协作申请”。
- 显示成功创建的成员数量。
- 提供“返回任务列表”和“继续发起”两个操作。
- 返回列表时默认进入“我发起的”，并刷新任务数据。
- 继续发起时保留当前团队，清空成员、标题、说明、优先级和截止时间。

提交失败时：

- 保留已选成员和所有表单内容。
- 在表单顶部显示明确错误原因。
- 提交按钮恢复可用，允许直接重试。
- 不显示部分成功结果，因为批量接口采用全有或全无事务。

## 5. 前端结构

### 5.1 `CollaborationHub.vue`

职责：

- 维护工作台整体打开和关闭动效。
- 维护内部页面切换方向。
- 为任务列表传入稳定的动效键值。
- 处理焦点进入、返回和关闭后的焦点恢复。

内部主体使用带 `key` 的过渡容器，键值由列表、请求表单、请求详情和工作项详情组成。进入子页面设置为前进方向，返回设置为后退方向。

### 5.2 `CollaborationRequestForm.vue`

职责：

- 管理发起协作表单。
- 管理已选成员 ID 列表和展示状态。
- 调用批量创建方法。
- 展示提交中、成功和失败状态。

表单不直接循环调用单人接口。所有成员作为一个批量请求提交。

### 5.3 独立成员选择组件

新增独立组件 `CollaborationMemberMultiSelect.vue`，职责仅包括：

- 展示触发器和下拉面板。
- 搜索成员。
- 选择、取消选择、全选当前结果和清空。
- 键盘操作、点击外部关闭和可访问性属性。

组件通过 `modelValue` 接收成员 ID 数组，通过 `update:modelValue` 输出新数组。它不负责提交协作任务，也不依赖协作 store。

### 5.4 Store 与客户端

- 客户端新增 `createCollaborationRequests(payload, idempotencyKey)`。
- Store 新增 `createRequests(payload)`，一次生成批次幂等键并调用批量接口。
- 请求进行中锁定重复提交。
- 成功后由 Store 刷新“我发起的”和“全部”数据。
- 现有 `createRequest` 保留，兼容旧页面和已有调用。

## 6. 后端接口

### 6.1 新接口

`POST /api/collaboration/requests/batch`

请求头：

```text
Idempotency-Key: <客户端生成的批次幂等键>
```

请求体：

```json
{
  "teamId": 3,
  "recipientUserIds": [11, 12, 13],
  "title": "完善路演材料",
  "description": "请分别完成负责部分并提交结果",
  "priority": "MEDIUM",
  "dueAt": "2026-08-02T18:00:00"
}
```

成功响应：

```json
{
  "count": 3,
  "items": [
    {
      "id": 101,
      "recipientUserId": 11,
      "status": "PENDING"
    }
  ]
}
```

`items` 返回完整的现有协作申请响应结构；示例仅展示关键字段。

### 6.2 校验规则

服务端在写入前完成全部校验：

- `Idempotency-Key` 必填且长度合法。
- `teamId` 必填，发起人必须是该团队的有效成员。
- `recipientUserIds` 去重后数量必须在 1 至 50 之间。
- 保留客户端选择顺序。
- 受邀人不能是发起人本人。
- 每名受邀人都必须存在、状态有效且属于目标团队。
- 标题、说明、优先级和截止时间沿用单人接口规则。

只要任意一名受邀人不合法，整个请求失败，不写入任何协作申请。

### 6.3 事务与幂等

批量创建在一个后端事务中完成：

1. 规范化并校验全部成员。
2. 由“批次幂等键 + 受邀人 ID”生成稳定的单条幂等键。
3. 批量写入多条现有 `collaboration_request` 记录。
4. 发布每条申请对应的领域事件。
5. 事务提交后发送通知。

单条幂等键使用 SHA-256 摘要，例如：

```text
batch:<sha256(batchKey + ":" + recipientId)>
```

这样可满足现有字段长度限制，也不会把原始幂等键直接拼接进数据库。

重试规则：

- 同一个批次幂等键和相同请求重试时，返回首次创建的全部记录，不重复插入。
- 同一个批次幂等键但请求成员或业务内容不一致时，返回冲突错误。
- 理论上不会出现只存在部分派生记录的状态；若检测到该异常状态，返回冲突错误并记录服务端异常，不自动补齐。

不新增批次业务表。为验证“同一批次键不能对应不同内容”，服务层基于已创建记录重建并比较规范化请求内容。

### 6.4 通知

每条申请创建后发布一条现有协作领域事件。通知监听器继续使用事务提交后执行：

- 事务回滚时不发送任何通知。
- 事务成功时向每名受邀人分别发送通知。
- 单个通知投递失败不回滚已经创建的协作申请，但需要记录可追踪日志。

## 7. 错误处理

前端按以下层级展示错误：

- 输入校验：在对应字段附近提示，例如“最多可选择 50 名成员”。
- 权限或成员变化：表单顶部提示具体原因，例如“王某已不在当前团队，请移除后重试”。
- 幂等冲突：提示“本次提交内容已发生变化，请重新发送”，并生成新的幂等键后允许重试。
- 网络或服务异常：提示“协作申请发送失败，请检查网络后重试”。

任何失败均不清空草稿和成员选择。

## 8. 可访问性与响应式

- 多人选择触发器使用组合框语义，结果面板使用列表框语义。
- 复选项可通过键盘聚焦和切换。
- 打开工作台时焦点进入工作台标题或首个可操作元素。
- 关闭工作台后焦点返回侧边栏协作入口。
- 动画期间不使用 `display: none` 提前移除仍需读取的内容。
- 桌面端工作台宽度保持现有视觉规格。
- 在约 390px 宽度下，多选标签、操作按钮和结果面板不得横向溢出。
- 移动端选择面板宽度不超过视口，并为结果列表保留可滚动高度。

## 9. 测试与验收

### 9.1 后端测试

- 1 人和多人批量创建成功。
- 重复成员去重并保持首次出现顺序。
- 0 人、超过 50 人、包含本人、非团队成员和无效成员校验。
- 任意成员无效时全部回滚。
- 相同幂等键重试返回原结果且不重复创建。
- 相同幂等键对应不同内容时返回冲突。
- 事务回滚时不发送通知。
- 权限和租户隔离。
- 现有单人创建接口回归通过。

### 9.2 前端测试

- 搜索姓名、账号和角色。
- 多选、取消选择、全选当前搜索结果和清空。
- 搜索词变化后已选成员保持。
- 切换团队时清空成员。
- 最少 1 人、最多 50 人限制。
- 请求中禁止重复提交。
- 成功结果人数正确，并能返回列表或继续发起。
- 失败后表单内容和成员选择保留。
- 打开、关闭、前进、返回和标签切换使用正确方向。
- `prefers-reduced-motion` 下无位移、缩放和错峰。
- 桌面和约 390px 宽度下无横向溢出。

### 9.3 验收标准

- 工作台打开、关闭和内部切换连续自然，没有明显跳动或延迟。
- 用户可以一次邀请 1 至 50 名当前团队成员。
- N 名成员成功提交后，数据库存在 N 条独立协作申请。
- 每名成员可以独立接受、拒绝和完成自己的任务。
- 批量请求不会出现部分成功。
- 网络重试或重复点击不会产生重复任务。
- 失败后用户输入不丢失。
- 动效不会妨碍键盘操作和减少动态效果用户。

## 10. 发布与回滚

- 先运行后端单元测试、控制器测试和学生端前端测试。
- 构建后端与学生端生产产物。
- 部署前备份当前后端包与学生端静态资源。
- 部署后验证登录态下的协作列表、单人创建兼容、多人创建、重复提交和任务状态流转。
- 若批量接口异常，可回滚后端包和学生端静态资源；现有单人数据结构未改变，不需要数据库回滚。
