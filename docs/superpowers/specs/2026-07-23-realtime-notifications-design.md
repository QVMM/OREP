# 学生端实时通知中心设计

## 目标

把学生端顶部通知从“点击后请求一次的消息列表”升级为可用的实时通知中心：

- 老师发送提醒后，在线学生无需刷新即可收到。
- 通知状态在服务端持久化，多设备保持一致。
- 角标只表示未读数量。
- 通知可点击，并进入明确的业务页面。
- 实时连接失败时仍可通过 REST 正常使用。

本期只覆盖现有教师端产生的训练提醒，不扩展成绩、会议、任务评论等新通知来源。

## 已有能力与问题

现有后端会把教师提醒写入 `teacher_portal_event`，学生端通过
`GET /api/notifications` 读取最近 20 条提醒。当前存在以下缺口：

- 学生点击铃铛后才首次请求，无法及时发现新提醒。
- 请求成功后不再刷新。
- 没有已读状态，角标表示列表条数而不是未读数。
- 通知条目不是可交互控件，点击后不会跳转。
- 项目虽有 STOMP/SockJS，但没有面向通知的用户级订阅与身份绑定。

## 技术方案

### 1. 持久化模型

继续使用 `teacher_portal_event` 作为通知事件来源，为其增加可空字段
`read_at DATETIME NULL`。现有提醒是一位接收者一条事件，
`target_id` 已经保存接收学生的用户 ID，因此已读状态可以安全地记录在事件本身。

服务启动时通过现有的兼容式表结构初始化补充字段，保持当前部署方式不变。

通知查询返回：

- `id`
- `eventType`
- `targetType`
- `title`
- `message`
- `deadline`
- `createdAt`
- `readAt`
- `isRead`
- `targetPath`

列表接口返回 `{ items, unreadCount }`。`items` 仍限制最近 20 条，
`unreadCount` 单独统计当前租户、当前用户全部未读提醒，避免角标被列表上限截断。

### 2. REST 接口

- `GET /api/notifications`
  - 首屏加载、断线降级和展开面板刷新。
- `PATCH /api/notifications/{id}/read`
  - 只能修改当前租户、当前用户拥有的提醒。
- `PATCH /api/notifications/read-all`
  - 将当前用户所有未读提醒标为已读。

所有写操作都同时校验 `tenant_id`、`target_id` 和
`event_type='REMINDER_SENT'`，禁止跨用户或跨租户修改。

### 3. 实时通道

复用现有 `/ws` STOMP/SockJS 端点。

- STOMP `CONNECT` 从 `Authorization: Bearer <token>` 读取 JWT。
- 服务端校验 Token 后，把 `userId` 绑定为 WebSocket `Principal`。
- 消息代理增加 `/queue`，学生只订阅 `/user/queue/notifications`。
- 教师提醒事务写入成功后，调用
  `convertAndSendToUser(userId, "/queue/notifications", notification)`。

客户端不在订阅地址中拼接用户 ID，避免用户猜测并订阅其他学生的消息。
现有会议 `/topic/**` 通道保持不变，本期不改会议消息模型。

### 4. 前端数据流

`WorkspaceTopbar` 不直接管理连接细节。新增一个通知客户端模块，负责：

- 页面进入后通过 REST 加载列表和未读数。
- 建立 STOMP 连接并订阅用户通知队列。
- 自动重连后重新订阅，并通过 REST 校准可能漏掉的消息。
- 收到推送时按 ID 去重，插入列表顶部并更新未读数。
- 页面重新获得焦点或展开通知面板时刷新 REST 数据。
- 组件卸载时取消订阅，不影响共享 WebSocket 客户端的其他订阅。

如果 WebSocket 连接失败，顶部通知仍可在展开面板或页面重新聚焦时更新。

### 5. 交互设计

通知面板头部显示“消息通知”、未读数量和“全部已读”。

每条通知使用真正的按钮元素：

- 未读通知使用轻微暖色背景和实心圆点。
- 已读通知保持白色背景，文字层级降低。
- 右侧显示箭头，明确可进入详情。
- 新通知到达且面板关闭时，显示一次 4 秒的轻量右上角提示。
- 不使用阻断弹窗，不自动切换用户当前页面。

点击通知时：

1. 立即在本地标记已读并减少角标。
2. 调用已读接口持久化。
3. 跳转通知的 `targetPath`。
4. 已读请求失败时重新拉取通知校准状态，不阻止页面跳转。

“全部已读”使用乐观更新；失败时恢复服务端数据并显示轻提示。

### 6. 跳转规则

本期现有通知都来自训练提醒：

- `TRAINING_CAMP` → `/training/today`
- `TRAINING_MISSING` → `/training/today`
- 其他未知提醒类型 → `/training/today`

跳转地址由服务端根据通知类型生成，不接受教师端传入任意 URL。
以后若通知载荷包含经过服务端验证的 `dayId` 或 `taskId`，
可以升级为对应训练任务的深链接。

## 错误处理

- 初始 REST 加载失败：面板显示“通知加载失败”和重试按钮，不伪装成“暂无通知”。
- WebSocket 断开：静默重连，保留现有通知；不连续弹错误提示。
- 推送重复：按通知 ID 去重。
- 已读接口失败：不阻断业务跳转，下一次 REST 刷新纠正状态。
- 无有效 Token：不建立通知订阅，沿用现有登录过期处理。

## 测试

### 后端

- 当前用户只能读取自己的通知。
- 单条已读和全部已读不能跨租户、跨用户操作。
- 未读数不受 20 条列表上限影响。
- 教师发送提醒后写入事件并向对应用户队列推送。
- WebSocket Token 能正确绑定用户身份，无效 Token 不能建立通知身份。

### 前端

- 首次进入加载通知和未读数。
- 实时消息到达后角标和列表立即更新。
- 重复推送不会出现重复条目。
- 点击未读通知会标记已读并跳转训练任务。
- 全部已读清空角标。
- WebSocket 失败时展开面板仍会刷新。
- 加载失败显示可重试状态。

## 非目标

- 不做浏览器系统级 Push Notification。
- 不做邮件、短信或移动端离线推送。
- 不把会议聊天、评分进度或协作评论纳入本期通知来源。
- 不重构现有会议实时通信。
