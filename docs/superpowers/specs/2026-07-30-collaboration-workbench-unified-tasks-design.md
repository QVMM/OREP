# 协作入口品牌图标与统一任务工作台设计

日期：2026-07-30  
状态：视觉与任务范围已确认，待书面审阅  
范围：用户端、教师端全局协作入口，协作悬浮工作台，统一工作项读取接口及相关测试

## 1. 背景

当前全局协作入口使用四个彩色方块，虽然有一定品牌识别度，但不能直接表达“成员连接、任务流转和跨角色协调”。用户已经指定新的“连接节点”SVG 轮廓，希望在此基础上加粗并做彩色科技感处理。

当前用户端协作工作台的 `/api/collaboration/summary` 与 `/api/collaboration/items` 只读取 `collaboration_request`。因此工作台能够显示学生之间的协作申请，却不会展示已经存在于 `project_task` 中的今日训练任务、团队任务和老师发布任务。教师端则从团队仪表盘、审核队列和协作摘要分别拼装数据，用户端与教师端的分类、状态和任务表达不一致。

本次改版要让“协作”成为平台级任务协调入口：既能发起、接受和处理协作申请，也能看到当前用户真正需要完成、提交或审核的任务。

## 2. 目标

1. 使用用户指定的“连接节点”SVG，建立用户端与教师端一致的协作品牌图标。
2. 侧栏底部入口继续以悬浮窗形式打开，不恢复为普通一级页面入口。
3. 在用户端统一展示今日训练、团队任务、老师任务和学生协作请求。
4. 在教师端统一展示待审核成果、管理范围内任务、老师发布任务和协作请求。
5. 统一工作项的来源、状态、截止时间、发起人和主操作表达。
6. 接受协作请求后避免同时显示“已接受申请”和其生成的项目任务。
7. 角标数量只表示“当前需要我立即处理”的工作项数量。
8. 保持现有任务提交、审核、协作接受/拒绝/撤回和实时通知能力不变。

## 3. 非目标

- 不重做项目团队完整任务管理页。
- 不改变训练营任务解锁、提交或审核规则。
- 不把通知中心、聊天、即时通信或在线会议并入协作工作台。
- 不新增跨团队随意指派权限；所有工作项仍受租户、团队成员和教师管理范围约束。
- 不修改 `project_task`、`collaboration_request` 和 `project_task_submission` 的业务写入模型。
- 不在第一版加入自定义排序、批量操作、拖拽看板或高级筛选。
- 不把资源中心重新合并进协作工作台。

## 4. 已确认产品决策

### 4.1 协作图标

使用用户提供的以下轮廓作为唯一图形来源：

- 圆形外边界代表全局协作范围；
- 三个节点代表发起人、协作者和任务承接者；
- 节点之间的连接路径代表任务协调、交付和反馈闭环。

正式实现：

- 保留原始 `viewBox="0 0 1024 1024"` 和路径结构；
- 路径增加约 `18px` 同色描边，使 36–60px 小尺寸更稳；
- 主填充采用从科技蓝到紫色、再到品牌橙的低跨度渐变；
- 允许使用轻微高光与投影，但不增加新的图形元素；
- 用户端与教师端复用同一 SVG 组件和同一颜色定义；
- 侧栏入口、悬浮窗标题和移动端入口分别验证 60px、48px、36px 容器下的辨识度。

图标不使用大面积霓虹、呼吸灯或持续旋转。只有存在待处理工作项时显示品牌橙数字角标。

### 4.2 任务范围

用户已经确认采用“全部相关任务”：

- 今日训练任务；
- 团队任务；
- 老师发布任务；
- 学生协作请求；
- 当前用户发起的协作任务。

教师端对应展示：

- 等待当前教师审核的成果；
- 当前教师管理团队中的非终态任务；
- 当前教师发布的任务；
- 当前教师可见的协作请求。

### 4.3 工作台分类

用户端和教师端统一使用四个一级分类：

| 分类 | 进入条件 |
| --- | --- |
| 待我处理 | 待接受的协作请求、当前用户待完成/待提交的任务、当前教师待审核成果 |
| 进行中 | 已接受或已经开始且尚未完成/取消的任务 |
| 我发起的 | 当前用户发起的协作请求或创建/发布的任务 |
| 全部 | 当前权限范围内的全部非重复工作项，终态项目放在后部 |

教师端不再把“待审核、进行中、已发布、已完成”作为另一套一级信息架构；审核和已发布语义分别落入“待我处理”和“我发起的”。

## 5. 统一工作项模型

### 5.1 读取模型

协作工作台使用只读投影 `CollaborationWorkItem`。它不替代原始业务表，只对前端提供一致表达。

固定响应字段：

```text
key                 稳定唯一键，例如 REQUEST:42、TASK:108
entityType          REQUEST | TASK
id                  原始实体 ID
teamId
teamName
sourceType          TRAINING_DAY | TEAM_TASK | TEACHER_ASSIGNMENT | PEER_COLLABORATION
sourceLabel         今日训练 | 团队任务 | 老师任务 | 学生协作
title
description
status
statusLabel
priority
dueAt
createdAt
updatedAt
requesterId
requesterName
recipientId
recipientName
ownerUserId
ownerName
assignees
reviewerUserId
linkedTaskId
trainingDayId
actionRequired
createdByCurrentUser
primaryAction        ACCEPT | OPEN | SUBMIT | REVIEW | NONE
targetPath
canAccept
canDecline
canWithdraw
```

前端不得根据中文标题猜测任务来源或跳转路径。

### 5.2 来源识别

- 与 `training_day_task` 关联的 `project_task` 统一标记为 `TRAINING_DAY`，优先级高于数据库原始 `source_type`。
- `project_task.source_type = TEACHER_ASSIGNMENT` 标记为老师任务。
- `project_task.source_type = PEER_COLLABORATION` 标记为学生协作任务。
- 其余 `project_task` 标记为团队任务。
- 尚未接受、没有 `linked_task_id` 的 `collaboration_request` 标记为学生协作请求。

### 5.3 去重规则

1. `collaboration_request` 仍为 `PENDING` 时显示请求工作项。
2. 请求被接受并生成 `linked_task_id` 后，以对应 `project_task` 为唯一工作项。
3. 已接受请求本身不再额外占一行，但任务详情可以保留原始请求人和接收人信息。
4. 教师待审核提交不新增独立重复任务；对应任务行改为 `actionRequired=true`，主操作变为“审核成果”。
5. 稳定键以最终呈现实体为准，确保刷新和实时通知不会生成重复行。

## 6. 权限与可见范围

### 6.1 学生

学生只看到：

- 自己是发起人或接收人的协作请求；
- 自己是 `owner_user_id` 或 `project_task_assignee` 的任务；
- 所在有效团队中的任务；
- 已达到训练日解锁条件的训练任务。

未解锁训练任务不得因为统一工作台而提前泄露标题、说明、附件或目标路由。

### 6.2 教师

教师只看到：

- 自己发起或接收的协作请求；
- 自己是导师或指导教师的团队任务；
- 自己创建的 `TEACHER_ASSIGNMENT`；
- 自己有权审核的最新提交。

### 6.3 管理员

现有租户管理员可见范围保持不变。本次前端不新增管理员专用工作台交互。

所有查询必须从服务端登录上下文读取 `tenantId`、`userId` 和 `role`；客户端不能指定任意用户范围。

## 7. 服务端设计

### 7.1 接口兼容策略

保留现有：

```text
GET /api/collaboration/summary
GET /api/collaboration/items
POST /api/collaboration/requests
POST /api/collaboration/requests/{id}/accept
POST /api/collaboration/requests/{id}/decline
POST /api/collaboration/requests/{id}/withdraw
```

其中两个读取接口升级为统一工作项读取模型，写接口保持不变。已有请求专属字段继续返回，避免详情和接受/拒绝流程破坏。

`GET /api/collaboration/items` 继续接受：

```text
view=ACTION_REQUIRED | IN_PROGRESS | CREATED_BY_ME | ALL
teamId
cursor
limit
```

### 7.2 服务职责

- `CollaborationService` 只继续处理协作请求的创建和状态变更。
- 新增 `CollaborationWorkItemService`，分别读取可见请求、可见任务和待审核提交，再归一化、去重、过滤和排序。
- `CollaborationController` 的 `summary` 与 `items` 委托给 `CollaborationWorkItemService`，请求详情与写操作继续委托给 `CollaborationService`。
- 不通过循环调用每个团队的仪表盘接口拼接任务，避免 N+1 查询。
- 查询结果必须带足够的来源与导航字段，前端不重复实现权限判断。
- `summary` 必须基于与 `items` 相同的统一读取规则，避免角标数量和列表内容不一致。

### 7.3 排序

- 待我处理：已逾期优先，其次按截止时间升序，无截止时间的按更新时间降序。
- 进行中：按截止时间升序，无截止时间的按更新时间降序。
- 我发起的：按更新时间降序。
- 全部：非终态在前，终态在后；组内按更新时间降序。

分页游标不能只使用原始数值 `id`，因为统一列表来自多个实体。升级为包含排序时间、实体类型和 ID 的不透明游标；第一版前端只负责透传。

## 8. 状态与主操作

### 8.1 状态归一

| 原始状态 | 工作台状态 |
| --- | --- |
| 请求 `PENDING` 且我是接收人 | 待接受 |
| 请求 `PENDING` 且我是发起人 | 等待回应 |
| 任务 `TODO` | 待开始 |
| 任务 `IN_PROGRESS` | 进行中 |
| 任务 `REVIEWING` 且我是提交人 | 待审核 |
| 最新提交待审核且我是审核人 | 待审核 |
| 审核要求修改 | 待修改 |
| 任务 `DONE` | 已完成 |
| 请求 `DECLINED/WITHDRAWN` 或任务 `CANCELLED` | 已结束 |

### 8.2 主操作

- 待接受请求：接受、婉拒。
- 我发起的待回应请求：查看、撤回。
- 已解锁训练任务：进入 `/training/tasks/{taskId}?dayId={trainingDayId}`。
- 团队、老师和学生协作任务：进入 `/project-team/details/task-{taskId}`。
- 当前用户可提交的任务：主操作文案为“去完成”或“提交成果”。
- 当前教师待审核任务：主操作为“审核成果”，进入工作台内现有审核详情。
- 已完成或无进一步动作的项目：查看详情，不显示虚假可操作按钮。

## 9. 前端交互与视觉

### 9.1 侧栏入口

- 继续固定在左侧一级菜单最底部，与普通模块入口拉开视觉分组。
- 使用最终连接节点图标。
- 默认状态保持克制；悬停和聚焦时增加浅蓝底与可见焦点环。
- 角标上限显示为 `99+`，只读取 `summary.actionRequired`。
- 点击后打开悬浮工作台，再次点击或按 `Esc` 关闭。

### 9.2 悬浮工作台

- 保持平台现有卡片、圆角、阴影、字号和间距令牌。
- 标题区使用新图标，标题为“协作工作台”。
- 用户端副标题为“协调任务、接收反馈并提交成果”。
- 教师端副标题为“发布协调任务并验收团队成果”。
- 四个分类横向排列；空间不足时可横向滚动，不能压缩到不可读。
- “发起”按钮保持唯一高强调操作。教师文案为“发布任务”，学生文案为“发起协作”。

### 9.3 任务行

每行固定包含：

1. 来源标签和状态；
2. 任务标题；
3. 团队名称；
4. 发布人/发起人；
5. 截止时间；
6. 与当前用户权限匹配的主操作。

来源颜色：

- 今日训练：品牌橙；
- 团队任务：科技蓝；
- 老师任务：绿色；
- 学生协作：紫色。

颜色只作为辅助识别，来源文字不能省略。逾期、失败和待修改使用平台现有警示颜色，不复用来源颜色表达风险。

### 9.4 响应式与无障碍

- 桌面端悬浮窗保持当前侧栏右侧定位和最大高度。
- 720px 以下使用左右 8px、顶部 66px、底部 8px 的近全屏浮层。
- 所有任务行、分类和操作按钮必须可键盘访问。
- 打开浮层后焦点进入浮层；关闭后返回协作入口。
- 图标本身为装饰元素，入口按钮提供“打开协作工作台”的可访问名称。
- 尊重 `prefers-reduced-motion`，不依赖动画传递状态。

## 10. 刷新、实时与错误处理

1. 工作台首次打开时并行读取摘要和当前分类。
2. 收到 `COLLABORATION_*`、`TEACHER_TASK_ASSIGNED`、任务提交或审核相关通知时刷新摘要与当前分类。
3. 窗口重新聚焦时刷新，防止长时间后台停留导致状态过期。
4. 刷新失败时保留上次成功数据；列表区域显示错误与“重新加载”。
5. 首次读取失败且无缓存时显示空错误态，不能把 404 误写成“暂无任务”。
6. 接受、拒绝、撤回、提交或审核成功后立即刷新相关分类和角标。

## 12. 验证标准

1. 用户端和教师端均使用用户指定的连接节点图标，不再出现四色方块图标。
2. 36px、48px、60px 三种容器下图标无裁切，外圆和三个节点可辨认。
3. 用户端“待我处理”能同时出现已解锁训练任务、团队/老师任务和待接受协作请求。
4. 教师端“待我处理”能出现待审核成果及需要教师响应的协作请求。
5. 接受协作请求后，刷新列表只显示生成的 `PEER_COLLABORATION` 任务，不显示重复申请行。
6. 训练日未解锁时，学生工作台不能看到对应任务。
7. 学生不能通过 `teamId` 参数读取其他团队任务；教师不能读取管理范围外团队。
8. 来源、状态、团队、发布人和截止时间在任务行中完整显示。
9. 训练任务和普通项目任务分别进入正确目标路由。
10. 角标数量与“待我处理”实际非重复条目数量一致。
11. 请求接受、拒绝、撤回以及任务提交、审核的现有流程继续通过。
12. 列表失败时显示明确错误，不把服务异常呈现为空列表。
13. 桌面端和 720px 以下布局无横向页面滚动，浮层可完整操作。
14. 学生端、教师端构建通过，协作接口单元/集成测试和浏览器端契约测试通过。

## 13. 发布与回退

- 继续受现有 `OREP_COLLABORATION_ENABLED` 与 `VITE_COLLABORATION_ENABLED` 控制。
- 数据库不新增迁移，发布风险集中在读取模型和前端呈现。
- 若统一工作项读取发生线上问题，可在不回退协作写入数据的情况下关闭协作功能开关或回退应用版本。
- 部署时必须同时更新后端、用户端和教师端，避免旧前端误解新的统一响应。
