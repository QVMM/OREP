# AI 评分“单次归因、三账本”正式设计

## 1. 背景与问题

现行评分链路将观测点满分、能力达成分、证据封顶和额外扣分直接叠加。在真实视频会话 `24` 中，同一个“缺少可核验证据”事实同时导致：

1. 能力达成比下降；
2. E0–E5 证据等级封顶；
3. `evidence-gap` 类型规则再次扣分。

因此旧策略得到：

```text
100.00
- 34.70 能力达成差距
- 11.70 证据封顶差距
- 14.50 额外扣分
= 39.10
```

其中 14.50 分额外扣分基本与前两层原因重复。当前 39.10 在数学上可复算，但在评分制度上不可作为可信结果。

## 2. 设计目标

### 2.1 用户目标

- 用户只看到一个正式 AI 分数。
- 用户不需要理解后台计算细节，但任何一分都能追溯。
- 用户能区分“表现没做到”、“做了但证据不足”和“额外违规”。
- “最高可争取”不承诺加分，不与满分差距混淆。

### 2.2 制度目标

- 同一个事实原因只能影响一次分数。
- 总分、维度分、观测点和失分账本误差不得超过 0.01 分。
- 相同结构化输入必须生成完全相同的正式分。
- 42 赛道的维度权重、观测点满分和 E0–E5 证据上限继续使用。
- 在没有专家黄金样本的阶段，先保证内部一致性、可追溯性和重复评分稳定性，不宣称与真实赛事专家完全一致。

## 3. 核心计分模型

### 3.1 观测点输入

每个 Observation 必须包含：

- `observationCode`：观测点编号；
- `dimensionCode`：所属维度；
- `maxScore` (`M`)：该观测点满分；
- `performanceScore` (`P`)：仅依据当前视频或当前现场可观测表现得到的能力分；
- `evidenceScoreCap` (`C`)：当前证据强度允许确认的最高分；
- `hardPenalty` (`H`)：独立违规事件的有效扣分；
- `performanceReason`：只解释可观测的操作、结果、完整度和熟练度；
- `evidenceReason`：只解释来源、可核验性、时间、对象和结果边界；
- `evidenceAnchorIds`：支持当前判断的会话内证据；
- `confidence`：识别与归因置信度。

### 3.2 单项公式

进入规则引擎前必须标准化：`0 <= P <= M`、`0 <= C <= M`、`H >= 0`。任何越界值触发契约失败，不允许静默截断后发布。

```text
scoreBeforePenalty = min(P, C)
finalObservationScore = max(0, scoreBeforePenalty - H)
```

其中：

```text
performanceGap = M - P
evidenceLimitedGap = max(0, P - C)
effectiveHardPenalty = min(H, min(P, C))
```

必须满足：

```text
M = finalObservationScore
  + performanceGap
  + evidenceLimitedGap
  + effectiveHardPenalty
```

总分是全部 `finalObservationScore` 之和。三类失分的合计与 `100 - finalScore` 完全一致。

全局赛事规则（例如超时或总分封顶）在观测点合计后执行。其对总分的实际影响必须转换为带规则编号的 `hard_violation` 账本行，保证总账仍然成立，不允许存在无解释的暗中封顶。

### 3.3 三阶段判断架构

表现与证据不能由同一段未分界提示词一次生成。新策略使用边界独立的三阶段判断：

1. **表现评估器**：只接收观测点的可观测任务定义、视频、转写和当前现场成果；不接收外部材料清单、第三方验证要求或 `evidenceCaps`；输出固定表现档位、`performanceScore` 和可观测理由。
2. **证据验证器**：接收规则所需材料、证据来源、时间点、对象、结果边界和可核验性；只输出 E0–E5、`evidenceScoreCap` 和证据理由，不修改 `performanceScore`。
3. **确定性规则引擎**：读取前两阶段的结构化结果，只根据显式 `hard_violation` 规则执行额外扣分，生成三账本和唯一正式分。

两个 AI 判断阶段使用固定模型版本、低温度、JSON Schema 和枚举字段。规则引擎不调用 LLM，确保相同结构化输入精确复算。

## 4. 三类失分的互斥边界

### 4.1 表现差距

`performanceScore` 只判断“当前路演做得怎么样”。

允许影响表现分的原因：

- 操作错误或技能不熟练；
- 过程不完整，缺少必要步骤；
- 当前展示结果质量不足；
- 讲解、节奏或现场配合影响任务完成；
- 应在当前现场展示的必要任务未展示。

禁止作为表现降分原因：

- 缺少第三方证明；
- 缺少书面材料；
- 数据来源无法核验；
- 缺少订单、客户反馈或运营附件；
- 只有当前视频无法提供的外部佐证。

### 4.2 证据限制

`evidenceScoreCap` 只判断“已经展示的内容能确认到什么程度”。

- E0–E5 的封顶比例仍由当前赛道规则决定；
- 证据不足只能降低 `C`，不能生成额外 `H`；
- 证据等级与表现达成度必须分开输出理由；
- 同一证据可以支持多个观测点，但必须说明对每个观测点的具体支持内容；
- 大量观测点无差别绑定相同证据时，进入重试或复核，不直接发布。

### 4.3 独立违规

`hardPenalty` 只处理评分项正常达成度和证据强度之外的额外事件：

- 赛事明确规定的超时；
- 作假、前后矛盾或伪造数据；
- 安全、合规、版权或知识产权的明确违规；
- 严重偏离赛道或组别的强制规则；
- 赛事文件明确规定的其他扣分事件。

每个独立违规必须具备：

- `penaltyRuleCode`：可追溯规则编号；
- `causeCode`：当前评分中唯一的原因编号；
- `triggerFact`：已发生的事实，不能使用“未提供证据”表述；
- 当前 Session 的证据锚点或确定性系统事件；
- 扣分上限和是否允许后续恢复。

## 5. 单次归因账本

所有失分原因必须写入 `lossLedger`：

```json
{
  "causeCode": "O10-EVIDENCE-OPERATING-DATA",
  "observationCode": "O10",
  "lossType": "evidence_limited",
  "points": 1.5,
  "reason": "已展示市场分析，但缺少项目实际销量、转化率或ROI记录",
  "evidenceAnchorIds": [101, 102],
  "consumedBy": "evidence_cap"
}
```

`lossType` 只允许：

- `performance_gap`；
- `evidence_limited`；
- `hard_violation`。

`causeCode` 不由 LLM 根据自由文本临时编造。每套规则必须为可计分条件提供稳定的 `criterionCode` 和 `deficitCode`，引擎通过 `observationCode:criterionCode:deficitCode` 生成 `causeCode`。自由文本只用于解释，不用于决定是否重复。

发布前必须校验：

- 同一 `causeCode` 只能出现一次；
- 同一事实不得以不同措辞落入多个账本；
- `evidence_limited` 不得再转换为 `hard_violation`；
- `performance_gap` 的理由不得包含外部证据缺失语义；
- 账本合计与满分差距必须完全一致。

## 6. 42 赛道规则迁移

### 6.1 保留内容

- 赛道、赛事、组别和规则版本解析；
- 维度权重和观测点满分；
- `requiredInfo`、`acceptableEvidence` 和验证方法；
- E0–E5 封顶比例；
- 整改任务、可接受材料和验收条件。

### 6.2 扣分规则分类

现有 `deductionRules` 自动迁移为：

- `evidence_gap`：证据不足，只产生证据封顶和整改任务，`scoreEffect = diagnostic_only`；
- `performance_gap`：属于正常达成度，只影响 `performanceScore`，`scoreEffect = included_in_performance`；
- `hard_violation`：仅在具备明确事件触发条件时额外扣分，`scoreEffect = subtractive`。

当前类似 `D-33-O04-evidence-gap` 的规则必须迁移为 `diagnostic_only`，不再从正式分中重复扣减。

迁移分类必须确定性执行：

- ID 或显式类型为 `evidence-gap` 的规则直接迁移为 `diagnostic_only`；
- 只有配置了 `penaltyType = hard_violation`、事件型触发条件和规则编号的规则才可以额外扣分；
- 无法分类的旧扣分规则默认不影响正式分，并进入规则准入报告，禁止为了“保守”而默认扣分；
- 42 赛道对 `requiredInfo` 和风险条件生成稳定 `criterionCode` / `deficitCode`，代码稳定性由迁移映射文件和规则哈希保证。

### 6.3 版本与指纹

- 新规则策略版本为 `score-policy-v2-single-attribution`；
- 任何扣分语义迁移都必须生成新 `ruleHash`；
- 评分指纹必须包含媒体哈希、材料哈希、赛道规则哈希、评分策略版本、提示词版本、模型版本和阈值配置；
- 旧报告保留原指纹，不静默改分。

## 7. 最高可争取与多轮路演

### 7.1 三种改善类型

- `evidenceUnlockPotential`：不改变当前表现分，仅将有效证据升级后可能解锁的上限；
- `recoverableHardPenalty`：新一轮证明违规事件已消失后，根据规则可撤销的上限；
- `performanceGap`：只能通过重新演练和重新展示改变，不得伪装成“上传材料即可追回”。

### 7.2 补证情景复算

在用户未提交新证据前，只能输出：

最高可争取不进行简单求和。情景引擎复制当前评分输入，只将用户可补齐的证据缺口提升至规则允许的最高已证明等级，并仅撤销规则明确允许恢复的独立违规，然后使用同一规则引擎复算：

```text
recoverableScore = scenarioFinalScore - currentFinalScore
```

`scenarioFinalScore` 不得超过当前 `performanceScore` 允许的总上限，因此上传证据不能直接补回表现差距。

文案固定为：

> 最高可争取约 X 分，最终以新增证据核验和重新评分结果为准。

提交新证据后，系统必须先重新判定证据等级，再通过规则引擎重算，不能直接将上限加到原分。

### 7.3 多轮路演

- 每轮先根据当前视频、材料和规则版本独立评分；
- 对比层分别追踪表现差距、证据限制和独立违规的变化；
- 只有新一轮当前证据验证通过，才可标记上一轮问题已改善；
- 上一轮的扣分不直接带入新一轮分数；
- 趋势对比使用正式分和同类失分账本，不比较不兼容规则版本的绝对分。

## 8. 证据与发布门禁

### 8.0 赛道、赛事与组别绑定门禁

正式评分不得根据视频内容猜测赛道，也不得使用页面默认值、历史会话参数或运维人员临时选择静默代替用户确认。评分入口必须保存一份版本化的 `competitionBinding`：

- `competitionId` / `competitionName`：赛事标识；
- `trackId` / `trackName`：赛道标识；
- `groupId` / `groupName`：组别标识；
- `ruleVersion` / `ruleHash`：实际采用的规则版本；
- `selectionSource`：只允许 `user_selected`、`registration_binding`、`project_binding`；
- `confirmedAt` / `confirmedBy`：确认时间和确认主体。

绑定解析优先级固定为：用户本次明确选择 > 报名记录唯一绑定 > 项目唯一有效绑定。若缺少绑定、存在多个候选、赛事或组别规则无法解析，则会话进入 `track_confirmation_required`，不得启动正式评分。视频内容识别只能给出候选提示，不能自动确认。

技术回归允许使用 `diagnostic_override`，但必须同时设置 `publishOfficialScore=false`，结果只能标记为诊断运行，不能写入用户正式报告，也不能参与多轮趋势。

评分指纹必须包含完整 `competitionBinding`；绑定任一字段或规则版本变化，都必须生成新指纹并重新评分。

正式分发布前必须通过：

1. 规则解析成功，观测点满分合计为 100；
2. 所有观测点具备 `performanceReason` 和 `evidenceReason`；
3. 非 E0 证据必须有当前 Session 的有效锚点；
4. 证据来源和置信度缺失时先重试抽取，重试后仍大量缺失则进入 `review_required`；系统推断的诊断置信度必须标记 `confidenceOrigin = inferred_default`，不能单独满足正式发布门禁；
5. 证据置信度全部为 0 时不得发布正式分；
6. `hard_violation` 必须有规则编号、触发事实和证据锚点；
7. `causeCode` 不重复，且损失账本对账成功；
8. Python 正式分与 Java 结构化复算结果一致；
9. 维度合计、观测点合计和总分误差不超过 0.01；
10. 评分结果通过指纹和回调幂等门禁。
11. `competitionBinding` 已确认，且不来自默认值、历史参数或内容猜测。

门禁失败时不能降级为旧 LLM 分数发布，应进入 `review_required` 或 `calculation_failed`。

## 9. 用户产品契约

用户主界面仍只展示一个 AI 正式分。评分解释使用三个简单概念：

- 当前路演表现；
- 证据能支持到的程度；
- 是否发生额外违规。

用户不展示 `llmRawScore`、影子分或多个竞争性总分。表达、节奏、临场、说服力和改进趋势属于训练诊断，只有当它们是某个 Rubric 观测点的明确评分条件时才影响正式分。

## 10. 稳定性与验收标准

### 10.1 42 赛道生成式测试

每个规则版本必须通过：

- 满分合计恰好为 100；
- 表现分、证据上限和最终分均在合法区间；
- 提升有效证据等级不得降低分数；
- 删除独立违规不得降低分数；
- 重复证据不得重复加分；
- 重复 `causeCode` 必须被拒绝；
- `evidence_gap` 和 `performance_gap` 类型不产生额外扣分；
- 账本算式在每个观测点和总分级别都完全成立。

### 10.2 重复评分稳定性

- 模型和提示词版本固定；
- 结构化输出使用枚举、数值范围和 JSON Schema 校验；
- 同一证据快照复算必须精确相同；
- 同一媒体完整重跑的正式分漂移超过 3 分时进入复核；
- 试运行阶段保留每次抽取差异、账本差异和规则指纹。

### 10.3 当前阶段的边界

没有专家或黄金样本时，本设计可验证：

- 计分公式正确；
- 原因不重复归因；
- 证据与规则可追溯；
- 相同输入复算一致；
- 重复评分漂移可监测。

本设计不宣称 AI 分数已经与真实赛事专家分数完全校准。

## 11. 失败处理与回退

- 证据抽取失败：限次重试，仍失败则不发布正式分；
- 规则迁移失败：当前赛道继续使用已发布旧策略，但新评分会话标记为旧版本，不混用新旧公式；
- Python 与 Java 复算不一致：报告进入 `calculation_failed`；
- 低置信度、证据矛盾或大量证据泛化：进入 `review_required`；
- AI 评审团失败：仅影响诊断复核，不改变正式分；
- 新策略可通过策略版本开关快速停止新报告放量，不篡改已发布历史报告。
