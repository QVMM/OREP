# OREP AI 生成 PPT 式 HTML 功能

## 多角色联合评审结论、问题清单与统一优化路线图

> 目的：把“产品经理、赛事专家、路演专家、PPT 专家、编导专家、架构专家、前端专家、后端专家”八个视角收敛成一份统一结论，帮助团队对这条功能形成一致认知，并明确下一阶段到底先改什么。

> 结论先行：OREP 当前这条功能已经不是“AI 生成器”，而是一个**面向职业院校技能大赛场景的路演内容生产与交付工作台**。它的主要问题不是“功能不够”，而是：
>
> 1. 比赛导向、叙事导向、页面契约导向还不够强  
> 2. 生成、质检、评分、素材、修复、交付几套系统没有彻底收口成唯一当前态  
> 3. 用户主路径仍然过重，系统暴露了太多内部概念  
> 4. 页面生成前的约束不够硬，导致系统更擅长“发现问题”，还不够擅长“第一次就生成对”

---

## 1. 多角色联合评审结论

### 1.1 这条功能的当前真实定位

从八个角色的共识来看，OREP 的 `AI 生成 PPT 式 HTML` 功能，本质上已经是：

> 一个“问卷输入 -> 比赛叙事策划 -> 页面生成 -> 质量检查 -> 单页修复 -> 证据绑定 -> 交付门禁 -> 下载导出”的完整系统。

也就是说，它不再只是：

- AI 写文案
- AI 生成网页

而是：

- AI 生成比赛路演内容
- AI 做结构检查
- AI 做评分点覆盖检查
- AI 做视觉审查
- AI 参与修复与补强
- 最终由系统判断“是否可以交付”

### 1.2 当前功能的 4 个明显优点

#### 1. 已经具备“先策划、再生成、再检查、再修复”的正确骨架

这一点非常关键。系统不是直接把问卷扔给模型换来 HTML，而是采用：

- Round 1：结构化项目画像
- Round 2：叙事大纲
- Round 3：内容充实
- Round 4：HTML 生成

随后再做：

- 质量报告
- 评分覆盖
- 路演结构
- 实操闭环
- 素材证据
- 视觉审查
- 下载门禁

这说明整体方向是对的。

#### 2. 已经有“人在回路”的关键环节

用户不是被动接受 AI 输出，而是可以：

- 编辑大纲
- 选择风格
- 预览页面
- 补图
- 单页修复
- 补评分点
- 再决定是否下载

这使它具备向“高质量工作台”演进的基础。

#### 3. 已经意识到“比赛可交付”不是生成成功

这是系统最有业务价值的一点。

当前系统已经把结果区分成：

- `blocked`：不可直接交付
- `warning`：当前版可下，但建议继续补强
- `ready`：可交付

这比普通 AI 生成产品高一层。

#### 4. 已经开始形成“当前页工作台”思路

当前前端已经在逐步把用户动作收敛到：

- 当前页讲稿
- 当前页风险
- 当前页补图
- 当前页修复
- 当前页主动作

这是未来真正简化体验的正确主路径。

### 1.3 当前功能的 4 个核心短板

#### 1. 比赛导向还没有成为系统的第一性原则

系统已经有评分覆盖和路演结构，但很多规则仍然带着：

- 商业 BP 偏向
- 通用产品汇报偏向
- 普通 HTML 生成偏向

而不是默认按“职业院校技能大赛 60 分钟汇报 + 实操”的模式来生成和约束。

#### 2. 页面契约和编导约束还不够硬

当前系统更像：

- 先生成
- 再审查
- 再修复

而不是：

- 先定义页面契约
- 先定义主视觉与证据位
- 先定义评分点职责
- 再生成

这会导致模板化、空洞页、焦点弱、缺证据页反复出现。

#### 3. 后端没有完全收口成“唯一当前真相”

当前用户感知到的很多问题，本质是：

- 任务状态一套
- 快照一套
- 当前 HTML 一套
- 质量报告一套
- 评分覆盖一套
- 素材绑定一套
- 下载门禁再聚合一套

这会导致：

- 做了却像没生效
- 传了图还说缺图
- 补了评分点但分数不涨
- 下载门禁像一直在变

#### 4. 用户主路径仍然偏重

虽然体验已经比之前顺很多，但从新人视角看，系统仍然需要用户理解：

- 路演结构
- 评分覆盖
- 质量报告
- 实操演示
- 素材证据
- 下载条件
- 总审

这说明系统目前更像“专业工作台”，还不够像“顺手的产品”。

### 1.4 联合结论

如果把八个角色的观点收成一句话：

> OREP 当前最需要做的，不是继续堆新功能，而是把“比赛导向、页面契约、唯一当前态、当前页主工作台”这 4 件事收口。只有这样，系统才会从“能生成、能检查、能修复”升级成“稳定产出比赛级 HTML”。

## 2. 角色分工视角下的问题清单

下面按八个角色分别列出最关键的问题。

## 2.1 产品经理视角

### 主要问题

1. 主路径仍然太重，用户要理解太多系统内部概念。
2. Step 0 -> Step 1 -> Step 3 的心智切换跨度大。
3. `PptHistoryDetail` 更像分析平台，而不是任务完成流。
4. 下载前处理虽然已经优化很多，但仍偏“条件解释”，不够“系统代办”。
5. 高级能力仍然过早暴露。

### 产品判断

用户真正想做的是：

- 让我先生成
- 告诉我哪里不行
- 尽量帮我自动补
- 到了可下载就直接让我下

而不是理解：

- evidence plan
- blocker detail
- route reason
- template risk

### 优先级

- `P0`：统一主流程语言、预览页成为唯一主工作台、下载前处理进一步代办化
- `P1`：历史详情页继续减法、问卷引导更轻、失败分流更自动
- `P2`：双前端定位、导出增强、技术债治理

## 2.2 赛事专家视角

### 主要问题

1. 系统虽然有“评分覆盖”，但默认评分规则还未彻底赛事化。
2. 路演结构检查已存在，但还没完全升级成“比赛规则引擎”。
3. 系统对“60 分钟汇报 + 实操”的章节分配还不够强约束。
4. “可交付”标准里，比赛项和一般质量项仍然耦合得偏紧。

### 赛事判断

比赛真正看重的是：

- 技能水平
- 任务难度
- 技术先进性
- 讲解效果
- 应用价值
- 团队协作
- 创新成效

而不是普通商业 BP 的：

- 商业模式
- 融资逻辑
- 财务预测

这些内容不是不能有，但优先级应低于比赛核心项。

### 优先级

- `P0`：评分规则默认切换成赛事优先模板
- `P0`：大纲阶段就强校验比赛必备结构
- `P1`：把“比赛可交付”单独定义，不混进一般页面审美问题

## 2.3 路演专家视角

### 主要问题

1. 故事线目前更多是“合理”，还不够“有上台节奏”。
2. 当前系统更擅长单页修正，不够擅长章节编排。
3. “主讲什么、承接什么、如何转场”还没有成为生成硬约束。

### 路演判断

真正好的比赛路演，不只是页对，而是：

- 开篇要立住问题与可信度
- 中段要建立方案与实操可信度
- 收束要建立价值、创新与团队印象

系统如果没有“章节镜头感”，就容易出现：

- 页面都对，但整体不顺
- 逻辑没错，但没有节奏

### 优先级

- `P0`：把章节职责写进页面契约
- `P1`：让视觉审查输出“跳段 / 承接弱 / 转场断裂”这类导演语言

## 2.4 PPT 专家视角

### 主要问题

1. 风格样张偏“封面预览”，不是“页面系统预览”。
2. 页面角色有了，但页面类型还不够成体系。
3. 焦点、密度、证据承载仍然容易失稳。

### PPT 判断

目前至少需要稳定支持 8 类强契约页面：

- 封面页
- 目录页
- 政策/背景证据页
- 问题洞察页
- 方案总览页
- 技术架构页
- 实操/结果证据页
- 团队/价值/总结页

### 优先级

- `P0`：把风格样张升级为“页系样张”
- `P0`：页面契约前置到 Round 3/4
- `P1`：视觉焦点和证据位进入生成硬约束

## 2.5 编导专家视角

### 主要问题

1. 模板化反复出现，本质是“这页到底要表达什么”没先定死。
2. 空洞页不是缺字，而是缺核心承载物。
3. 证据当前更像补充物，还不是页面主体的一部分。

### 编导判断

真正的“单页重设计”不应该是：

- 再润一下 HTML

而应该是：

- 先重做这一页的结构方案
- 再决定文案与视觉焦点
- 再生成 HTML

### 优先级

- `P0`：把修复从“补丁式 repair”升级成“单页重设计”
- `P1`：把视觉审查输出从问题列表升级成设计约束

## 2.6 架构专家视角

### 主要问题

1. `ppt_service.py` 过于集中，是系统性单点。
2. 当前系统缺“唯一当前态聚合层”。
3. 状态模型太多：
   - task status
   - pipeline jobs
   - quality report
   - scoring coverage
   - materials
   - deliverability
4. 工作流虽然跑得通，但一致性代价过高。

### 架构判断

系统未来必须分成三层：

1. **事实层**
   - 当前 HTML
   - 当前显式素材绑定
   - 当前 outline

2. **派生层**
   - 质量
   - 评分
   - 路演结构
   - 实操闭环

3. **决策层**
   - 交付门禁
   - 当前推荐动作
   - 下载路径

### 优先级

- `P0`：建立唯一当前态聚合层
- `P0`：素材绑定改成 confirmed / recommended 双层模型
- `P1`：继续把前端和后端流程控制做显式分层

## 2.7 前端专家视角

### 主要问题

1. `ppt.js` 仍然是混合式大总管，旧流程和新流程共存。
2. `PptEditor` 仍有双状态源。
3. `PptHistoryDetail` 虽然拆了组件，但动作编排层仍然很重。
4. 下载条件卡已经接近二级工作流引擎，复杂度高。

### 前端判断

当前最大的前端风险不是“UI 不好看”，而是：

> 流程状态、动作编排、页面职责没有彻底分层。

### 优先级

- `P0`：拆 `ppt.js`
- `P1`：把 `PptEditor` 流程控制抽成 composable/store
- `P1`：把 `PptHistoryDetail` mutation/download flow 再下沉一层
- `P1`：顶部 tab 再降成主视图 + 高级视图

## 2.8 后端专家视角

### 主要问题

1. 生成、评分、素材、修复、交付几套逻辑交叉耦合。
2. `recommended_page_bindings` 被当成事实，导致缺图误判。
3. 修复缺少根因分流和熔断。
4. 评分规则默认带商业 BP 偏向。
5. Prompt 的“草稿态占位”与“终稿态零占位”没有分层。
6. LLM 错误语义不统一。

### 后端判断

当前很多用户问题，不是“模型没生成好”，而是系统没有先定义：

- 当前 HTML 真相是什么
- 当前评分真相是什么
- 当前素材绑定真相是什么
- 当前交付真相是什么

### 优先级

- `P0`：confirmed material binding
- `P0`：deliverability 聚合口径收口
- `P0`：scoring checker 改成赛事优先
- `P1`：repair 根因分流 + 熔断
- `P1`：Prompt 草稿态 / 终稿态分层
- `P2`：统一 LLM 错误契约

## 3. 统一优化路线图

下面把八个角色的意见收成一套统一路线图。

## 3.1 路线图的总原则

下一阶段不建议再以“加功能”为主，而要围绕这 4 个原则推进：

1. **比赛优先**
2. **契约前置**
3. **当前态唯一**
4. **当前页主工作台**

换句话说：

- 先定义比赛型对不对
- 再定义页面应该长成什么
- 再保证系统知道最新状态是什么
- 最后把修复和下载尽量收回当前页完成

## 3.2 第一阶段：先收口比赛导向与当前态口径

### 目标

解决“系统说得不一致”“补了像没补”“评分和比赛不完全对齐”的问题。

### 重点动作

1. 建立唯一当前态聚合层  
2. 素材绑定改成 `recommended + confirmed` 双层  
3. 评分规则默认切到赛事优先模板  
4. 交付门禁明确区分：
   - 硬阻塞
   - 软补强建议  
5. Prompt 分层：
   - 草稿态允许占位
   - 终稿态禁止占位进入正式内容

### 成果标准

- 用户补图后，不会再出现“传了还说缺图”
- 用户补评分点后，分数变化真实可信
- 下载条件和总审不会出现状态打架
- 比赛规则与评分覆盖的关系清晰可解释

## 3.3 第二阶段：把页面生成从“后修型”升级成“前约束型”

### 目标

减少模板化、焦点弱、空洞页、证据弱页的生成概率。

### 重点动作

1. 页面契约前置到 Round 3/4  
2. 风格样张升级成“页系样张”  
3. 证据位前置进页面设计元数据  
4. 视觉焦点从检测项升级成生成硬约束  
5. 单页修复正式升级成“单页重设计”

### 成果标准

- 页面类型明显分化，不再是一套通用结构反复换文案
- 证据页、技术页、实操页、总结页具备稳定差异
- 视觉审查通过率提升，修复次数下降

## 3.4 第三阶段：把主流程真正收成“任务完成流”

### 目标

让用户不用理解整个系统，只要围绕当前任务完成路径工作。

### 重点动作

1. 预览页成为唯一主工作台  
2. 素材证据、评分覆盖、路演结构进一步降成：
   - 当前页内联处理
   - 高级视图补充  
3. 下载条件卡继续从“说明”进化成“系统代办”  
4. 前端状态模型改成 `task session`

### 成果标准

- 用户大部分动作不需要跨多个 tab
- 用户知道自己永远在：
  - 生成
  - 预览
  - 修复
  - 下载前处理
  这 4 种流程之一

## 3.5 第四阶段：做真正的“智能一键修复并达标”

### 目标

把“系统很会告诉你哪里有问题”，升级成“系统会尽量帮你补到能交付”。

### 重点动作

1. 智能一键修复编排器  
2. 自动循环：
   - 结构修正
   - 页面重做
   - 补评分点
   - 补图/临时图
   - 复检  
3. 收益不足自动换策略  
4. 只在必须时才让用户补真人材料

### 成果标准

- 用户不会陷入“手动一页页折腾”
- 绝大部分测试阶段任务能自动走到 `warning` 或 `ready`

## 4. 先改产品、内容逻辑，还是先改代码实现？

这件事的答案不是二选一，而是有顺序：

### 结论

> **先统一比赛导向和页面契约，再同步做 P0 级代码收口，最后再继续做大规模实现优化。**

换成更直白的话就是：

### 第一步：先定规则

先把这 3 件事定清楚：

1. 什么叫比赛可交付
2. 什么叫一页技术页/证据页/实操页/总结页
3. 什么算当前真相，什么只是推荐/快照

这是产品逻辑和内容逻辑层面的工作。

### 第二步：立刻同步做 P0 代码收口

因为当前系统已经在跑，不能等规则全写完再动代码。

最先要改的代码层是：

1. 唯一当前态聚合
2. confirmed material binding
3. scoring checker 赛事优先化
4. repair 根因分流

### 第三步：再做中期重构和体验增强

等前两步稳定后，再继续：

- 页面契约前置
- 单页重设计
- 主工作台收口
- 智能一键修复

### 不建议的顺序

不建议继续这样做：

- 先不停堆 UI
- 再靠更多提示词补漏洞

因为那会让系统越来越像：

- 表面顺了
- 底层更乱

## 5. 建议的实际推进顺序

如果要马上进入下一轮开发，我建议按下面顺序推进：

### 第一批：必须马上做

1. `评分规则赛事优先化`
2. `confirmed material binding`
3. `唯一当前态聚合层`

### 第二批：最影响输出质量

5. `页面契约体系`

7. `视觉焦点和证据位前置`
8. `单页重设计替代反复 repair`

### 第三批：最影响用户体验

9. `task session 主流程模型`
10. `预览页彻底成为主工作台`
11. `下载条件卡继续代办化`
12. `高级视图进一步后置`

### 第四批：中长期能力

13. `智能一键修复并达标`
14. `LLM 错误契约统一`
15. `前后端流程状态模型继续拆分`

## 6. 最终结论

这次多角色联合评审的真正结论，不是“系统还有很多问题”，而是：

> **OREP 这条 AI 生成 PPT 式 HTML 功能，方向已经做对了，甚至已经走到了一个比普通生成器更高级的位置；但它下一阶段要解决的，不再是“会不会生成”，而是“能不能稳定地、按比赛规则、以较低用户成本，产出可交付的路演级结果”。**

所以接下来真正最该做的，不是继续拼更多局部修补，而是：

1. 先把比赛规则和页面契约前置  
2. 再把后端当前态和绑定口径收口  
3. 最后把前端主路径继续压成“当前页完成流”  

只有这样，系统才会从：

- “强大的 AI 工作台”

真正进化成：

- “稳定的比赛级内容生产系统”
