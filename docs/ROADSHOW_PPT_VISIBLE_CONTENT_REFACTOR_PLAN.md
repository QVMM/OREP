# 职业院校技能大赛路演 PPT 参赛级生成修复方案

版本：V1  
目标：先确认方案，不直接开发  
适用范围：`/ppt-editor` 路演 PPT 分支，不影响论文 PPT 分支

## 一、问题定义

当前 `b576154999f8` 已能生成完整 38 页路演 PPT，并且视觉上已经具备架构图、数据流、实操看板、证据链、仪表盘等主视觉。但它仍不能作为参赛级 PPT，核心原因不是页面画不出来，而是 **PPT 可见内容混入了大量后台策划语和系统控制语**。

典型问题：

- 显示“评分要素、评分维度、展示映射”等采分逻辑。
- 显示“操作角色B、记录角色C、关键节点口令、成功信号”等现场调度语。
- 显示“正式导出门禁、测试草稿版、待补充来源”等系统内部质量控制语。
- 显示“模拟测试数据、模拟日志、模拟编号、占位团队”等不适合正式参赛展示的信息。
- 章节逻辑更像“功能演示 runbook”，而不是“项目背景 -> 研发历程 -> 实施过程 -> 创新设计 -> 应用价值”的参赛作品汇报。

因此，本次修复目标不是继续换模板，而是建立 **参赛可见内容合同**：明确哪些内容能给评委看，哪些只能给选手看，哪些只能给系统内部使用。

## 二、修复目标

### 1. 生成内容分层

将 roadshow 生成内容拆成三层：

| 层级 | 用途 | 是否进入 PPT 可见正文 |
|---|---|---|
| `visible_slide_content` | 给评委看的页面标题、结论、图表标签、证据摘要 | 是 |
| `speaker_notes` | 给选手看的讲稿、提示、页内讲解重点、操作提醒 | 否，进入备注或编辑器侧栏 |
| `private_runbook` | 给系统用的评分映射、口令、门禁、故障预案、内部字段合同 | 否，仅后台使用 |

### 2. 可见 PPT 像真实参赛作品

最终 PPT 应该像参赛团队自己做的作品汇报，而不是 AI 生成系统的规划文档。

页面应呈现：

- 项目为什么做。
- 调研发现了什么问题。
- 团队如何研发。
- 技术方案如何落地。
- 现场能演示什么。
- 结果如何证明。
- 创新和应用价值在哪里。

页面不应呈现：

- 我们如何拿分。
- 哪一页对应哪个评分点。
- 讲解者该给操作者发什么口令。
- 这个 PPT 是否能正式导出。
- 数据是否“待补充”。
- 哪些字段是给 Agent 用的。

### 3. 证据不足时不伪装成果

如果用户资料没有真实截图、真实日志、真实测试报告、真实设备照片和真实成果数据，系统不能生成“正式成果页”口吻。

应改为：

- 生成“测试方法 / 验收口径 / 待采集证据清单”。
- 明确该任务为“样稿/草稿”。
- 禁止生成漂亮但无来源的 KPI 数字。

## 三、整体技术路线

本方案采用“前半段内容治理 + 后半段视觉执行不大改”的路线。

保留现有能力：

- paper-ppt-agent 的逐页 SVG 生成机制。
- Strategist / SVG Executor / Critic / Preview / Export。
- roadshow 分支已有的 `primary_visual` 主视觉合同。
- 视觉审查和正式导出门禁。

重点修改：

- roadshow agent 的前半段提示词和中间数据结构。
- manuscript 到 SVG executor 之间的内容清洗。
- export gate 前置为 evidence gate。
- 用户前端展示“草稿/正式可导出”的原因。

## 四、核心设计

### 1. 新增 RoadshowContentContract

在 roadshow manuscript 阶段，要求模型不再直接输出一整段可渲染文本，而是输出结构化内容合同。

建议结构：

```yaml
slide_id: 14
page_type: content
section: 实施过程
page_title: 设备接入与数据解析演示
visible_slide_content:
  claim: 完成环境数据从采集到可追溯记录的闭环
  main_points:
    - 输入原始环境数据帧
    - 解析为温度、湿度、烟雾、PM2.5等标准读数
    - 生成事件编号并写入日志
  evidence_summary:
    - 设备连接截图
    - 原始数据帧日志
    - 解析结果记录
visual_contract:
  primary_visual_type: live_demo_board
  required_elements:
    - 输入数据
    - 处理流程
    - 输出状态
    - 证据摘要
  forbidden_layouts:
    - 纯四卡片
    - 角色口令表
speaker_notes:
  talk_goal: 说明本页证明数据可采集、可解析、可追溯
  suggested_script: 这里由主讲介绍输入数据帧，再切到系统看板
private_runbook:
  judge_focus: 技能水平-数据解析能力
  operator_action: 操作员提交数据帧
  command_cue: 主讲提示操作员开始演示
  fallback_plan: 若设备不可用，切换离线回放数据
evidence_gate:
  status: draft
  missing:
    - 真实设备连接截图
    - 真实日志导出文件
```

SVG Executor 只能读取：

- `page_title`
- `visible_slide_content`
- `visual_contract`

不得读取：

- `private_runbook`
- `judge_focus`
- `command_cue`
- `fallback_plan`
- `operator_action`

### 2. 新增台面安全词过滤器

在 SVG 生成前和生成后各做一次文本扫描。

#### 禁止进入可见 PPT 的词

评分类：

- 评分要素
- 评分点
- 评分维度
- 得分点
- 采分点
- 展示映射
- 评分支撑

系统字段类：

- page_role
- judge_focus
- visual_strategy
- layout_hint
- primary_visual
- command_cue
- acceptance_signal
- fallback_plan
- display_target

现场调度类：

- 操作角色A
- 操作角色B
- 记录角色C
- 应急角色D
- 保障角色
- 关键节点口令
- 口令交接
- 成功信号

门禁/草稿类：

- 正式导出门禁
- 测试草稿版
- 草稿态
- 待补充
- 来源待补充
- 未核验数据
- 模拟截图
- 模拟日志

占位类：

- XX职业院校
- XX代表队
- [学校]
- [团队名称]
- [联系方式]

处理策略：

- 如果这些词出现在 `private_runbook` 或 `speaker_notes`，允许。
- 如果出现在 `visible_slide_content`，生成前必须改写。
- 如果出现在 SVG 文本中，生成后必须自动要求修复。
- 修复 3 次仍失败，则该页标记为“不可正式使用”，但不影响其他页缓存。

### 3. 新增源资料分层识别

当前用户上传的 PDF 可能是三类：

| 类型 | 特征 | 生成策略 |
|---|---|---|
| 正式项目资料 | 有真实截图、日志、测试报告、设备照片、真实数据 | 可生成正式参赛稿 |
| 半成品资料 | 有部分真实资料，但缺测试/证据/成果 | 生成草稿，缺口页显示“验证方法/采集清单” |
| Agent 母稿 | 包含 `PPT Agent`、`生成母稿`、`primary_visual`、`command_cue`、`模拟测试数据` 等 | 只提取项目事实，不把内部指令写入 PPT |

新增识别逻辑：

```text
如果资料中出现以下任意 3 类信号，判定为 Agent 母稿：
- PPT Agent / 生成母稿 / 生成能力测试
- primary_visual / page_role / command_cue
- 正式导出门禁 / 测试草稿版
- 模拟测试数据 / 待补充来源 / 未核验证据
- 讲解角色A / 操作角色B / 记录角色C
```

识别为 Agent 母稿后，源文档拆成：

- `project_facts`：项目名称、场景、技术方案、模块、真实可用信息。
- `internal_generation_rules`：给 Agent 的规则，不进入 PPT。
- `evidence_claims`：证据与数据，按真实/模拟/待补充分类。
- `speaker_support`：可转成备注的讲解建议。

### 4. 改造路演大纲

默认 38 页结构改为更符合真实比赛逻辑。

| 板块 | 页数建议 | 内容 |
|---|---:|---|
| 封面与目录 | 2 | 项目名称、汇报结构 |
| 项目背景 | 5-6 | 时事/政策、行业痛点、调研发现、研发动因 |
| 研发历程 | 7-8 | 产教融合、调研提炼、问题策略、技术架构、安全规范、研发分工 |
| 实施过程 | 12-14 | 产品设计、前端实现、后端处理、测试工程、现场实操闭环 |
| 创新设计 | 5-6 | 技术创新、模式创新、量化成效、可持续改进 |
| 应用价值 | 5-6 | 企业价值、教学价值、团队成长、知识产权 |
| 结尾 | 1 | 总结与致谢 |

重点变化：

- 不再把 12-27 页全部做成功能模块 runbook。
- 现场实操只保留关键 5-7 页，嵌入“实施过程”。
- 团队分工从“口令交接表”改成“岗位协作与交付物”。
- 评分映射页取消，改成“能力闭环与证据支撑”或直接融入各章节。

### 5. 成果页证据门禁前置

在生成成果页前先做 evidence gate：

```yaml
metric:
  name: 预警响应时间
  value: 2.1s
  source_type: simulated | verified | missing
  evidence_id: EV-201
  source_file: 系统测试报告.pdf
  can_show_as_result: false
```

规则：

- `verified`：可以作为成果展示。
- `simulated`：只能用于样稿或测试页，不可作为正式成果。
- `missing`：不能显示具体数值，只显示“待实测”或“验收指标”。

正式参赛稿中禁止出现：

- 来源待补充
- 模拟测试数据
- 待补充
- 漂亮但无来源的百分比、时长、金额、数量

### 6. 前端状态提示

用户前端需要明确区分：

- `样稿生成成功`
- `草稿生成成功，缺证据，不能正式导出`
- `正式稿生成成功，可导出`

任务结果区展示：

```text
当前版本：草稿版
原因：缺少真实设备截图、真实测试报告、真实日志导出文件
可操作：
1. 上传缺失证据
2. 继续编辑草稿
3. 仅导出草稿 PPTX
```

不再简单显示“生成失败”，因为 38 页已经生成成功，只是正式导出被拦截。

## 五、开发步骤

### 阶段 1：方案落地前的结构准备

目标：不改变生成效果，只先建立代码结构。

任务：

1. 新增 `roadshow_content_contract.py`。
2. 定义 `RoadshowSlideContract`、`VisibleSlideContent`、`VisualContract`、`SpeakerNotes`、`PrivateRunbook`、`EvidenceGate`。
3. 给旧 manuscript 增加兼容转换函数。

验收：

- 原有 roadshow 任务仍能跑。
- 论文 PPT 分支不受影响。

### 阶段 2：源资料分层识别

目标：识别 Agent 母稿、正式资料、半成品资料。

任务：

1. 新增 `classify_roadshow_source()`。
2. 增加 Agent 母稿特征检测。
3. 在 debug 输出 `source_classification.json`。
4. 将源资料拆为 `project_facts`、`internal_rules`、`evidence_claims`、`speaker_support`。

验收：

- 上传 `GPT55_职业院校技能大赛路演PPT生成母稿_智能温室项目.pdf` 时，应识别为 `agent_seed_draft`。
- `command_cue`、`primary_visual`、`正式导出门禁` 等内容不能直接进入可见正文。

### 阶段 3：重写 roadshow manuscript prompt

目标：让模型输出内容合同，而不是混合文本。

任务：

1. 修改 `MANUSCRIPT_SYSTEM_PROMPT`。
2. 取消“每页必须包含现场执行字段进入页面文本”的要求。
3. 改为每页必须包含 `visible_slide_content`、`visual_contract`、`speaker_notes`、`private_runbook`。
4. 增加“可见内容不得出现评分/口令/门禁/待补充”的硬约束。

验收：

- manuscript 中仍保留内部字段，但 SVG 输入只使用 visible 层。
- 第 3 页不再叫“评分要素与展示映射”。
- 第 33 页不再叫“口令交接”。

### 阶段 4：SVG Executor 输入隔离

目标：Executor 只能看到可展示内容。

任务：

1. 在送入 `svg_executor.py` 前提取 `visible_slide_content`。
2. `private_runbook` 不进入 executor prompt。
3. `speaker_notes` 不进入 executor prompt，只保存到 notes。
4. 增加生成后 SVG 文本扫描。

验收：

- SVG 文本中不出现 `操作角色B`、`评分要素`、`导出门禁`、`待补充来源`。
- 如果出现，自动进入页面修复。

### 阶段 5：证据门禁前置

目标：不要等导出时才发现不能用。

任务：

1. 在 research 阶段生成 `evidence_gate.json`。
2. 成果页生成前读取 evidence gate。
3. 缺真实证据时，成果页改为“测试方法/验收设计/证据采集计划”。
4. 前端显示当前任务是样稿、草稿还是正式稿。

验收：

- 只有模拟数据时，不生成正式 KPI 成果页。
- 任务状态不再误报“生成失败”，而是“草稿生成完成，正式导出受限”。

### 阶段 6：按比赛逻辑重构默认大纲

目标：让 PPT 更接近用户给的逻辑图。

任务：

1. 修改 outline agent 默认结构。
2. 将五大板块调整为：项目背景、研发历程、实施过程、创新设计、应用价值。
3. 保留官方常见板块名称时，在内部映射，不直接牺牲用户提供的比赛逻辑。
4. 实操页嵌入实施过程，不再连续做成 runbook。

验收：

- 新生成 PPT 能明显覆盖参考图的五大分支。
- 现场实操页不超过关键 5-7 页。
- 团队分工页体现岗位交付物，不体现口令交接表。

## 六、验收标准

### 内容验收

生成结果必须满足：

- 没有姓名、学校、电话、邮箱等隐私信息。
- 没有 `XX职业院校`、`XX代表队` 等占位符。
- 没有“评分要素/采分点/得分点”等台面不自然语言。
- 没有“操作角色B/记录角色C/口令/成功信号”等内部调度语言。
- 没有“导出门禁/测试草稿版/待补充来源”等系统内部语言。
- 没有无来源的 KPI 数字。

### 结构验收

生成结果必须覆盖：

- 项目背景。
- 研发历程。
- 实施过程。
- 创新设计。
- 应用价值。
- 现场实操闭环。
- 团队岗位协作。
- 证据与成果来源。

### 视觉验收

生成结果必须满足：

- 每页有一个清晰主视觉。
- 技术页不是纯卡片。
- 实操页像操作看板，不像说明书。
- 成果页是证据驱动，不是空泛 KPI 卡片。
- 缩略图总览能看出章节节奏变化。

### 系统验收

系统必须满足：

- 论文 PPT 分支不受影响。
- 旧 roadshow 任务历史可打开。
- 单页重新生成仍可用。
- 生成中断后已有页面缓存不丢。
- 正式导出门禁仍保留，但前端显示更准确。

## 七、风险与取舍

### 风险 1：内容合同会增加模型输出复杂度

解决：

- 先兼容旧 manuscript。
- 快速验证使用 8 页/15 页。
- 正式 38 页再启用完整结构。

### 风险 2：可见内容过滤过严，可能误删正常词

解决：

- 禁词分级：block / warn / allow_in_notes。
- 首版只 block 明确内部词。
- 保存命中报告，方便调参。

### 风险 3：用户确实想在 PPT 中展示团队分工

解决：

- 可以展示“岗位协作与交付物”。
- 不展示“口令交接与角色调度”。
- 例如：产品设计、前端实现、后端处理、测试验证、现场保障。

### 风险 4：资料不足导致页面看起来不够“成果化”

解决：

- 这是正确行为。
- 缺证据时生成“验收设计/测试方法/证据清单”，不要编造成果。
- 前端引导用户补充截图、日志、报告、设备照片。

## 八、建议执行顺序

建议先做 P0-P2，不急着全量重构：

1. 先做台面安全词过滤和 visible/private 分层。
2. 再做 Agent 母稿识别。
3. 再重写 manuscript prompt。
4. 用 `GPT55_职业院校技能大赛路演PPT生成母稿_智能温室项目.pdf` 重新跑 8 页验证。
5. 验证无内部词后，再跑 15 页。
6. 最后跑 38 页完整稿。

这样能快速验证方向是否正确，避免又生成一整套才发现基础逻辑错了。

## 九、本方案完成后的预期变化

当前问题页会这样变化：

| 当前页面 | 修复后 |
|---|---|
| 评分要素与展示内容映射 | 项目能力闭环与证据支撑 |
| 目录与 55 分钟路演路线图 | 汇报结构与项目主线 |
| 操作角色B现场演示 | 环境数据接入演示 |
| 记录角色C确认成功信号 | 日志与状态变化证明 |
| 正式导出门禁说明 | 证据链完整性说明，门禁逻辑仅后台保留 |
| 模拟测试数据来源待补充 | 测试方法与待采集证据，或真实成果数据 |
| 口令交接表 | 岗位协作与研发交付物 |

最终目标是让生成的 PPT 看起来像：

> 一个参赛团队围绕真实项目做出的作品汇报。

而不是：

> 一个 AI 系统根据评分表和内部 runbook 生成的比赛材料。
