## 0. 执行摘要与版本定位

### 0.1 为什么需要 2.0

| 层级 | 1.0 方案在说什么 | 局限 |
|------|------------------|------|
| 工程 / 体验 | 证据可点、双引擎收敛、待办闭环、对比 | **正确，但是「及格线」**；民用 Agent 1–2 年可仿观感 |
| 战略 | — | 缺「像 AI 评审团那样」**抽象、可传播、制度性** 的招牌 |

2.0 的合并原则：

```text
招牌（评价议会）  = 用户为什么记得你、为什么觉得 Agent 替不了
地板（证据·账本·闭环）= 议会不沦为话剧、报告不沦为散文
组织（教师·后果·常模）= 学校/营为什么不得不买
```

### 0.2 一句话目标

> **把 AI 评分从「一次生成报告」升级为「评价议会」：有席位、有程序、有证据、有终裁、有承诺、有后果；并在 1–2 年内形成通用 Agent 难以替代的制度与现场能力。**

### 0.3 双层交付物

| 类型 | 内容 | 用户感知 |
|------|------|----------|
| **α 招牌** | 开庭仪式、主审/规则/质疑席、决议书 UI、合议时间线 | 「这不是 ChatGPT」 |
| **β 地板** | 锚点可跳秒、权威字段统一、ledger/任务可信 | 「能信、能点、能跟」 |
| **γ 壁垒** | 教师终裁审计、承诺续审、后果编排、营期分位、现场庭 | 「班/营必须用系统」 |

### 0.4 总周期（结论先看）

| 方案包 | 周期 | 说明 |
|--------|------|------|
| **MVP 2.0（α+关键 β）** | **14–18 周**（约 3.5–4.5 个月） | 议会最小闭环 + 证据跳转 + 权威统一 + 基础后果/承诺 |
| **标准 2.0** | **MVP + 10–14 周**（合计约 **6–8 个月**） | 对比主路径、训练对接、共评、锁分 |
| **完整 2.0（含现场与常模）** | **再 +1–2 季度**（合计约 **9–14 个月**） | 现场庭、抽检治理、常模网络 |

以下周期按 **1 名产品 + 1 前端 + 1 Java + 1 Python/AI + 0.5 测试/兼设计** 的「小而全」编制估算；加人可并行压缩日历时间，但 **α 仍建议先串行做透招牌**。

## 1. 现状基线（1.0 能力与结构）

> 详细代码级说明见 v1.0；此处只保留 2.0 决策所需基线。

### 1.1 架构

```text
学生/教师前端                Java /api/ai-score/*              ai-scoring :8090
上传 + 报告四 Tab    ←→    Session / 回调 / 报告落库    ←→   score-session 流水线
                           权限 · 媒体 · remediation          ASR·视觉·LLM·规则·jury
```

### 1.2 主链路（上传）

1. `POST /upload-session` → 建 `AiScoringSession` + 绑赛道量表  
2. `AiScoringPipelineClient` → `POST /api/ai/score-session`（**`publishOfficialScore=false`**）  
3. Python：`run_session_pipeline` → 进度回调 → `finalResult`  
4. Java：`processPipelineCallback` → `ai_score_report` + 锚点 + v3 任务  
5. 前端：轮询 status → `GET reports/by-session/{id}` → result / todos / why / jury / compare  

### 1.3 已有「可升级资产」（2.0 必须复用，禁止推倒）

| 资产 | 位置 | 2.0 用法 |
|------|------|----------|
| Session + 回调契约 | Java / Python | 升级为 **EvaluationEvent / 呈堂庭** |
| loss ledger + remediation v3 | report JSON + 表 | 议会 **动议/后果** 的数据源 |
| evidenceAnchors | 回调 + `ai_score_evidence_anchor` | **质疑席弹药** + 跳秒 |
| AI 评审团 | jury 表 + `AiScoreReportJury.vue` | 升级为 **议会 AI 席团 / 质疑席** |
| 赛道 ruleVersion/hash | track_rubric_config | **规则席** 只读绑定 |
| 说话人归因 | media_evidence + DB | 庭审多方发言 |
| 待办 Tab + PATCH 状态 | 前端 + remediation API | **承诺/后果** 的第一落点 |

### 1.4 现状结构性问题（2.0 必须消解）

1. 叙事与 UI 仍是「报告阅读器」，特色（评审团）是旁路 Tab  
2. 证据锚点与视频秒级绑定不硬 → 跳转体验不稳  
3. 双引擎（Python ledger / Java p8-c / 遗留 meeting）真相源不清  
4. 闭环断在「整场再上传」，缺续审与承诺  
5. 诊断分 vs 官方分话术与代码不一致  
6. 后果几乎不改系统状态（训练/权限）

## 2. 2.0 目标与产品定义

### 2.1 产品名与定位

| 项 | 定义 |
|----|------|
| 对内代号 | **AI Score 2.0 / Chamber** |
| 对外主叙事 | **评价议会（Evaluation Chamber）** |
| 一句话 | 路演进入有席位、有程序、有冻结、有后果的评价议会；不是丢给 AI 写评语 |
| 收编关系 | **AI 评审团 → 议会内 AI 席**；主报告 → **决议书** |

### 2.2 分层架构（2.0）

```text
L4 组织     权限 · 锁分 · 抽检 · 导出 · 常模
L3 闭环     承诺 · 续审 · 后果编排 · 训练对接
L2 账本     Loss · 锚点 · 权威 · 对比轨迹
L1 感知     ASR/视觉/说话人（可换模型）——不宣传为壁垒
L0 程序★   席位 · 开庭 · 质疑 · 合议时间线 · 决议书   ← 2.0 新增招牌层
```

\*L0 是 2.0 相对 1.0 的**产品灵魂层**；L2–L3 是 1.0 工程方案升级后的地板。

### 2.3 三种开庭模式

| 模式 | 场景 | 2.0 阶段 |
|------|------|----------|
| **B 呈堂庭** | 现行上传视频 | **MVP 主路径** |
| **C 续审庭** | 只审承诺与弱项 | 标准 2.0 |
| **A 现场庭** | 实时会议在场 | 完整 2.0 |

### 2.4 默认席位（MVP 最小集）

| 席位 | 职责 | 数据从哪来 |
|------|------|------------|
| 书记席 | 冻结 session、版本、时间线 | 系统 |
| 规则席 | 只引用量表条款与 ruleHash | track_rubric + 规则结果 |
| 主审席 | 维度分、草案、置信度 | 主流水线 finalResult |
| 质疑席 | 专攻无证据/过度推断/张冠李戴 | **新建挑战生成** + 锚点校验 |
| 教师席 | 采信/驳回/改判（可配置必经） | 新 API + 审计 |
| （可选）评审团扩展席 | 多 Persona 意见 | 现有 jury，**并入时间线**而非孤立 Tab |

### 2.5 非目标（2.0 明确不做）

- 与 GPT 比散文评语  
- 推倒重写整条 ASR/视觉流水线  
- 一次做满 42 赛道同等深度（按赛道优先级）  
- 用「更多模型」当对外壁垒话术

## 3. 核心技术难点

> 按「难度 × 对壁垒的必要性」排序。难点分 **产品契约 / 数据与一致性 / AI 生成可控 / 前端体验 / 组织与权限 / 性能运维**。

### 3.1 难点一：评价对象模型升级（Session → 议会事件）

| 项 | 说明 |
|----|------|
| **难在哪** | 现有 `AiScoringSession` + `ai_score_report` 是「任务+结果」模型，缺 **程序状态机**（开庭中/合议中/待教师/已冻结/续审中）、缺 **动议/质疑/终裁** 一等公民表结构 |
| **若做不好** | UI 只是皮肤，Agent 仍可说「我也能模拟流程」 |
| **技术要点** | 兼容扩展：不砍 Session id；增加 `evaluation_event` 视图或并列表；callback 完成后进入 `deliberation` 子阶段而非直接 `completed` 终态（或 `completed` 细分为 draft/challenged/judged） |
| **涉及** | Java 实体/状态机、回调处理、前端路由与轮询语义 |

### 3.2 难点二：质疑席的「有效攻击」而非表演

| 项 | 说明 |
|----|------|
| **难在哪** | 简单 Prompt「你唱反调」→ 胡搅蛮缠或重复主审；要 **可验证的攻击**（指出无锚点维度、时间错配、条款不匹配） |
| **若做不好** | 质疑有效率≈0 或≈100，用户认为是玩具 |
| **技术要点** | 规则优先：扫描「有分无 valid 锚点」「锚点时间越界」「loss 无 acceptance」；LLM 只生成攻击叙述，**不得发明时间戳**；每条 challenge 必须挂 `targetDimension/lossId/anchorIds` |
| **涉及** | Python 新模块 `challenge_service`；与 `evidence_extraction` / ledger 对齐；Java 持久化 challenges |

### 3.3 难点三：证据锚点与媒体时间轴硬绑定

| 项 | 说明 |
|----|------|
| **难在哪** | 锚点常有文本无可靠 `startMs`；与 `transcript_segment` / `frame` FK 为空；前端跳转失败即「伪证据」 |
| **若做不好** | 议会与账本全部失去信任 |
| **技术要点** | 契约校验：invalid 锚点不得支撑决断分；抽检集；播放器统一 `seek(ms)` API；回调后回填 segmentId 的对齐算法（字幕 force-align / 最近句） |
| **涉及** | `persistEvidenceAnchors`、转写表、Why/Result UI、评测集 |

### 3.4 难点四：单一评分真相源（权威 Authority）

| 项 | 说明 |
|----|------|
| **难在哪** | Python diagnostic_rule_engine / legacy_llm / Java p8-c / 前端补拉 `/api/ai/result` 多源并存 |
| **若做不好** | 议会决议与 Tab 数字不一致，致命 |
| **技术要点** | 冻结字段：`scoreAuthority`、`contractVersion`、`publishOfficial`；前端 **禁止** 用遗留接口覆盖权威总分；Java structured-result 标 deprecated 或仅内部 |
| **涉及** | `AiScoringPipelineClient`、`useAiScoreReport.js`、报告 DTO |

### 3.5 难点五：合议时间线与异步任务编排

| 项 | 说明 |
|----|------|
| **难在哪** | 主流水线已很长；再串质疑席/评审团易超时、进度语义混乱 |
| **若做不好** | 用户以为卡死；或跳过质疑直接出分，招牌丢失 |
| **技术要点** | 阶段机：`sensing → draft_judgment → challenge → (optional jury) → await_teacher? → frozen`；质疑可与 jury **并行**；进度回调扩展 `currentStage` 枚举；超时降级策略写死 |
| **涉及** | `session_pipeline_service`、progress JSON、前端处理中态 UI |

### 3.6 难点六：后果图接入现有业务状态机

| 项 | 说明 |
|----|------|
| **难在哪** | 训练日解锁、任务系统、权限字段分散；错误触发会锁死学生路径 |
| **若做不好** | 要么空转（只有文案任务），要么误伤（错误锁权限） |
| **技术要点** | 后果 **声明式配置**（规则：维度&lt;阈值 → 动作类型+参数）；先做 **站内必做任务**（低耦合），再深链训练模块；所有后果可回滚、可审计 |
| **涉及** | remediation、训练 API、可选 feature flag |

### 3.7 难点七：教师终裁与审计的产品×权限

| 项 | 说明 |
|----|------|
| **难在哪** | 谁可改、改后学生是否可见、锁分后如何申诉；多租户角色 |
| **若做不好** | ToB 不敢用；或变成教师重填分的表格 |
| **技术要点** | 操作类型枚举：ACCEPT_CHALLENGE / REJECT_CHALLENGE / OVERRIDE_SCORE / DISMISS_LOSS；全量 audit log；乐观锁防并发 |
| **涉及** | 新 Controller、教师端审阅页或学生报告教师模式 |

### 3.8 难点八：纵向承诺与续审匹配

| 项 | 说明 |
|----|------|
| **难在哪** | 跨 Session 关联同一人/队/项目；弱项定义漂移；复评只重跑全场成本高 |
| **若做不好** | 「进步」无法自动判定，又退回散文 |
| **技术要点** | `commitment` 表挂 user+project+dimension；续审策略 v1：**整场再评 + 自动差分**（先不做局部重算）；差分算法基于维度分与 lossKey |
| **涉及** | remediation 跨次核验增强、Compare UI 首页化 |

### 3.9 难点九：现场庭（完整 2.0，非 MVP）

| 项 | 说明 |
|----|------|
| **难在哪** | 实时音视频、多端同步开庭状态、提问插入 docket、与 LiveKit 集成、失败恢复 |
| **技术要点** | 独立里程碑；复用会议基础设施；呈堂庭对象模型必须先稳 |
| **依赖** | LiveKit、信令、录制回调 |

### 3.10 难点十：常模与隐私

| 项 | 说明 |
|----|------|
| **难在哪** | 样本量不足时分位无意义；跨租户合规 |
| **技术要点** | 单租户营期分位 + 最小样本门闸（如 n≥20 才展示）；禁止早期跨校默认开启 |

### 3.11 难点优先级矩阵

| 难点 | 壁垒贡献 | 工程难度 | MVP 是否必须 |
|------|----------|----------|--------------|
| 3.1 对象/状态机 | 高 | 中高 | **是** |
| 3.2 质疑席有效性 | 极高 | 高 | **是** |
| 3.3 证据硬绑定 | 极高 | 高 | **是（核心路径）** |
| 3.4 权威统一 | 高 | 中 | **是** |
| 3.5 异步编排 | 中 | 中高 | **是** |
| 3.6 后果图 | 极高 | 中高 | **MVP 做轻量** |
| 3.7 教师终裁 | 极高 | 中 | 标准 2.0 |
| 3.8 承诺续审 | 极高 | 中 | 标准 2.0 |
| 3.9 现场庭 | 极高 | 极高 | 完整 2.0 |
| 3.10 常模 | 高 | 中 | 完整 2.0 |

## 4. 具体改什么、升级哪些部分、怎么做

### 4.1 总览：模块升级地图

```text
┌─────────────────────────────────────────────────────────────┐
│ 产品层：文案 · 开庭仪式 · 决议书信息架构 · 教师审阅入口      │
├──────────────┬──────────────┬──────────────┬────────────────┤
│ 前端 user    │ 前端 teacher │ Java API/DB  │ Python AI      │
│ 决议书UI     │ 上传/审阅    │ 状态机·审计  │ 质疑席·阶段    │
│ 时间线·跳秒  │ 队列         │ challenge表  │ 锚点质量       │
│ 承诺/对比    │              │ 后果执行器   │ 进度枚举       │
└──────────────┴──────────────┴──────────────┴────────────────┘
```

### 4.2 数据模型升级（建议）

**原则：扩展优先于推翻。**

| 对象 | 建议 | 说明 |
|------|------|------|
| `ai_scoring_session` | 增字段 | `chamber_phase`、`chamber_mode(present/live/continuance)`、`judgment_status`、`frozen_at` |
| `ai_score_chamber_challenge` | **新表** | id, session_id, target_type, target_ref, claim, evidence_anchor_ids, status(open/accepted/rejected), created_by(system/teacher) |
| `ai_score_chamber_event` | **新表** | 时间线事件：phase_enter、draft_ready、challenge_raised、teacher_action… |
| `ai_score_commitment` | **新表** | user/team/project、dimension、target_score、deadline、status |
| `ai_score_consequence_log` | **新表** | 触发的动作类型、参数、回滚信息 |
| `ai_score_judgment_audit` | **新表** | 教师操作审计 |
| `ai_score_report` | 增字段/JSON | `chamber_summary`（席位结论摘要）、保持 v3 ledger |

现有 jury 表：**保留**，通过 `chamber_event` 引用 jury_session_id，UI 并入时间线。

### 4.3 后端 Java：改什么

| 序号 | 改动项 | 怎么做 |
|------|--------|--------|
| J1 | 状态机 | 在 `AiScoringSessionService` 明确 phase 迁移；`completed` 前可经 `awaiting_judgment` |
| J2 | 回调扩展 | `processPipelineCallback` 识别 draft 完成 vs 全完成；接收 challenges[] |
| J3 | Challenge API | CRUD/列表；教师 accept/reject |
| J4 | Judgment API | override score / freeze；写 audit |
| J5 | 权威字段 | 报告 DTO 强制输出 authority、contractVersion、chamberPhase |
| J6 | 废弃策略 | 日志标记 legacy meeting callback；前端切断覆盖路径 |
| J7 | 后果执行器 | 接口 `ConsequenceDispatcher`：先实现 `CREATE_REMEDIATION_TASK`、`FLAG_TRAINING_TODO` |
| J8 | 对比 API | `GET .../sessions/{id}/compare?with=previous` 维度差分 + 承诺对照 |
| J9 | 权限 | 教师操作走租户+角色校验，复用 `AiScoreAccessControlService` 扩展 |

### 4.4 Python AI：改什么

| 序号 | 改动项 | 怎么做 |
|------|--------|--------|
| P1 | 流水线阶段 | `draft_judgment` 后插入 `challenge_generation`；进度枚举同步 Java/前端 |
| P2 | `challenge_service` | 规则扫描 + LLM 润色；输出严格 schema；禁止无依据时间 |
| P3 | 锚点质检 | 过滤 invalid；提升时间对齐；与 lossId 关联率监控 |
| P4 | finalResult 扩展 | `challenges`、`chamberDraft`、`proceedingsHints` |


## 7. 验收基准与门禁

### 7.1 分层

| 类型 | 用途 |
|------|------|
| **MVP 门禁** | 不达标不得全量宣传「评价议会」 |
| **标准 2.0 门禁** | 不达标不得开官方锁分 |
| **北向指标** | 季度看是否跑赢 Agent 心智 |

### 7.2 证据与质疑（MVP）

| 指标 | MVP | 标准 2.0 |
|------|-----|----------|
| 维度证据覆盖率 | ≥70% | ≥85% |
| 锚点可跳转率 | ≥90% | ≥95% |
| 无证据决断率 | ≤5% | ≤2% |
| 挑战 schema 合法率 | 100% | 100% |
| 质疑「可定位」率（挂 anchor 或明确 gap 类型） | ≥85% | ≥90% |

### 7.3 程序与后果（MVP）

| 指标 | MVP |
|------|-----|
| 走完 draft→challenge 阶段的 session 占比 | ≥80% |
| 后果触发率（至少建 1 任务或明确无任务原因） | ≥70% |
| 权威字段完整率 | 100% |
| 相对升级前耗时劣化 | ≤15% |

### 7.4 招牌感知（MVP）

| 指标 | 要求 |
|------|------|
| 30s 盲测 | ≥70% 受试说出席位/质疑/程序/决议之一 |
| 证据点击率 | ≥35% 访问产生至少一次跳转或证据点击 |

### 7.5 标准 2.0 增量

| 指标 | 要求 |
|------|------|
| 二次路演默认对比展示 | 有 prior 时 100% |
| 承诺创建率 | ≥50%（可配置引导） |
| 教师操作审计完整率 | 100% |
| 再评关联 prior losses | ≥95% |

### 7.6 北向（12 个月）

- 证据交互率 ≥40%  
- 30 日二次评分率较基线 +50%  
- 试点教师周活审阅达标  
- 访谈差异点含「议会/质疑/后果」≥70%

## 8. 风险、依赖与决策清单

### 8.1 风险

| 风险 | 缓解 |
|------|------|
| 质疑席变成吵闹表演 | 规则优先、有效率监控、上限 5 条 |
| 流水线过慢 | 快评模式关重视觉/重模型；质疑超时跳过 |
| 双引擎回潮 | 前端禁止双源；代码 owner 审查 |
| 后果误伤 | 默认轻量任务；权限类后果延后；可回滚 |
| 范围膨胀 | 现场/常模锁 Phase 6；MVP 冻结功能列表 |
| 金标不足 | Phase 0 强制 15 场再开工 |

### 8.2 依赖

- 共享存储路径 Java↔Python（`file-root`）稳定  
- 试点赛道量表 ruleHash 正确  
- 训练深链依赖训练 API 排期（可降级）  
- 现场庭依赖 LiveKit 稳定性  

### 8.3 立项前必须拍板的决策

| # | 决策 | 选项建议 |
|---|------|----------|
| D1 | MVP 是否强制教师终裁 | **默认否**，租户可开 |
| D2 | 正式锁分何时开 | **标准 2.0** |
| D3 | 试点 3 赛道 | 产品指定 |
| D4 | Jury 是否默认跑 | MVP **可选**；不阻塞质疑席 |
| D5 | 后果是否动训练解锁 | MVP **仅任务**；解锁放标准 |
