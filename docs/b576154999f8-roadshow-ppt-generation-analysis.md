## 一、总体结论

这次生成结果已经具备“路演 PPT 骨架”，但还不是参赛级 PPT。

主要问题不是 SVG 画不出来，也不是 MiMo 单次生成能力不足，而是前半段内容规划把大量“后台策划语、评分语、执行脚本语、质量门禁语”当成了可以进入幻灯片的正文。结果导致 PPT 看起来像 AI 为比赛生成的“作战手册”，而不是选手拿到现场自然汇报的参赛作品。

最核心的判断：

- 源 PDF 本身质量高，但它是“PPT Agent 母稿”，不是“台面展示材料”。
- 当前 roadshow agent 没有区分 `内部生成约束`、`演讲备注`、`PPT 可见文字`。
- 当前 prompt 过度强调评分映射、55 分钟 run-of-show、角色口令、导出门禁，导致这些内容被模型显性写到 PPT 上。
- 视觉上比早期版本强很多，已有架构图、数据流、现场看板、证据链、仪表盘等主视觉；但内容语气和信息选择仍不够像真实参赛队伍。
- 正式导出被拦截是正确的，因为源资料明确是模拟数据，PPT 中也存在大量模拟日志、待补充来源、示例编号。

## 四、为什么会生成这些内容

### 1. 源 PDF 是“Agent 母稿”，不是“参赛台面材料”

源 PDF 开头明确写了：

- 本文是给 PPT Agent 用的高质量生成母稿，不是参赛正式材料。
- 数据、截图编号、日志编号、成果数据均为模拟。
- 现场演示必须写清讲解角色、操作角色、操作动作、预期屏幕状态、成功信号、故障兜底和导出口令。
- 正式导出门禁必须作为内容的一部分。

这些内容对系统设计很有价值，但不能直接进入正式参赛 PPT。当前模型遵循了源 PDF 的强约束，因此把很多内部规则当成了页面内容。

### 2. roadshow_agent 的 prompt 强制生成现场执行字段

当前 `roadshow_agent.py` 要求每页必须有：

- `judge_focus`
- `stage_mode`
- `display_target`
- `speaker_role`
- `operator_role`
- `operator_action`
- `expected_screen_state`
- `fallback_plan`
- `acceptance_signal`
- `command_cue`

这些字段本来是好设计，但它们应该进入 `speaker_notes` 或 `private_runbook`，不是进入可见 PPT 正文。现在 manuscript 只有一种文本通道，导致执行器容易把字段值画出来。

### 3. SVG executor 只禁止“字段名”，没有禁止“字段值”

执行器目前提醒“不要把 page_role、judge_focus 等字段名逐字渲染”，但没有明确禁止显示字段值。例如字段名 `command_cue` 没有显示，但字段值“请操作角色B...”被画进了页面。

这说明当前约束粒度不够。真正要禁止的是一类台面不安全语汇，而不仅是字段名。

### 4. Review Agent 更关注“有没有字段”，不够关注“能不能上台”

当前 review 规则会检查是否缺少现场执行字段、是否缺少 55 分钟节奏、是否缺少团队匿名分工。它没有把“评分映射、口令交接、导出门禁、待补充来源、模拟日志”作为可见内容风险来强制修订。

这会让系统更倾向于生成“完整的内部策划稿”，而不是“干净的参赛展示稿”。

### 5. 证据门禁太靠后

正式导出门禁在最后拦截了 PPTX，这是对的。但用户已经看到了 38 页包含大量 `待补充`、模拟日志、模拟 KPI 的页面，体验上仍然会觉得“生成出来但不能用”。

证据不足应该在生成前就改变页面策略：

- 有证据：生成成果页、证据页、数据仪表盘。
- 证据不足：生成“测试方法/验收设计/待采集清单”，不要伪装成成果。
- 全部模拟：只能生成训练稿/样稿，不能按正式参赛口吻生成。

## 五、参赛级 PPT 应该如何改

### 1. 内容逻辑要回到参考图，而不是 runbook

建议正式路演 PPT 的主线改为：

1. 项目背景：政策/行业趋势/调研发现/研发动因。
2. 研发历程：调研痛点 -> 问题策略 -> 技术架构 -> 安全规范 -> 团队研发分工。
3. 实施过程：产品设计、前端实现、后端数据处理、测试验证、现场实操。
4. 创新设计：技术创新、模式创新、量化成效。
5. 应用价值：企业价值、教学价值、团队成长、知识产权。

现场实操仍然保留，但只作为“实施过程”中的关键证明，不应占据 12-27 页这么长的独立 runbook。

### 2. 页面可见文本要分级

必须把生成内容拆成三层：

- `visible_slide_content`：允许出现在 PPT 上的标题、结论、图表标签、证据摘要。
- `speaker_notes`：允许给选手看的讲稿，包括口令、角色分工、提醒。
- `private_runbook`：只给系统用，包括评分映射、门禁、字段合同、故障预案、重试策略。

SVG executor 只能读取 `visible_slide_content` 和 `visual_contract`，不能读取 `private_runbook`。

### 3. 增加“台面安全词”过滤

以下词语不应出现在正式参赛 PPT 的 SVG 文本中：

- 评分要素、评分点、采分点、得分点、评分维度、评分映射
- judge_focus、command_cue、page_role、primary_visual、layout_hint
- 操作角色A/B/C/D、记录角色、保障角色、应急角色
- 口令、关键节点口令、成功信号、acceptance_signal、fallback_plan
- 正式导出门禁、测试草稿版、待补充、来源待补充
- 模拟测试数据、模拟日志、模拟截图、未核验数据
- XX职业院校、XX代表队、2024-05-24 这类占位或可疑精确日期

这些词可以出现在后台日志、编辑器提示、演讲备注里，但不能作为 PPT 可见文字。

### 4. 成果页必须改为证据驱动

成果页的生成规则应改成：

- 没有真实证据时，不生成“98%、95%、2.1s”这类漂亮 KPI。
- 只允许展示“测试设计”和“待采集证据清单”。
- 真实数据必须绑定 `evidence_id + 来源文件 + 验证方法`。
- 如果数据来自联网材料，只能用于行业背景，不能写成用户项目成果。

### 5. 现场实操页要换表达方式

实操页可以保留操作闭环，但可见文案应像这样：

- 输入：环境数据帧 / 阈值参数 / 控制指令。
- 处理：解析、判定、联动、记录。
- 输出：看板状态变化 / 设备回执 / 报告生成。
- 证据：日志、截图、接口返回、测试表。

不应显示：

- 讲解角色A发出口令。
- 操作角色B点击按钮。
- 记录角色C确认。
- 应急角色D切换热点。

这些都放到备注或 runbook。

## 六、修复开发步骤

### P0：新增“台面内容净化层”

位置建议：

- `ai-scoring/app/services/ppt/agent/backend/orchestrator/roadshow_agent.py`
- `ai-scoring/app/services/ppt/agent/backend/orchestrator/roadshow_quality.py`
- `ai-scoring/app/services/ppt/agent/backend/orchestrator/svg_executor.py`

开发内容：

1. 在 roadshow manuscript 后新增 `sanitize_visible_manuscript()`。
2. 把 `stage_mode/display_target/speaker_role/operator_role/command_cue/fallback_plan` 移到 speaker notes 或 private runbook。
3. 将 `评分要素与展示映射` 改写为 `能力闭环与证据支撑`。
4. 将 `正式导出门禁说明` 改写为内部门禁，不进入可见 PPT。
5. 对 SVG 输出做文本扫描，命中禁词则自动进入修订，不允许直接进入 `svg_final`。

### P1：重构 roadshow prompt 的字段合同

当前问题是“每页必须包含现场执行字段”。应改为：

- 每页必须包含 `visual_contract`。
- 可见页只包含 `visible_title / visible_claim / visible_elements / evidence_summary`。
- 现场执行字段统一放入 `speaker_notes`。
- `judge_focus` 改成内部字段 `private_judge_focus`，不能给 executor 渲染。

同时把 review agent 的严重问题增加：

- 可见文本出现评分/采分语言。
- 可见文本出现角色口令。
- 可见文本出现导出门禁/草稿态。
- 可见文本出现待补充或模拟成果。
- 可见文本出现占位学校或占位团队。

### P2：按参考图重做比赛路演大纲

将默认 38 页结构从“功能模块 runbook”改成“比赛作品叙事”：

1. 封面与目录：2 页。
2. 项目背景：5-6 页，必须含政策/行业/调研/研发动因。
3. 研发历程：7-8 页，必须含调研痛点、策略、架构、安全规范、研发分工。
4. 实施过程：12-14 页，含产品、前端、后端、测试、实操。
5. 创新设计：5-6 页，含技术、模式、量化成效。
6. 应用价值：5-6 页，含企业、学校、团队、知识产权。
7. 结尾：1 页。

现场实操页不再连续占 14 页，而是嵌入实施过程，用 5-7 页展示最关键闭环。

### P3：证据先行，而不是生成后拦截

新增生成前证据分级：

- A 级：真实截图/日志/测试表/设备照片齐全，允许正式成果页。
- B 级：有部分真实资料，缺口页面显示“验证方法”而非成果数字。
- C 级：只有文字描述或模拟母稿，只生成演示样稿，不生成正式成果口吻。

对于 C 级资料，系统应明确提示用户：这是样稿，不是参赛正式稿；页面中不得出现真实成果数字。

### P4：对源 PDF 做“母稿识别”

如果上传资料包含以下特征，应自动识别为 Agent 母稿：

- `PPT Agent`
- `生成母稿`
- `必须遵守`
- `page_role`
- `primary_visual`
- `command_cue`
- `正式导出门禁`
- `模拟测试数据`

识别后分离为：

- `internal_instruction_sections`
- `project_fact_sections`
- `visible_candidate_sections`
- `evidence_sections`

只有 `visible_candidate_sections` 和 `project_fact_sections` 可以进入 PPT 正文。

## 七、优先级判断

最重要的不是继续优化视觉模板，而是先解决“台面可见内容污染”。

当前视觉已经能做出架构图、证据链、实操看板和仪表盘。真正让它不像参赛 PPT 的原因，是页面上出现了太多系统内部语言：

- 评分映射
- 采分式结构
- 操作角色口令
- 导出门禁
- 待补充来源
- 模拟日志和模拟 KPI

所以修复顺序应为：

1. 可见文本净化。
2. 源资料分层。
3. 大纲改为参考图的比赛叙事。
4. 证据分级与成果页门禁前置。
5. 再继续做视觉精修。

## 八、结论

`b576154999f8` 证明 roadshow 分支已经能生成完整 38 页、风格统一、有主视觉的 PPT，但还没有达到“参赛级”。

它失败的关键不是素材完全不行，而是源素材和系统提示词共同把“给 Agent 的内部控制信息”推到了幻灯片台面上。下一步要做的是建立严格的“参赛可见内容合同”：哪些能给评委看，哪些只能给选手看，哪些只能给系统看。

完成这一步后，再基于参考图重构大纲，才有机会从“AI 生成的比赛说明书”进化成“能带上赛场的作品汇报 PPT”。
