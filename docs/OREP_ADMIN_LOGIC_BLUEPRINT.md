# OREP 管理端逻辑蓝图

日期：2026-07-16  
状态：本轮只定义逻辑，不制作管理端页面

## 1. 管理端定位

管理端负责“平台如何被安全、稳定、可追溯地运行”，不替代教师完成项目指导，也不替代学生完成项目任务。

管理端与业务端的边界：

- 管理端配置组织、账号、角色、赛制、内容与评分规则。
- 教师端创建项目、指导团队、发布课程与测评、审核交付物、组织路演。
- 学生/队长端完成学习、项目、路演与整改。
- 管理员默认不能直接修改业务结果；涉及成绩、审核或证据的特殊操作必须留下原因和审计记录。

## 2. 管理域

### 2.1 租户与组织

- 创建、启用、停用学校或机构租户。
- 维护校区、学院、专业、班级、教研组等组织树。
- 设置学年、学期、时区、数据保留周期和品牌配置。
- 设置租户配额：账号数、项目数、存储、录制时长、AI 评分次数。
- 支持组织合并、拆分与历史归档，不覆盖已有业务署名。

### 2.2 账号与身份

- 账号来源：单点登录、校内导入、邀请注册、管理员创建。
- 身份与账号分离：一个账号可以同时拥有学生、教师或管理员身份。
- “队长”不是全局身份，而是账号在某个项目中的关系角色 `CAPTAIN`；同一学生可在一个项目中任队长、在另一个项目中任成员。
- 生命周期：待激活、正常、锁定、停用、离校/离职、归档。
- 组织变更不删除历史项目、成绩、审核与路演署名。
- 高风险操作需要二次验证；批量导入必须提供预检与回滚记录。

### 2.3 角色与权限

采用 RBAC 与数据范围相结合的模型：

`用户 → 角色 → 权限动作 → 资源 → 数据范围 → 条件`

数据范围：

- `SELF`：本人数据。
- `PROJECT`：当前项目。
- `CLASS`：指定班级。
- `ORG`：学院或组织节点及其下级。
- `TENANT`：整个学校/机构。
- `PLATFORM`：跨租户平台级。

条件示例：

- 队长只有在 `roleInTeam = CAPTAIN` 时可分配项目任务。
- 教师只有在项目导师、课程教师或考试负责人范围内可审核。
- 管理员若要代改业务状态，必须具备 `BREAK_GLASS` 权限，并填写原因。

业务接口返回有效权限快照：

`actingIdentity + projectRole + permissions + dataScope + authzRevision`

账号、角色或范围变化后递增 `authzRevision`。已有 Token、WebSocket 会议、上传和评分任务在下一次写操作时必须重新校验，避免存量会话继续使用旧权限。

### 2.4 竞赛与项目规则

- 维护比赛、赛道、组别、赛制、阶段模板和报名窗口。
- 配置项目人数、导师数量、材料要求、路演时长和阶段出口条件。
- 阶段模板只影响新项目；已开始项目通过版本化迁移更新。
- 项目归档后只读，恢复需要项目管理员或租户管理员批准。
- 赛制规则变更必须记录版本、生效时间和受影响项目。

### 2.5 课程、题库与测评治理

- 课程状态：草稿、待审核、已发布、已下架、已归档。
- 题目状态：草稿、已审核、已发布、停用；题干、答案和解析分别版本化。
- 支持课程分类、适用赛道、适用角色、先修条件和有效期。
- 正式考试发布后不可直接修改题目；必须复制为新版本。
- 成绩更正需要原分、改后分、原因、操作者、审批人和时间。

### 2.6 路演与录制治理

- 管理会议服务配置、最大并发、录制策略和存储周期。
- 支持敏感会议的禁止录制、自动录制和手动录制策略。
- 录制状态：处理中、可用、失败、已删除、已归档。
- 删除录制前检查是否被评分报告或证据引用。
- 被引用录制执行逻辑删除；报告仍可读取证据摘要和审计信息。

### 2.7 AI 评分治理

- 评分规则、维度、权重、提示词、模型与阈值组成一个不可变评分版本。
- 新版本先进入沙盒评测，通过基准集后才可灰度发布。
- 已生成报告永久关联当时的评分版本，不随新规则自动变化。
- 教师复核只能增加人工观察、证据有效性判断和校准意见，不覆盖 AI 原始输出。
- 评分事实分为三层：不可变的 `AiScoreReport`、追加式的 `TeacherReview/ManualScoreRecord`、经审批形成的 `OfficialResultVersion`。
- 业务端必须分别标识 AI 分、人工分和官方分，并由 `displayPolicy` 决定默认展示口径。
- 成绩更正申请人与审批人不得为同一主体。
- 重跑评分生成新轮次，旧报告保留，支持前后对比。
- 失败评分任务支持重试、取消、转人工和异常工单。

轮次比较需要可比较性契约：

- 报告公开 `scoringVersionId`、`rubricVersion`、`modelVersion`、`evidenceSchemaVersion` 和 `effectiveAt` 等安全版本字段。
- 重跑时明确选择“沿用原评分版本”或“使用当前版本”。
- 跨版本比较返回 `comparable = false` 与规则差异摘要，不能直接把分数变化解释为能力变化。
- 当规则或证据口径变化导致整改效果不可观察时，返回 `not_observable`，不自动宣称提分。

### 2.8 通知与运营配置

- 配置站内信、邮件、短信或企业消息渠道。
- 通知模板区分事务型、风险型、学习型和运营型。
- 用户可关闭非必要通知；审核、考试和安全通知不可完全关闭。
- 首页推荐位、课程推荐和公告都需要有效期、目标范围和发布审核。

### 2.9 审计、合规与数据治理

- 所有管理写操作及教师高风险业务动作记录：操作者、有效身份、资源、旧值/新值哈希、原因、时间、来源 IP/设备、工单和追踪号。
- 教师证据确认、人工评分、材料审核、整改验证和管理员 `BREAK_GLASS` 都进入同一审计链。
- 审计记录只追加、不覆盖，普通管理员不可删除。
- 导出、批量查看、权限提升、成绩更正、评分规则发布为高风险事件。
- 数据脱敏按角色执行；管理员也不默认获得完整敏感字段。
- 支持数据保留、冻结、归档、匿名化和法定删除流程。
- 保留优先级为：法律保全 `legal hold` → 法定删除要求 → 租户保留策略。
- 源录制删除后，仅保留可解释所需的最小脱敏证据快照：摘要、时间锚点、内容哈希、评分版本和不可逆匿名化结果。
- 证据接口返回 `sourceAvailability`、`redactionStatus` 与 `retentionPolicyId`，避免业务端打开已失效来源。

## 3. 管理角色

| 角色 | 主要职责 | 默认数据范围 | 不允许直接做的事 |
|---|---|---|---|
| 平台超级管理员 | 平台租户、基础设施与应急处理 | PLATFORM | 无理由修改成绩或项目审核结果 |
| 租户管理员 | 学校账号、组织、配额与品牌配置 | TENANT | 修改其他租户数据 |
| 组织管理员 | 学院/专业/班级与成员维护 | ORG | 发布平台级评分规则 |
| 竞赛管理员 | 比赛、赛道、阶段模板与项目归档 | TENANT/ORG | 代替教师审核普通交付物 |
| 内容管理员 | 课程、题库、资源与发布审核 | TENANT/ORG | 查看无关项目私密材料 |
| AI 评分管理员 | 评分版本、基准评测与灰度发布 | TENANT/PLATFORM | 覆盖历史报告结果 |
| 审计员 | 查看审计、导出审批与异常追踪 | TENANT/PLATFORM，只读 | 执行业务写操作 |
| 支持人员 | 处理账号、任务失败和服务工单 | 受工单限制 | 无工单查看用户业务数据 |

平台支持自定义角色，但不可移除系统保留的权限边界。

说明：原型中的“学生 / 队长 / 教师切换”仅用于快速演示不同上下文；正式产品只能切换账号已经被授予的身份与项目关系，不能自助提权。

## 5. 关键状态机

### 账号

`PENDING_ACTIVATION → ACTIVE → LOCKED / DISABLED → ACTIVE / ARCHIVED`

约束：

- 锁定用于安全风险，停用用于组织或权限变化。
- 归档前必须完成在途任务、考试和审核的责任转移。

### 课程与题目

`DRAFT → REVIEWING → PUBLISHED → OFFLINE → ARCHIVED`

退回路径：

`REVIEWING → CHANGES_REQUESTED → DRAFT`

### 评分规则

`DRAFT → BENCHMARKING → APPROVED → CANARY → ACTIVE → RETIRED`

约束：

- 同一租户、同一赛道、同一生效时间只能有一个 `ACTIVE` 版本。
- `RETIRED` 版本仍可解释历史报告。

### 管理导出

`REQUESTED → RISK_CHECK → APPROVED / REJECTED → GENERATED → EXPIRED`

高敏感导出必须双人审批，并设置短期下载有效期。

### 全域状态迁移约束

任务、提交、材料、考试尝试、会议、录制、AI 会话和整改也必须进入统一状态字典。每个资源都需要定义：

- canonical enum 与中文显示名。
- 允许操作者和数据范围。
- 前置条件与副作用。
- 终态、撤销或重开路径。
- 对应审计事件。

所有状态写接口携带 `resourceVersion` 或 `If-Match`，并支持 `Idempotency-Key`。版本冲突返回 `409 Conflict`，避免重复审核、重复交卷或重复生成评分版本。

## 6. 关键管理流程

### 6.1 新学校开通

1. 创建租户与组织根节点。
2. 配置身份源、时区、学年和数据保留策略。
3. 创建租户管理员。
4. 导入学院、班级、教师与学生。
5. 分配角色和数据范围。
6. 发布默认课程、赛制与评分版本。
7. 运行权限预检后开放业务端。

### 6.2 教师入职或调岗

1. 身份源同步账号状态。
2. 组织管理员分配教师身份与组织范围。
3. 转移原教师负责的项目、课程、考试和待审核事项。
4. 历史署名保持不变，新动作使用新负责人。
5. 记录权限变化审计。

### 6.3 评分规则发布

1. 创建规则草稿并绑定模型、权重和提示词版本。
2. 使用脱敏基准集评测一致性、偏差和失败率。
3. AI 评分管理员提交审批。
4. 先灰度到指定项目或组织。
5. 观察异常率和教师校准差异。
6. 达标后全量生效；异常时回滚到上一个活动版本。

### 6.4 成绩更正

1. 教师或管理员发起更正申请。
2. 系统保存原分与关联答卷。
3. 独立审批人核对原因和证据。
4. 通过后生成新成绩版本。
5. 学生收到更正说明；原成绩仅在审计中可见。

### 6.5 账号离校/离职

1. 冻结新业务操作。
2. 检查项目负责人、课程教师、考试负责人和审核队列。
3. 完成责任转移。
4. 按政策归档或匿名化个人数据。
5. 保留必要业务署名与审计关系。

## 7. 数据所有权

| 数据 | 业务所有者 | 管理责任 | 历史策略 |
|---|---|---|---|
| 项目、任务、材料 | 项目团队/学校 | 租户与竞赛管理员 | 项目归档后只读 |
| 课程、题库 | 创建组织/学校 | 内容管理员 | 发布版本永久保留 |
| 考试答卷与成绩 | 学校 | 测评负责人 | 更正生成新版本 |
| 会议与录制 | 学校/项目 | 路演策略管理员 | 按保留策略归档或逻辑删除 |
| AI 报告与证据 | 学校/项目 | AI 评分管理员 | 绑定评分版本长期可解释 |
| 审计日志 | 平台 | 审计员 | 只追加、按合规周期保留 |

## 8. 与用户端、教师端的接口约束

- 管理端停用账号后，业务端立即禁止新的写操作，但保留只读历史。
- 角色或数据范围变更后，业务端下一次请求重新计算权限。
- 课程、题目、赛制和评分规则都向业务端提供明确版本号。
- 管理端归档项目后，用户端和教师端进入只读模式。
- 评分规则更新不修改历史报告；用户端通过“评分版本”解释差异。
- 管理端配置的通知模板只提供内容骨架，业务端负责传入具体任务上下文。

## 9. 管理端未来页面优先级

### P0：平台可运营

- 租户与组织
- 账号与身份
- 角色、权限与数据范围
- 比赛、赛道与阶段模板
- 审计日志
- 系统健康与失败任务

### P1：内容与评分可治理

- 课程与题库审核
- 测评发布与成绩更正
- 评分规则版本与基准评测
- 录制策略与存储
- 通知模板

### P2：规模化运营

- 配额与计费
- 跨组织内容共享
- 运营推荐位
- 数据导出与报表中心
- 自动化风险策略

## 10. 管理端验收原则

- 普通配置操作不超过三层页面。
- 所有高风险操作明确显示影响范围。
- 批量操作先预检、后确认、可追踪。
- 权限配置能解释“谁、在什么范围、为什么能做什么”。
- 历史业务结果不可被静默覆盖。
- 管理员代操作必须有原因、审批和审计。
- 评分版本可回滚，历史报告可解释。
- 管理端故障不应阻断用户查看已生成的历史结果。
