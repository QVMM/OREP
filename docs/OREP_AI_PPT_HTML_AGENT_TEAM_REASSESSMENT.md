## 1. 联合评审结论

这次 team 的统一结论是：

**OREP 当前的 AI 生成 PPT 式 HTML 功能，已经明显超出“普通生成器”范畴，正在形成一套比赛导向的生成、质检、修复、交付系统。**

但它还存在 3 个层级的核心问题：

1. **最终成品层**
   - 还没有稳定做到“真正像比赛级 PPT”
   - 仍会产出“更稳定的普通 HTML 页”
   - 技术页、实操页、价值页最容易丢掉“PPT 感”“路演感”“比赛感”

2. **业务逻辑层**
   - 比赛评分标准、叙事节奏、实操观测点、团队协作、安全规范等，虽然已经进入系统，但还没有彻底成为唯一北极星
   - 底层仍残留商业 BP / 普通路演的语义惯性

3. **系统与体验层**
   - 后端已经长成复合系统，但状态源和读写边界仍复杂
   - 前端虽然可用了很多，但对普通用户来说仍然偏重、偏分析平台、偏“需要理解系统”

所以现在的准确定位应该是：

> 它已经是“比赛导向 AI 路演生成系统的雏形”，但还不是“真正稳定输出比赛级 PPT 页，并且让普通用户轻松完成交付”的成熟系统。

---

## 2. 统一问题分层

### A. 最终成品问题

1. 页面还会有明显的“HTML 味”
2. 技术架构、实操闭环、价值矩阵、创新页最容易模板化
3. 视觉焦点、页系语言、章节镜头感不够稳定
4. 证据页经常是“内容页加证据”，不是“证据主导页”

### B. 比赛逻辑问题

1. 底层评分覆盖仍有商业 BP 语义残留
2. 结构检查存在，但节奏控制还不够比赛原生
3. 实操页更像“说明页”，不够像“操作能力展示页”
4. 团队协作、安全规范、职业素养页容易变成补模块页，而不是评分服务页
5. 创新与应用价值容易泛化，缺少可打分的量化和证据

### C. 系统实现问题

1. 当前真相源仍然过多
2. 读接口带写副作用
3. 快照、当前页、评分覆盖、交付门禁边界不够纯
4. repair / fallback / rebuild / deliverability 仍然是多条并行环路，刚开始收口但还没完全统一
5. 页面契约虽已进入链路，但还需要更多 deterministic validator

### D. 用户体验问题

1. 用户在“生成完成后”仍要做很多事
2. 预览页虽然已收成主工作台，但依然偏重
3. 内部概念暴露仍然偏多
4. 下载链路已经大幅改善，但真实用户仍然需要系统更主动兜底
5. 等待体验虽有改善，但仍然不是“零焦虑”

## 3. 角色分工视角下的问题清单

## 3.1 产品经理视角

### 结论

当前功能不是弱，而是**太强但太重**。  
对第一次使用的人来说，它更像“比赛内容工作台”，而不是“生成后基本可用的智能工具”。

### 重点问题

1. 生成完成后，用户心理预期是“差不多可以用了”，但系统实际告诉用户“真正的工作现在才开始”
2. 预览页承担了太多责任：看页、补图、修页、看讲稿、看风险、看交付状态
3. 用户还在被迫理解太多系统语言：
   - deliverability
   - blocker
   - scoring coverage
   - template page risk
4. 下载流程虽然变好了，但本质仍然偏“条件解释系统”
5. 真正缺的不是更多按钮，而是“系统替用户多做一步”

### 产品经理建议

1. 把“生成后修整”明确包装成一个独立阶段
2. 继续压缩主路径，只留下“当前页推荐动作”
3. 强化“智能一键修复并达标”
4. 高级分析页继续降级，主流程不要要求用户理解系统

---

## 3.2 普通用户代表视角

### 结论

一个普通用户的真实感受会是：

- 功能很强
- 页面很多
- 系统很聪明
- 但经常不知道“我下一步最该做什么”

### 用户最痛的点

1. 生成后不敢轻易下载，因为系统会告诉他还有很多条件
2. 不知道补图以后到底有没有真绑定
3. 不知道修这一页到底有没有用
4. 不知道做到什么程度才算“可以交了”
5. 不知道系统是在帮我，还是在考我

### 用户代表建议

1. 所有复杂判断都尽量回收成“下一步推荐动作”
2. 素材补图、评分补强、页面修复，都尽量在当前页完成
3. 下载时系统要更像“我带你过关”，而不是“我把条件列给你”

---

## 3.3 赛事专家视角

### 结论

系统已经有明显的比赛意识，但**还不是完全比赛原生**。  
最大的风险不是缺页，而是底层评分逻辑、叙事重心、实操观测点表达还没有彻底统一到“评委怎么打分”上。

### 重点问题

1. 底层评分覆盖仍残留商业 BP 语义：
   - 市场规模
   - 竞争优势
   - 融资需求
   - 财务预测
2. 当前更擅长结构检查，不够擅长比赛节奏控制
3. 实操闭环存在，但容易生成流程说明页，而不是操作能力观测页
4. 团队协作、安全规范、职业素养页容易变成“表达态度”，而不是“展示可观测行为”
5. 创新与应用价值经常缺少量化、对比、试点证据

### 赛事专家建议

1. 技能大赛评分标准必须成为唯一主评分底座
2. 商业/市场语言只做补充，不再主导生成与评估
3. 章节需要时间配额和页数配额控制
4. 交付标准建议分为：
   - 可交付预演版
   - 比赛终稿版

---

## 3.4 路演专家视角

### 结论

故事线已经比之前健康很多，但仍然更像“结构正确的项目稿”，不总是“60 分钟比赛答辩脚本”。

### 重点问题

1. 系统能防止明显乱序，但不总能稳定保证“技术实操主导”
2. 背景、痛点、方案、实操、价值的节奏配比仍然会失衡
3. 后段容易堆价值、创新、团队、总结，造成“前松后挤”
4. 章节之间的承接感还不够导演式

### 路演专家建议

1. 把四幕式比赛叙事模板做成主线：
   - 建立问题与背景
   - 提出方案与技术骨架
   - 实操演示与技术突破
   - 价值、创新、团队、收束
2. 引入章节页数上限、实操页下限、关键技术页下限
3. 章节开场页和总结页必须有更强镜头感

---

## 3.5 PPT 专家视角

### 结论

现在的系统方向是对的，但很多页面还停留在：

> “像 PPT 的 HTML 页面”

而不是：

> “真正专业的比赛级 PPT 页面”

### 重点问题

1. 页面虽然统一成 16:9，但很多页仍像网页模块拼装
2. 风格样张更像“封面样张”，不是“页系样张”
3. 技术页、实操页、价值页最容易模板化
4. 视觉焦点不稳定
5. 页面信息密度经常均匀，但没有权重
6. 章节页、突破页、结果页、收束页缺少镜头感

### PPT 专家建议

1. 页面契约必须硬化
2. 页系样张必须覆盖一套风格的关键页，不只看封面
3. 技术页要有“图为王”的结构，不是文字卡堆叠
4. 价值页、证据页、总结页必须有强主视觉和收束感

---

## 3.6 编导专家视角

### 结论

系统现在的修复能力更像“问题修补”，还不够像“导演式重设计”。

### 重点问题

1. 页面逻辑是有了，但镜头感和讲述任务分配还不够强
2. 证据页经常是“加了图”，不是“图在说话”
3. 当前修复流擅长修错，不够擅长重建一个更会讲的页面
4. 章节承接页和情绪节点页仍然较弱

### 编导专家建议

1. 修页要从“修 HTML”升级成“重设计页面”
2. 当前页应该明确知道自己的讲述任务：
   - 建立信任
   - 解释机制
   - 展示能力
   - 证明结果
   - 情绪收束
3. 视觉审查要从“检察官”继续升级成“导演助手”

---

## 3.7 架构专家视角

### 结论

这套系统已经是一个复合平台，不是单一生成链。  
当前最大架构风险是：

> 当前真相源过多，读写边界不纯，很多“读接口”仍在做重算、兜底、写快照。

### 重点问题

1. `task / html_page / quality / scoring / snapshot / deliverability` 多层真相源并存
2. 多个读接口带写副作用
3. snapshot 既像历史，又在承担当前读路径回退
4. deliverability 虽统一了很多，但仍更像 overlay，不是系统级正式状态
5. repair 采用缺少强版本保护
6. 页面契约是“AI 协议深，系统协议浅”

### 架构专家建议

1. 明确 canonical source
2. 尽量把读接口改成纯读，把重算改成显式 refresh
3. 给页面和 repair 候选引入更强的版本与 CAS 保护
4. 将 `page_contract` 提升为统一 schema，而不只是 prompt context

---

## 3.8 后端专家视角

### 结论

后端最值得肯定的是：  
它已经具备了“比赛型生成系统”的领域模型。  
但最危险的是：

> 运行时边界还没完全纯化，容易继续制造状态漂移和隐形复杂度。

### 重点问题

1. `get_html_pages / get_task_scoring_coverage / get_task_deliverability / get_task_history_detail` 读时重算、读时写库、读时写快照
2. HTML 真值和交付给前端的页不完全一致
3. 评分覆盖仍然过度依赖文本启发式
4. 页面契约接得很深，但 deterministic validator 还要继续加强
5. repair 已经很强，但仍承担了太多职责
6. 素材绑定仍偏推荐型 JSON，而非硬关系层
7. `history-detail` 是超级聚合接口，性能和一致性压力都很高

### 后端专家建议

1. 先收读路径副作用
2. 再强化评分覆盖结构化声明
3. 再给契约页增加更强程序化校验
4. 素材绑定应有明确关系表或关系层
5. `history-detail` 要更像稳定投影，而不是临时重算大接口

---

## 3.9 前端专家视角

### 结论

前端已经比之前成熟很多，但：

> 主路径虽然顺了，代码结构和交互编排成本仍然很高。

### 重点问题

1. `PptHistoryDetail.vue` 虽然已经拆块，但动作编排仍很重
2. `PptEditor.vue` 的轮询 / 恢复 / 预览 orchestrations 仍复杂
3. `ppt.js` 仍然混装流程状态、问卷 schema、transport
4. `request.js` 仍然把 transport 和全局 UI 提示耦合
5. 焦点跳转还大量依赖 selector / scrollIntoView
6. 很多一键动作虽然能用，但 page-level imperative chain 维护成本高

### 前端专家建议

1. 继续把动作链 service 化
2. 继续把 transport 层与 UX 提示层拆开
3. 当前页补图 / 修页 / 补评分点统一成页面任务模型
4. DOM selector 型高亮和跳转逐步改成 registry/ref 模式

---

## 4. 用户角色视角补充问题

从用户视角，这个功能当前最大的真实问题不是“不会点”，而是：

### 1. 不知道什么时候算完成

用户最大的疑问永远是：

- 现在这套能不能交
- 我到底还差什么
- 做完这一项是不是就能下

### 2. 不知道系统到底帮没帮上忙

用户经常会感觉：

- 我传图了，为什么还提示缺图
- 我补评分点了，为什么分数没涨
- 我修页面了，为什么还不能下

### 3. 不知道页面为什么“不像 PPT”

用户通常能感知到：

- “这页还是很网页”

但之前系统不一定说得清：

- 是页面契约没兑现
- 还是页系样张语言缺了
- 还是主视觉没落地

### 4. 不知道“继续优化”和“不能交付”有什么区别

这也是当前用户心智里最容易混淆的一点：

- blocked
- warning
- ready

如果没有很好的人话翻译，用户会天然理解成：

- 都是不行

## 5. 团队统一优先级判断

这次 team 最统一的优先级排序是：

### 第一优先

**让最终页面真正像比赛级 PPT，而不是更稳定的普通 HTML。**

这要求：
- 页面契约硬化
- 页系样张成体系
- 章节编导模板继续落地
- 单页重设计持续收敛

### 第二优先

**让比赛评分标准真正成为唯一北极星。**

这要求：
- 评分底座比赛原生化
- 实操、团队、安全、创新、价值都变成可观测页
- 可下载与可比赛终稿分层

### 第三优先

**让后端当前态与交付门禁真正成为唯一真相。**

### 第四优先

**让前端继续减法，让用户更少理解系统，多让系统替用户多做一步。**

---

## 6. 团队统一下一步建议

如果按实际推进顺序，team 一致建议：

1. **继续推进“编导与页面设计专项”**
   - 让页面契约 / 页系样张 / 单页重设计真正稳住最终成品

2. **继续推进“比赛逻辑专项”**
   - 让评分覆盖、节奏、实操页、团队页、安全页彻底比赛化

3. **继续推进“后端收口专项”**
   - 把当前真相源与重算链收干净

4. **继续推进“前端主路径专项”**
   - 进一步把系统变成“用户能顺手完成的工作台”

---

## 7. 最终一句话总结

这次 agent team 的统一判断是：

> OREP 的 AI 生成 PPT 式 HTML 功能，已经具备了走向比赛级系统的骨架，但当前最关键的问题不是“还缺几个功能”，而是“最终页面是否真的像比赛页、底层逻辑是否真的比赛原生、系统是否真的替用户完成复杂工作”。  
> 接下来最该做的是继续收页面设计、比赛逻辑和系统真相源，而不是单纯继续堆交互或堆页面数量。
