# OREP AI HTML 生成功能 UX 修复与优化执行计划

> 版本：v1.0
> 日期：2026-04-23
> 依据文档：`/Users/liuyixing/项目/OREP/OREP_AI_HTML生成_UX分析报告.md`
> 适用范围：主用户前端、`ai-scoring` 后端、HTML 生成链路、交付门禁、预览与修复工作台

---

## 一、文档目标

本计划不是再做一份“分析报告”，而是把当前 AI 生成 PPT 式 HTML 功能的用户体验问题，整理成一份可直接开发、可验证、可排期的执行文档。

目标有 4 个：

1. 先解决“明明做了操作，但系统状态不一致、结果不生效”的核心问题。
2. 再把用户主流程从“分析平台”改成“任务驱动工作流”。
3. 在不降低 HTML 生成质量的前提下，简化补图、修复、导出这几条主路径。
4. 为后续组件拆分、进度系统升级、导出增强打基础。

---

## 二、总体判断

当前系统的问题，不是“功能不够多”，而是：

- 状态口径不统一
- 主路径过重
- 用户要理解太多内部概念
- 修复动作和真实结果没有形成闭环

因此本计划优先级不是“再加更多功能”，而是：

1. 统一状态与门禁
2. 减少跳转和概念暴露
3. 让用户在当前页面就能完成主要处理
4. 让系统反馈真实、可解释、可执行

---

## 三、优先级总览

| 优先级 | 目标 | 核心结果 |
|---|---|---|
| P0 | 修掉会误判、会卡死、会造成状态不一致的问题 | 下载门禁可信、评分覆盖可信、修复结果可信 |
| P1 | 把主流程改成任务驱动，减少跳转和理解成本 | 用户在当前页即可完成多数修复 |
| P2 | 解决结构性技术债和生成过程体验 | 大组件拆分、等待体验真实化、前后端职责更清晰 |
| P3 | 增强导出和展示能力 | PDF/ZIP/在线播放等增强项 |

## 四、P0：状态一致性与门禁可信度修复

### P0.1 统一交付门禁口径

#### 问题

当前“下载条件卡”“终稿总审”“优化任务队列”“后端下载接口”存在读取数据源不一致的问题，容易出现：

- 前端显示已通过，后端仍拦截
- 已处理任务仍被计入 `P0`
- 软风险被当成硬阻塞

#### 目标

所有交付相关判断统一基于同一份最新状态。

#### 开发内容

- 统一 `deliverability` 计算入口，确保所有页面和接口都读取同一结果。
- 严格区分：
  - `blocked`：硬阻塞
  - `warning`：可预览但需补强
  - `ready`：可交付
- 统一 `P0` 计数规则，只统计真正未完成的硬阻塞任务。
- 将“体检未 ready”“继续打磨”“页面可提升”这类软建议降为 `P1` 或 `warning`，不参与下载硬拦截。

#### 影响范围

- `ai-scoring/app/services/ppt/ppt_service.py`
- 下载接口路由
- 历史详情页下载条件卡
- 总审页
- 优化任务队列

#### 验收标准

- 同一任务在前端所有视图中看到的阻塞项完全一致。
- `warning` 状态不再拦截正式下载接口。
- `P0` 数量在处理完成后能正确归零。

---

### P0.2 清理内部修复痕迹污染正式内容

#### 问题

内部修复面板、调试文案、建议补充类文字会被正式质检误读，导致：

- 占位词误杀
- 评分注释泄露
- 页面明明可用却被误判为失败

#### 目标

内部辅助层不参与正式质检、不参与导出、不参与交付门禁。

#### 开发内容

- 在质检前统一剥离内部修复注入层。
- 在导出前统一剥离内部修复注入层。
- 占位词检测、模板页检测、评分覆盖检测统一只针对正式页面主体内容。
- 增加内部修复痕迹测试样例，防止回归。

#### 验收标准

- 不再出现“建议补充/建议上传/repair panel”导致页面失败。
- 导出的最终 HTML 不含内部修复辅助块。

---

### P0.3 评分覆盖改为“当前 HTML 优先”

#### 问题

一键补评分点后，前端动作执行了，但分数不变。根因通常是评分覆盖仍优先读取旧大纲或旧快照，而不是当前 HTML。

#### 目标

评分覆盖结果必须真实反映当前页面内容。

#### 开发内容

- 评分覆盖计算优先读取当前 HTML。
- 如同时存在大纲和 HTML，使用“当前 HTML + 大纲语义补全”的合并模式重算。
- “一键补评分点”时，将 `target_points` 作为硬约束写入修复 prompt。
- 为必备评分点建立明确规则，例如：
  - `市场规模`：需出现市场量级/TAM/SAM/SOM/规模测算
  - `竞争优势`：需出现竞争对比/差异化/壁垒
  - `融资需求`：需出现融资金额/资金用途/阶段目标

#### 验收标准

- 点击“一键补评分点”后，覆盖率能真实变化。
- 缺失评分点列表与页面实际内容一致。

---

### P0.4 补图绑定与缺图提示一致性修复

#### 问题

用户上传图片后，系统仍持续提示“缺图”，根因通常是：

- 页面绑定逻辑过宽或过弱
- 旧质检结果未刷新
- 页面提示仍走旧 `repair_route`

#### 目标

补图成功后，缺图状态必须正确刷新，且提示逻辑只看最新失败项。

#### 开发内容

- 增强“显式页码绑定”规则：
  - 文件名/说明中出现 `第26页`、`page26` 等，优先绑定当前页。
- 上传成功后自动触发当前页静默重质检。
- 前端“先补图”提示只基于最新 `failed_checks` 判断，不再依赖旧修复路径。
- 对“已补图但仍失败”的页，明确切换为：
  - 占位词
  - 模板化
  - 评分点
  这类真实剩余问题。

#### 验收标准

- 用户补图后，不再机械重复提示“先补证据”。
- 当前页已关联素材与实际绑定结果一致，不再串页。

## 五、P1：主流程任务化与工作台减法

### P1.1 把下载条件卡做成当前页工作台

#### 目标

用户停留在当前页面就能完成主要修复，而不是反复跳 tab。

#### 开发内容

- 下载条件卡内直接提供动作：
  - 一键清占位词
  - 一键重做模板页
  - 一键补评分点
  - 一键处理 P0
- 每张卡显示：
  - 当前优先处理项
  - 关联页面
  - 剩余数量
  - 处理后回显结果
- 动作执行后在卡内直接显示：
  - 本次处理了哪些页
  - 哪条规则已满足
  - 哪条仍未满足

#### 验收标准

- 用户在不切换 tab 的情况下，可以完成 60% 以上的常见修复动作。
- 处理动作执行后，卡内状态立即刷新，不出现“点了没变化”的感知问题。

---

### P1.2 将“素材证据”主路径并入 HTML 预览页

#### 问题

单独的“素材证据”页信息过重，证据包、绑定、上传、映射等概念叠加，用户很容易迷失。

#### 目标

用户围绕“当前页缺什么图”来工作，而不是围绕“证据包系统”工作。

#### 开发内容

- 在 HTML 预览右侧工作台直接展示：
  - 当前页缺图任务
  - 当前页已关联素材
  - 直接上传入口
- 上传后自动刷新当前页缺图状态。
- “素材证据”页降级为高级管理页，默认收起高级视图。
- 保留“证据包/证据链”作为高级辅助，不再做主路径。

#### 验收标准

- 用户在 HTML 预览页即可完成大部分补图动作。
- 用户无需切换到“素材证据”页也能完成当前页补图。

---

### P1.3 简化补图交互为“逐页缺图清单”

#### 目标

让用户看到的是“第几页缺哪张图”，而不是先去理解证据包。

#### 开发内容

- 素材页顶部改为“逐页待上传清单”。
- 每张卡直接显示：
  - 页码
  - 页面标题
  - 缺少的图类型
  - 建议上传内容
  - 一键进入该页上传
- 证据包逻辑退到次级层，仅用于系统内部复用和高级管理。

#### 验收标准

- 用户第一眼看到的是页面任务，不是系统抽象概念。
- 补图入口清晰且与页面直接对应。

---

### P1.4 优化 HTML 预览区交互

#### 目标

让用户感觉自己在“改 PPT”，而不是在“操作后台系统”。

#### 开发内容

- 保持 16:9 自适应舞台。
- 增加：
  - 适应窗口
  - 100%
  - 整页查看
- 增加键盘导航：
  - 左右翻页
  - Home/End 首尾页
- 将“当前页风险 / 当前页讲稿 / 当前页补图 / 当前页修复动作”集中到右侧单一工作台。

#### 验收标准

- 预览页成为主操作中心。
- 用户常见操作不再依赖多个 tab 来回切换。

---

## 六、P1.5：等待体验真实化

### P1.5.1 真实进度拆分

#### 问题

用户可以等待，但不能接受“看似有进度、实则不知系统在做什么”。

#### 目标

让用户看到的是 AI 当前真实处理阶段和页级进度。

#### 开发内容

- Round 1-4 增加更细粒度子状态。
- 返回当前页/总页数、批次数、最近一次输出时间。
- 对恢复机制提供可见说明：
  - 当前正常生成
  - 当前处于恢复阶段
  - 当前已从中断恢复

#### 验收标准

- 用户能知道系统当前正在处理哪一页、哪一批、哪个阶段。

---

### P1.5.2 渐进式结果可见

#### 目标

减少“纯等待感”。

#### 开发内容

- 大纲一生成即刻可看。
- HTML 已完成页可先预览。
- 已完成缩略图渐进展示，不必等待整套完全结束。

#### 验收标准

- 长任务过程中，用户有持续反馈和阶段性成果可看。

## 七、P2：结构性技术债治理

### P2.1 拆分 `PptEditor.vue`

#### 问题

当前单文件过大，维护成本和状态复杂度过高。

#### 目标

按步骤拆分组件，保留状态集中管理。

#### 开发内容

- 拆分为：
  - `StepQuestionnaire`
  - `StepOutline`
  - `StepGeneration`
  - `StepPreview`
  - `StepExport`
- 将 API 调用继续收口在 Pinia store。
- 将弹窗、工作台、对话框拆为独立组件。

#### 验收标准

- 主流程文件显著缩小。
- 单步逻辑可独立维护与测试。

---

### P2.2 明确双前端定位

#### 目标

避免用户误入原型前端造成体验割裂。

#### 开发内容

- 主前端作为唯一正式入口。
- AI Scoring 前端明确标注 `DEV ONLY`，仅供开发/调试。
- 将有价值组件逐步迁移到主前端，避免双维护。

#### 验收标准

- 正式用户不会接触到原型级调试前端。

---

### P2.3 统一画布与字体规范

#### 目标

减少不同路径生成质量不一致的问题。

#### 开发内容

- 统一 HTML 视口为 `1920x1080`。
- 统一系统字体栈，移除对 Google Fonts CDN 的依赖。
- 对模板降级页、修复页、正式页统一输出规范。

#### 验收标准

- 所有 HTML 页面尺寸一致。
- 离线或内网环境下字体表现稳定。

### P3.3 传输层与渲染层后续评估

#### 说明

## 九、推荐开发顺序

### 第一阶段：先修可信度

1. 统一交付门禁口径
2. 清理内部修复痕迹污染
3. 评分覆盖改为当前 HTML 优先
4. 补图绑定与缺图提示一致性修复

### 第二阶段：压主流程复杂度

1. 下载条件卡当前页工作台化
2. 素材证据并入 HTML 预览
3. 逐页缺图清单替代证据包主视图
4. 预览区交互优化

### 第三阶段：增强等待与组件结构

1. 真实进度拆分
2. 渐进式结果可见
3. 拆分 `PptEditor.vue`
4. 明确双前端定位

### 第四阶段：导出与展示增强

1. PDF 导出
2. ZIP 导出
3. 在线播放模式
4. 评估 SSE / WebSocket / 更高级渲染方案

## 十、完成标准

当以下标准满足时，可视为本轮 UX 修复完成：

### 状态一致性

- 下载按钮、总审、质检、队列、后端接口口径一致
- 不再出现“处理了但状态不变”的核心误导

### 主路径清晰

- 用户在 HTML 预览页即可完成大部分修复与补图
- 下载条件卡能直接处理主要阻塞项

### 反馈真实

- 评分覆盖、缺图状态、交付状态、P0 数量变化可实时感知
- 等待过程能看到真实进展

### 生成质量不降级

- 视口、字体、正式页输出规则统一
- 修复动作不会将内部调试信息带入正式结果

---

## 十一、备注

本计划默认原则是：

- 不牺牲 HTML 最终质量
- 不把系统内部概念强加给用户
- 优先缩短用户从“发现问题”到“完成处理”的路径
- 优先修状态一致性，再做体验美化

如果后续进入实施阶段，建议再为本计划补一份“代码级任务拆解表”，明确到：

- 哪个文件改什么
- 哪个接口返回什么
- 哪张卡片对应什么动作
- 如何验证回归
