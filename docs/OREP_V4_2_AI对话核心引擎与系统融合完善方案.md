## 1. 核心修正结论

V4.2 的第一原则是：

> **AI 对话练习不是 OREP 的一个新增功能，而是 OREP 长期能力画像的数据引擎，是整个系统的心脏。**

现有 OREP 的会议室、AI 评分、讲稿、PPT、复盘、统计、推荐都应围绕 AI 对话练习产生的数据运转，而不是和 AI 对话练习并列。

因此，V4.2 对 V4.1 做四个关键修正：

| 修正点 | V4.1 问题 | V4.2 方案 |
|---|---|---|
| 产品定位 | 把 AI 对话和路演会议写成并重关系 | AI 对话是主引擎，路演是阶段性检验 |
| 会议室融合 | 设计了会中 Sidecar，容易增加操作负担 | 会中不加交互，会议室保持纯净；会后自动分析 |
| 核心引擎 | 缺少三层问题、追问、防糊弄、评分算法 | 补齐 AI 对话引擎详细设计 |
| 数据模型 | `ability_event` 与 `dialogue_*` 关系不清 | 明确 `dialogue_*` 是原始记录，`ability_event` 是画像事件层 |

V4.2 的产品总线：

```text
教学大纲
→ AI 对话练习
→ 对话评分与追问分析
→ 能力事件生成
→ 学生能力画像
→ 教师班级报告
→ 学校驾驶舱
→ 路演检验
→ 会后复盘
→ 缺口补练
→ 下一轮 AI 对话练习
```

一句话：

> **练习是主线，路演是检验，复盘是反馈，画像是沉淀。**

## 2. 产品定位重写

### 2.1 推荐定位

**OREP：以 AI 对话练习为核心引擎的职业院校学生能力画像与成长平台。**

### 2.2 副标题

通过每日 AI 对话练习，持续检测学生知识掌握、表达能力、应用能力和复盘能力，并将数据沉淀为学生成长画像、教师教学报告和学校人才培养决策依据。

### 2.3 核心关系

```text
AI 对话练习：主通道，占能力数据 60% 左右
项目/PPT/讲稿：材料与场景支撑，占能力数据 10%-15%
路演/答辩：高压检验，占能力数据 15%左右
会议数据：补充证据，占能力数据 5%左右
复盘记录：学习闭环，占能力数据 5%-10%
```

### 2.4 不应再这样表述

不建议说：

> AI 对话是日常训练，会议室是综合验证，两者共同构成平台核心。

因为这会削弱 AI 对话练习的数据引擎地位。

建议说：

> AI 对话练习是日常数据主引擎，会议室路演是对日常练习成果的阶段性检验。

## 4. AI 对话练习引擎详细设计

这一部分是 V4.2 的核心。研发实现时，应优先保证本章，而不是优先改会议室。

### 4.1 对话练习的主通道地位

AI 对话练习承担四个任务：

1. **高频采集数据**：每天都能产生学生能力数据。
2. **低门槛覆盖全员**：不要求学生有完整项目，也不要求录制正式视频。
3. **即时反馈学习**：练完立刻知道哪里会、哪里不会。
4. **持续驱动画像**：所有画像、报告、推荐、预警首先由对话练习驱动。

其他场景的角色：

| 场景 | 角色 |
|---|---|
| 项目专项练习 | 对话练习的场景增强 |
| 路演前模拟 | 对话练习的高压版本 |
| 路演会议 | 对话练习成果的阶段检验 |
| 路演后复盘 | 对话练习下一轮补练的输入 |

### 4.2 三层问题结构

每次练习围绕一个知识点，默认 5-8 个问题，分三层递进。

| 层级 | 目标 | 题型 | 权重 | 示例 |
|---|---|---|---:|---|
| 事实层 | 验证基本概念是否掌握 | 定义、组成、步骤、作用 | 30% | “什么是 B+ 树索引？” |
| 推理层 | 验证是否理解原理 | 原因、对比、条件、限制 | 40% | “为什么联合索引要遵循最左前缀原则？” |
| 应变层 | 验证是否能应用到真实场景 | 排查、决策、方案、项目结合 | 30% | “线上查询突然变慢，你会怎么排查？” |

### 4.3 问题生成规则

AI 生成问题时必须遵守：

1. 每次只问一个问题。
2. 先事实层，再推理层，再应变层。
3. 每个知识点至少包含一个“场景问题”。
4. 至少有一个问题要求学生结合自己的项目或经历。
5. 不直接追求标准答案，而追求“理解是否真实”。
6. 对同一学生要根据历史卡点调整难度。

### 4.4 动态追问策略

AI 追问不是随机聊天，而是数据质量保证机制。

#### 4.4.1 追问触发条件

| 触发条件 | 说明 | 追问方向 |
|---|---|---|
| 回答太短 | 少于 15 个字或明显敷衍 | 澄清追问 |
| 回答正确但浅 | 有关键词但缺少原理 | 深入追问 |
| 回答模板化 | 像背答案或复制答案 | 经验结合追问 |
| 回答错误 | 概念或逻辑错误 | 引导纠错 |
| 回答绝对化 | “一定”“都可以”等过度判断 | 反例追问 |
| 停顿过久 | 语音模式长时间无回答 | 降低难度或提示 |
| 追问后改善明显 | 学生被引导后答得更好 | 记录学习能力 |

#### 4.4.2 追问类型库

| 类型 | 模板 | 使用场景 |
|---|---|---|
| 澄清追问 | “你说的 `{关键词}` 具体是什么意思？” | 回答模糊 |
| 深入追问 | “为什么这样做会有效？背后的原理是什么？” | 回答正确但浅 |
| 反例追问 | “如果换成 `{相反场景}`，还成立吗？” | 回答绝对化 |
| 场景追问 | “你能结合自己的项目举个例子吗？” | 验证真实理解 |
| 对比追问 | “它和 `{相近概念}` 有什么区别？” | 验证概念边界 |
| 纠错追问 | “你再想想，如果 `{条件}` 出现，这个方法会不会失效？” | 回答错误 |
| 降阶提示 | “提示一下，可以先从 `{线索}` 想起。” | 学生卡住 |

#### 4.4.3 追问深度控制

- 每个主问题最多追问 3 次。
- 第 1 次追问：要求解释更清楚。
- 第 2 次追问：给出场景或反例。
- 第 3 次追问：给提示或降低难度。
- 仍无法回答，则记录为卡点，不继续消耗学生耐心。

### 4.5 对话 Prompt 设计

#### 4.5.1 System Prompt 框架

```text
你是 OREP 的职业院校 AI 学习教练，正在和学生进行课后对话练习。

你的目标不是考试，而是通过对话判断学生是否真正理解知识点，并帮助学生在回答和追问中学习。

当前练习信息：
- 课程：{course_name}
- 知识点：{topic_title}
- 知识点描述：{topic_desc}
- 难度：{difficulty}
- 关联能力：{related_abilities}
- 学生历史卡点：{weak_topics}
- 学生最近练习水平：{recent_level}

对话规则：
1. 每次只问一个问题。
2. 按事实层、推理层、应变层递进。
3. 学生回答后先判断质量，再决定追问或进入下一题。
4. 不要直接羞辱或否定学生。
5. 对明显背诵或疑似查答案的回答，要切换为经验结合问题。
6. 至少一个问题要求学生结合自己的项目、经历或课堂任务。
7. 每个主问题最多追问 3 次。
8. 总时长控制在 5-8 分钟。

输出 JSON：
{
  "message": "给学生看到的问题或反馈",
  "layer": "fact/reasoning/adaptive",
  "question_type": "concept/analysis/scenario/experience/decision",
  "followup": true/false,
  "should_record_answer": true/false,
  "evaluation_hint": {
    "target_points": ["关键点1", "关键点2"],
    "rubric": "评分说明"
  }
}
```

#### 4.5.2 单题评分 Prompt 框架

```text
请评估学生对以下问题的回答。

问题：{question}
标准关键点：{target_points}
学生回答：{answer}
问题层级：{layer}

请从 4 个维度评分：
1. 准确性 accuracy：是否正确，是否有明显错误
2. 完整性 completeness：是否覆盖关键点
3. 深度 depth：是否展示理解而非背诵
4. 表达 expression：是否清晰、连贯、口语可理解

返回 JSON：
{
  "accuracy": 0-100,
  "completeness": 0-100,
  "depth": 0-100,
  "expression": 0-100,
  "comment": "一句简洁点评",
  "weak_points": ["薄弱点1"],
  "followup_recommended": true/false,
  "followup_reason": "为什么需要追问"
}
```

### 4.6 单题评分算法

单题得分：

```text
answer_score =
  accuracy × 0.40
+ completeness × 0.25
+ depth × 0.20
+ expression × 0.15
```

层级得分：

```text
fact_score = 事实层题目平均分
reasoning_score = 推理层题目平均分
adaptive_score = 应变层题目平均分
```

综合得分：

```text
total_score =
  fact_score × 0.30
+ reasoning_score × 0.40
+ adaptive_score × 0.30
```

### 4.7 对话结果输出

每次练习结束后，必须生成：

| 输出 | 用途 |
|---|---|
| 综合评分 | 学生即时反馈 |
| 三层得分 | 告诉学生是基础、理解还是应用弱 |
| 能力变化 | 告诉学生本次练习推动了哪些能力 |
| 卡点列表 | 给学生补练，也给老师看班级问题 |
| 追问表现 | 评估学习能力和抗压能力 |
| 推荐练习 | 形成下一次练习入口 |

## 5. “作弊也能学”机制

这是 OREP V4 的差异化设计，必须保留并强化。

### 5.1 设计理念

AI 时代，学生查资料、问 AI、复制答案不可避免。OREP 不应把全部精力放在“防死”，而应把学生的查答案行为引导为学习过程。

核心理念：

> **查到答案不等于掌握答案。OREP 要检测的是学生能否解释、迁移、结合自身场景，并经得起追问。**

### 5.2 半开放问题设计

| 类型 | 示例 | 为什么防糊弄 |
|---|---|---|
| 经验结合型 | “你能结合你们小组项目说说哪里用到了索引吗？” | 标准答案无法替代个人经历 |
| 观点表达型 | “你觉得 MySQL 和 MongoDB 哪个更适合你们项目，为什么？” | 需要权衡和解释 |
| 现场推理型 | “这是一个查询计划输出，你能分析瓶颈在哪里吗？” | 查答案也要现场理解 |
| 决策模拟型 | “预算有限时，你会优先优化哪类慢查询？” | 没有唯一答案 |
| 反思型 | “刚才你第一遍回答和追问后的回答有什么不同？” | 检测自我认知 |

### 5.3 查答案后的引导策略

当系统发现学生疑似查答案，不直接扣分，也不直接提示“你作弊了”，而是切换为追问：

```text
你说得比较完整。那我换个角度问：
这个知识点在你自己的项目里有没有出现过？
如果你是项目负责人，你会怎么做取舍？
```

结果：

- 学生查答案，至少接触了正确知识。
- 如果能结合自身场景解释，说明发生了学习。
- 如果追问答不上来，系统识别真实卡点。

### 5.4 产品话术

对学生：

> 你可以查资料，但 AI 会继续追问你自己的理解。查资料不是问题，不能解释才是问题。

对老师：

> OREP 不只是判断学生是否背出答案，而是通过追问判断学生是否真正理解和会应用。

## 6. 防糊弄检测机制

### 6.1 检测目标

防糊弄不是为了惩罚学生，而是为了保护能力画像数据质量。

### 6.2 检测信号

| 信号 | 说明 | 处理 |
|---|---|---|
| 回答时间异常 | 思考少于 2 秒但回答很完整 | 增加经验结合追问 |
| 答案风格突变 | 语言突然从口语变成书面百科 | 增加个人场景追问 |
| 标准答案相似度过高 | 与 AI 标准答案高度接近 | 要求解释原理或举例 |
| 追问断崖 | 第一问完美，追问明显答不上 | 标记为疑似背诵 |
| 多次答非所问 | 可能复制了无关答案 | 降低分数并记录卡点 |
| 语音停顿异常 | 长时间静默后读出完整书面答案 | 增加即时追问 |

### 6.3 风险标记

不建议用“作弊”这个字段对学生展示。内部可使用：

```text
authenticity_risk: low / medium / high
```

对应策略：

| 风险 | 策略 |
|---|---|
| low | 正常继续 |
| medium | 增加 1 次经验结合追问 |
| high | 切换到开放场景题，并降低本题置信度 |

### 6.4 数据处理

防糊弄结果不直接把学生成绩清零，而影响两个字段：

```text
answer_score：仍按回答质量评分
confidence：降低该回答对能力画像的贡献
```

这样既避免误伤，也保证画像数据质量。

## 7. 能力画像计算方式

### 7.1 六维能力模型

| 能力 | 定义 | 主要数据源 |
|---|---|---|
| 专业能力 | 知识掌握深度和准确性 | 对话事实层、推理层、项目/路演专业评分 |
| 表达能力 | 清晰、有逻辑地表达观点 | 对话表达评分、语音特征、路演表达评分 |
| 学习能力 | 被追问后能否修正和提升 | 追问改善、连续练习、卡点减少 |
| 应用能力 | 将知识应用到真实场景 | 对话应变层、项目专项练习、路演应用价值 |
| 协作能力 | 角色理解、团队配合、沟通 | 项目练习、会议/路演协作、团队角色问答 |
| 复盘能力 | 能否反思问题并制定改进 | 会后复盘、练习反思、整改完成 |

### 7.2 数据权重

能力画像必须体现“对话练习是主通道”。

| 数据源 | 建议总权重 | 说明 |
|---|---:|---|
| AI 对话练习 | 60% | 日常高频主数据 |
| 路演/答辩 | 15% | 阶段性检验 |
| 项目/PPT/讲稿 | 10% | 场景和材料支撑 |
| 会议过程数据 | 5% | 补充表达和协作证据 |
| 复盘/整改 | 10% | 学习闭环证据 |

### 7.3 能力计算示例

专业能力：

```text
professional_score =
  对话事实层得分 × 0.25
+ 对话推理层得分 × 0.25
+ 对话应变层专业相关得分 × 0.10
+ 路演专业维度得分 × 0.15
+ 项目专业评分 × 0.10
+ 时间衰减修正
```

表达能力：

```text
expression_score =
  对话表达评分 × 0.35
+ 语音流畅度 × 0.10
+ 对话逻辑连贯性 × 0.15
+ 路演表达评分 × 0.25
+ 会议表达补充 × 0.05
+ 复盘改讲表现 × 0.10
```

学习能力：

```text
learning_score =
  追问后改善程度 × 0.35
+ 卡点减少率 × 0.20
+ 连续练习稳定性 × 0.15
+ 同类题进步趋势 × 0.20
+ 复盘质量 × 0.10
```

### 7.4 时间衰减

近期练习应更能代表当前能力。

```text
time_weight = e^(-λ × days)
建议 λ = 0.03-0.05
```

建议：

- 7 天内数据权重高。
- 30 天前数据只做趋势参考。
- 学期报告保留历史，不直接覆盖当前画像。

### 7.5 能力事件与原始记录的关系

这一点修正 V4.1 的数据库冲突。

```text
dialogue_practice：一次练习的主记录
dialogue_detail：每道题、每次追问、每个回答的原始记录
practice_score_summary：按天/课程汇总
ability_event：从原始数据抽取出来的“画像贡献事件”
student_ability_profile：画像结果表
```

关系：

```text
dialogue_detail 不直接等于画像
dialogue_detail → 评分与置信度计算 → ability_event → student_ability_profile
```

例如：

| 原始数据 | 生成事件 |
|---|---|
| 一道推理层问题答得好 | 专业能力 + 学习能力事件 |
| 追问后回答明显改善 | 学习能力事件 |
| 应变层结合项目回答好 | 应用能力事件 |
| 疑似复制答案但追问答不上 | 专业能力低置信事件 |

`ability_event.score` 是这条事件对某个能力维度的贡献分，`dialogue_detail.answer_score` 是单题原始得分。两者不冲突。

## 8. 对话练习与路演的因果关系

V4.2 必须讲清楚：

> 路演不是和对话练习并列的另一个评估系统，而是对日常 AI 对话练习效果的阶段性检验。

### 8.1 因果闭环

```text
日常 AI 对话练习
  ↓
学生专业理解、表达、应用能力提升
  ↓
项目专项练习把知识迁移到真实项目
  ↓
路演中集中展示这些能力
  ↓
AI 评分和人工评分发现差距
  ↓
会后 AI 复盘定位差距原因
  ↓
系统推送下一轮补练
```

### 8.2 路演前练习触发逻辑修正

不再使用“会议创建时才生成会前练习包”作为主逻辑。

正确逻辑：

```text
系统持续记录学生已练知识点
        ↓
路演项目/PPT/讲稿/赛道模板识别涉及知识点
        ↓
系统计算“应掌握知识点 - 已稳定掌握知识点”
        ↓
生成缺口清单
        ↓
推送补练任务
```

会议创建只是一个提醒节点，不是练习生成的唯一触发点。

### 8.3 缺口分析示例

项目路演涉及：

- 数据采集
- 模型训练
- API 部署
- 应用价值测算
- 隐私安全

学生已稳定掌握：

- 数据采集
- 模型训练

系统推送补练：

- API 部署说明
- 应用价值测算
- 隐私安全答辩追问

## 9. 会议室融合修正方案

### 9.1 会议室保持纯净

V4.2 不建议在会议中增加 Sidecar 交互面板。

原因：

- 老师路演现场要听、看、评分，不适合再操作 AI 标记。
- 学生路演中不能被 AI 提醒，否则破坏真实检验。
- 会议室已经有聊天、评分、问题列表、录制，继续加面板会增加复杂度。
- 会中静默观察的实时展示价值不大，完全可以会后生成。

### 9.2 会议室只保留三类轻量改造

| 改造 | 是否影响会议 | 说明 |
|---|---|---|
| 创建会议时关联课程/项目/赛道 | 不影响 | 用于会后分析和缺口比较 |
| 录制/转写继续用于 AI 评分 | 不影响 | 沿用现有能力 |
| 会议结束后自动生成复盘入口 | 不影响 | 把分析放到会后 |

### 9.3 取消会中 Sidecar 的替代方案

用“会后自动分析卡片”替代 Sidecar：

会议结束后，在 `MeetingHistoryDetail` 或 `AiScoreResult` 展示：

```text
本次路演自动分析

1. 与日常练习相比，表达能力下降 7 分
   可能原因：语速偏快、技术术语过密

2. 项目应用价值说明不足
   关联日常练习卡点：应用场景分析得分偏低

3. 推荐补练：
   [技术降维表达] [应用价值数据化] [答辩追问应对]

[开始会后 AI 复盘] [生成补练任务]
```

### 9.4 会议室不做的事

- 不显示 AI 实时提示。
- 不弹出 AI 追问。
- 不要求老师会中手动标记。
- 不新增右侧 AI 面板作为 P0。
- 不改变现有视频、评分、聊天、录制交互。

## 10. 学生端体验设计

### 10.1 学生首页必须极度聚焦

对学生来说，首页第一屏只回答一个问题：

> 今天我要练什么？

不建议把学生首页堆满 Hero、Telemetry、任务模块、最近会议、快捷操作。现有 `Dashboard` 可以保留给综合工作台，但学生登录后的默认视图建议做“学习态首页”。

### 10.2 学生首页结构

```text
顶部：Hi，小明 | 连续练习 6 天 | 综合能力 78

主卡片：今日必练
  课程：数据库应用开发
  知识点：查询优化
  预计：8 分钟
  关联能力：专业能力、应用能力
  [开始练习]

次卡片：能力变化
  本周 +3
  最强：专业能力
  待提升：应用能力

次卡片：补练推荐
  [索引失效场景]
  [慢查询排查]

底部/侧边：历史记录、能力画像、路演复盘
```

### 10.3 练习结果页必须突出能力变化

结果页不只是显示“82 分”，而要显示：

```text
本次练习完成

综合得分：82
事实层：90
推理层：78
应变层：70

能力变化：
专业能力 +2.1
应用能力 +1.4
表达能力 +0.6

本次卡点：
1. 联合索引最左前缀
2. 慢查询排查步骤

下一步：
[再练一道应变题] [查看详细反馈] [加入补练计划]
```

### 10.4 激励机制

为了保证日常练习频率，需要设计轻量激励。

| 机制 | 说明 |
|---|---|
| 连续练习 | 连续天数，断签可补签但有限制 |
| 能力成长条 | 每次练习显示能力变化 |
| 知识点徽章 | 某知识点连续高分获得徽章 |
| 班级榜单 | 默认展示前 10，可关闭或匿名 |
| 进步榜 | 比总分榜更公平，突出成长 |
| 周目标 | 每周完成 5 次练习 |
| 老师点赞 | 老师可对进步明显学生点赞 |

注意：不要让激励变成纯游戏化刷分，应强调“能力成长”和“知识掌握”。

老师每周做一次：

```text
录入/生成下周教学大纲
→ 查看本周班级报告
→ 处理预警学生
→ 选择优秀学生/推荐参赛候选
```

### 11.2 教学大纲管理详细设计

必须保留 V4 原方案的三种模式。

#### 模式一：手动录入

字段：

| 字段 | 说明 |
|---|---|
| 课程 | 选择课程 |
| 教学周 | 第几周 |
| 日期/课时 | 哪一天哪节课 |
| 知识点标题 | 必填，如“查询优化” |
| 知识点描述 | 选填，越详细越利于出题 |

模板字段：

```text
日期 | 课时 | 知识点标题 | 知识点描述 | 难度 | 关联能力 | 是否发布
```

导入后必须有预览和错误提示。

#### 模式三：AI 生成大纲

输入：

- 课程名称

- 教学周

输出：

- 每日知识点

- 练习目标
- 关联能力

老师确认后发布。

```text
教师工作台

快捷操作：
[录入教学大纲] [查看班级报告] [处理预警] [生成补练]
```

### 11.4 班级报告页面

| Tab | 内容 |
|---|---|
| 今日 | 完成率、平均分、未完成名单、今日卡点 |

## 16. 研发验收标准

### 16.1 对话引擎验收

- AI 能按事实层、推理层、应变层生成问题。
- AI 能根据学生回答触发追问。
- 每道题有 4 维评分。
- 练习结束有三层得分和综合得分。
- 能生成卡点和推荐练习。

### 16.2 防糊弄验收

- 能识别回答时间异常。
- 能识别模板化答案。
- 能对疑似查答案切换为经验结合追问。
- 高风险回答进入画像时降低置信度。

### 16.3 画像验收

- 一次练习能生成多条 `ability_event`。
- `ability_event` 能更新学生六维画像。
- 学生能看到本次练习带来的能力变化。
- 老师能看到班级卡点统计。

### 16.4 路演融合验收

- 会议室现有功能不受影响。
- 会议结束后能生成日常练习与路演表现对比。
- 路演问题能生成补练任务。

## 17. 最终产品故事

OREP V4.2 的故事应这样讲：

> 过去，学校只能在考试、比赛或答辩时看到学生表现，但这些场景频率低、覆盖窄、反馈慢。OREP V4.2 把 AI 对话练习变成学生每天都能完成的能力检测和学习训练。学生每次回答、每次追问、每次卡住、每次修正，都会变成能力画像的一部分。
>
> 路演不再是孤立的一场展示，而是对日常练习成果的阶段性检验。学生平时通过 AI 对话练专业理解、表达逻辑、应用场景和复盘能力；正式路演时集中展示这些能力；会后系统对比日常表现和现场表现，生成补练建议，再回到下一轮对话练习。
>
> 对学生来说，OREP 让成长每天可见。  
> 对老师来说，OREP 让教学短板每天可见。  
> 对学校来说，OREP 让人才培养质量持续可见。

## 18. 一句话总结

> **OREP V4.2 的核心不是“给会议室加 AI”，而是“用 AI 对话练习驱动学生能力画像，再用会议室路演检验这套画像是否真实”。**

## 19. 与上一版的取舍说明

本版明确替换上一版中以下设计：

| 上一版设计 | 本版取舍 |
|---|---|
| AI 对话与会议室共同构成核心 | 改为 AI 对话是核心引擎，会议室是检验场 |
| 会中 AI 教练 Sidecar | 取消 P0/P1 会中交互，改为会后自动分析 |
| 会议创建时生成会前练习包 | 改为基于已练知识点与路演涉及知识点做缺口补练 |
| 能力事件表关系不清 | 明确 `dialogue_*` 是原始记录，`ability_event` 是画像贡献事件 |
| 页面融合偏会议室 | 重排优先级，P0 先做对话引擎和画像基础 |

最终执行优先级：

```text
先做 AI 对话引擎
再做能力画像和教师报告
再做学生激励与防糊弄增强
最后做会议室会后分析融合
```
