# OREP AI 生成 PPT 式 HTML
# Team 持续协作机制、当前任务板与下一阶段分工表

## 1. 目的

本文档用于把 OREP 的 `AI 生成 PPT 式 HTML` 功能，从“单线程修问题”正式切换到“持续协作 team 模式”。

目标不是增加沟通成本，而是明确：

- 谁负责定义目标
- 谁负责发现问题
- 谁负责落地实现
- 谁负责验收把关
- 当前到底在做什么
- 下一阶段先做什么

---

## 2. Team 固定编制

### 2.1 总控角色

`总控 / 集成负责人`

职责：

- 统一路线与优先级
- 协调三大工作组
- 合并设计、产品、后端、前端结论
- 把讨论转成文档、任务和代码落地
- 决定何时进入下一阶段

当前承担者：

- Codex 主代理

### 2.2 监督与质量管控官

`监督 / 质量管控官`

职责：

- 动态检查当前阶段目标是否真的落地
- 判断是否允许进入下一步
- 抽查真实任务
- 识别“看起来做了，实际没生效”的风险
- 持续维护验收口径

职责边界：

- 不直接主导设计
- 不直接主导开发
- 重点做路线跟进、验收、问题归因、风险预警

---

## 3. 三个执行小组

## 3.1 编导与页面设计组

成员职责来源：

- 赛事专家
- 路演专家
- PPT 专家
- 编导专家
- 用户角色

核心职责：

- 定义“比赛级 PPT 页面应该长什么样”
- 定义“这套路演应该怎么讲、怎么承接、怎么收束”
- 定义“什么叫不像普通 HTML、什么叫真正像比赛页”

负责产物：

- 页面契约表
- 页系样张方案
- 章节编导模板
- 单页重设计协议
- 页面契约回归验收口径

## 3.2 后端收口组

成员职责来源：

- 架构专家
- 后端专家

核心职责：

- 把设计规则真正接进 Round 2 / 3 / 4 / judge / repair / accept-reject
- 保证唯一当前态、唯一交付门禁口径
- 保证 repair / rebuild / fallback 逻辑统一
- 保证真实任务可复验

负责产物：

- 页面契约注册表
- Round 2/3/4 字段扩展
- 视觉审查契约化
- repair 契约化
- 候选页 accept/reject 机制
- 回归脚本与验收入口

## 3.3 前端体验组

成员职责来源：

- 产品经理
- 前端专家
- 用户角色

核心职责：

- 把复杂系统能力变成顺手的当前页工作台
- 减少跨 tab 理解成本
- 让用户知道“现在该做什么”“做到什么程度能下载”
- 让系统提示更像任务助手，而不是后台报表

负责产物：

- 当前页主工作台
- 下载条件工作台
- 素材补图主路径
- 等待过程真实化
- 当前页动作反馈
- 下载流程持续语境

---

## 4. 持续协作节奏

## 4.1 周期

采用 `滚动三段式` 节奏：

1. `定义`
2. `落地`
3. `验收`

每一个小阶段都必须经过这三步，而不是只做“先写代码再说”。

## 4.2 每轮固定流程

### 第一步：定义目标

由总控组织，编导与页面设计组先明确：

- 这一轮要改善什么问题
- 什么是完成态
- 如何判断页面更像比赛页

### 第二步：后端/前端落地

由后端收口组和前端体验组并行推进：

- 后端接规则
- 前端接入口与反馈

### 第三步：监督验收

由监督/质量管控官执行：

- 用真实任务抽样
- 看设计规则是否真的进系统
- 看用户链路是否真的变顺
- 看是否允许进入下一步

---

## 5. 当前阶段判断

当前项目已从：

`流程修补阶段`

进入：

`比赛级页面表达能力落地阶段`

也就是说，当前主问题已经不再是：

- 接口能不能通
- 页面能不能生成

而是：

- 生成结果像不像真正比赛页
- 页面设计契约有没有真的兑现
- 用户能不能顺着当前页一路处理到下载

---

## 7. 下一阶段分工表

## 7.1 编导与页面设计组

下一阶段任务：

1. 对 5 类重点页系做截图级视觉复核
2. 给出“仍像普通 HTML”的残留症状清单
3. 指定下一轮最该修的页系骨架

交付物：

- 页系抽样评审备注
- 残留 HTML 味问题清单
- 下一轮页系优化建议

进入下一步标准：

- 至少能明确指出 3 个以内的剩余设计短板
- 不再泛泛说“不够像 PPT”

## 7.2 后端收口组

下一阶段任务：

1. 继续把页系契约回归结果接入 accept/reject
2. 让拒绝原因可持久回流到页面缺陷档案
3. 跑真实任务回归并清掉回归项

交付物：

- 新一轮回归报告
- 拒绝原因持久化链路
- accept/reject 调整结果

进入下一步标准：

- 真实任务里没有“候选页已拒绝但前端无感知”的情况
- 真实任务里没有“刷新后原因丢失”的情况

## 7.3 前端体验组

下一阶段任务：

1. 用真实任务压主路径
2. 修掉下载条件、当前页工作台、总审之间的细碎不一致
3. 让契约型问题的人话表达更统一

交付物：

- 真实任务路径压测结论
- 缺陷收尾列表
- 已修收尾项

进入下一步标准：

- 用户能看懂“为什么不能采用”
- 用户能看懂“现在要做什么”
- 用户能看懂“做到什么程度可以下载当前版/最终版”

## 7.4 监督与质量管控官

下一阶段任务：

1. 盯真实任务端到端链路
2. 决定当前阶段是否允许进入下一轮
3. 记录“还剩哪些关键短板”

重点验收问题：

- 契约型问题是否真正闭环
- 页系骨架是否真的减少 HTML 味
- 下载链路是否仍有状态错位
- 质量卡/总审/下载条件是否一致

输出格式：

- 通过 / 不通过
- 阻塞项
- 建议下一步

## 8. 当前阶段验收口径

当前阶段不是要求“一切都做完”，而是要求以下 4 件事必须成立：

1. 页面契约已经真实进入系统主链
2. 候选页 accept/reject 已经按比赛页标准工作
3. 用户在主工作台里能理解并处理契约型问题
4. 真实任务里，页系骨架已经明显减少普通 HTML 味

只要这 4 件事还没全部稳定成立，就不能视为该阶段完成。

当前阶段建议：

- 继续按 `编导与页面设计 -> 后端收口 -> 前端体验 -> 监督验收`
  的顺序滚动推进

当前最优先动作：

1. 继续做真实任务端到端压测
2. 继续抽样验证页系骨架是否仍有 HTML 味
3. 继续把契约型问题的信息链收口到一致

当前不建议做的事：

- 再补泛化概念文档
- 再扩大量新功能
- 再分散去修无关小问题

---

## 10. 使用方式

后续每次推进时，默认遵循：

1. 先看本任务板当前阶段目标
2. 只做当前阶段最优先的事
3. 做完后由监督/质量管控官判断是否进入下一步

这样可以避免项目重新回到：

- 一边修 bug
- 一边改交互
- 一边猜页面该长什么样

的混乱状态。
