# OREP 在线路演评审平台需求分析文档

文档版本：V1.0  
编制日期：2026-07-06  
适用范围：OREP 当前项目已有功能与短中期产品建设说明  
项目定位：面向职业院校技能竞赛、项目制教学与路演训练场景的在线路演评审与学生能力成长平台

## 1. 引言

### 1.1 编写目的

本文档基于 OREP 当前项目代码、页面、接口、数据库脚本和部署配置，对系统现有能力进行需求分析与业务归纳，形成可用于项目汇报、研发对齐、验收沟通和后续迭代规划的专业需求文档。

本文档不把 OREP 简化为普通会议系统或普通评分系统，而是围绕“准备、训练、路演、评分、复盘、整改、再训练”的业务闭环，说明系统应支撑的用户角色、功能模块、数据对象、业务流程、权限边界、非功能要求与验收口径。

### 1.2 项目背景

职业院校技能大赛、创新创业路演、项目制课程汇报等场景普遍存在以下问题：

1. 参赛团队准备过程依赖经验，PPT、讲稿、答辩材料缺少结构化组织。
2. 路演训练过程难以留痕，老师和评委很难基于证据做持续复盘。
3. 评分结果容易停留在分数层面，扣分原因、证据链和整改任务无法闭环。
4. 学校缺少面向学生、团队、课程、项目和赛事的持续能力数据。
5. 远程评审、跨校区指导、专家复核和过程留档成本较高。

OREP 的建设目标是在上述场景中提供一套覆盖“学生成长 + 项目备赛 + 路演评审 + AI 复盘 + 管理运营”的综合平台，使学校、教师、学生、评审专家能够在同一系统内完成训练、评审和改进闭环。

### 1.3 产品目标

OREP 的核心产品目标包括：

1. 建立线上路演训练与评审环境，支持会议创建、参会、录制、回看、评分和报告导出。
2. 建立结构化评分体系，覆盖人工评分、AI 评分、评审团复核和问题整改。
3. 支持课程学习、题库练习、项目团队协作、PPT/讲稿准备等备赛前置流程。
4. 沉淀学生、团队、项目、会议、评分、证据和整改数据，形成可持续的能力画像与训练记录。
5. 支持学校级、多角色、多组织的数据管理与权限控制，满足校内教学管理与竞赛管理需要。

### 1.4 术语说明

| 术语 | 说明 |
|---|---|
| OREP | Online Roadshow Evaluation Platform，在线路演评审平台 |
| 路演会议 | 学生团队在线展示项目、讲解 PPT、接受评委评分和复盘的实时会议 |
| AI 评分 | 系统基于音频、视频、文本、PPT 和评分规则生成的智能评分与分析结果 |
| 证据链 | 支撑评分结论的转写片段、视觉帧、扣分项、观察点和上下文材料 |
| AI 评审团 | 由不同评审画像或人格视角组成的多角度复核机制 |
| 能力画像 | 基于学习、练习、路演、评分、复盘等数据形成的学生或团队能力结构 |
| 工作项 | 团队协作中的任务、问题、资料审核、整改建议等可执行事项 |

## 2. 总体需求概述

### 2.1 一句话定位

OREP 是面向职业院校的学生能力画像与竞赛路演成长平台，帮助学校完成从日常学习、项目准备、团队协作、模拟路演、AI/人工评审到复盘整改的全过程管理。

### 2.2 总体业务闭环

系统应围绕以下主线提供能力：

```text
用户注册/登录
→ 课程学习与题库练习
→ 项目组队与备赛材料准备
→ PPT/讲稿生成、编辑与沉淀
→ 创建或加入在线路演会议
→ 会议录制、聊天、附件和参会记录留痕
→ 人工评分与 AI 评分
→ 生成评分报告、证据链、扣分项和建议
→ AI 评审团多视角复核
→ 问题跟踪与团队整改任务
→ 下一轮训练、路演和能力提升
```

### 2.3 系统边界

#### 2.3.1 包含范围

1. 用户端：学生、教师、评委、专家等角色使用的学习、练习、会议、评分、报告、团队和资料功能。
2. 管理端：面向平台管理员、学校管理员和教师的用户、组织、课程、题库、会议、评分、资源、监控和 AI 评审配置管理。
3. 后端服务：认证授权、业务数据、文件上传、会议管理、评分管理、课程管理、考试练习、AI 评分回调、PDF 导出、监控统计等。
4. AI 评分服务：音视频处理、语音转写、视觉帧提取、评分规则分析、报告生成、AI 评审团和表达训练建议。
5. 实时通信与录制服务：LiveKit、信令服务、录制机器人、会议录制文件管理。
6. 部署运维：Docker Compose、Nginx、MySQL、Redis、MinIO、LiveKit 等运行组件。

#### 2.3.2 不包含范围

1. 不替代国家或学校正式竞赛评分规则的最终裁定权，系统评分应作为训练、辅助评审和复盘依据。
2. 不承诺对所有行业赛道自动生成完全无人工复核的最终评审结论。
3. 不承担第三方大模型服务、邮件服务、对象存储、浏览器兼容环境本身的可用性责任，但系统应具备必要的容错和提示机制。

## 3. 用户角色与权限需求

### 3.1 角色定义

| 角色 | 典型用户 | 核心诉求 |
|---|---|---|
| 平台管理员 ADMIN | 平台运维或系统负责人 | 管理全局用户、组织、资源、监控、配置和数据 |
| 学校管理员 SCHOOL_ADMIN | 学校竞赛或教学管理人员 | 管理本校用户、组织、课程、资源、会议和统计 |
| 教师 TEACHER | 指导老师、课程老师 | 创建课程、布置练习、管理团队、创建会议、查看评分与问题 |
| 学生 STUDENT | 参赛学生、课程学生 | 学习课程、参与练习、准备材料、参加路演、查看反馈并整改 |
| 评审员 REVIEWER | 校内外评委 | 参与评分、查看路演材料、给出评审意见 |
| 专家 EXPERT | 外聘专家、行业导师 | 参与指导、复核评分、提出专业建议 |

### 3.2 权限控制要求

1. 系统必须基于 JWT 进行登录态识别，并在用户端、管理端和后端接口中保持一致的认证策略。
2. 管理端菜单和页面必须按角色展示，未授权用户不得访问无权限页面。
3. 平台管理员可查看全局数据；学校管理员、教师、评委和专家应受学校、学院、租户范围约束。
4. 用户管理、组织管理、课程管理、题库管理、PPT 管理、AI 评审团画像配置等写操作应限制在具备管理权限的角色范围内。
5. 会议、评分、录制、报告和团队数据必须执行组织范围数据隔离，避免跨学校或跨学院越权访问。
6. 下载报告、播放录制、访问文件预览等受保护资源时，应通过携带认证信息的接口访问，不应依赖公开裸链接。

## 4. 功能需求分析

### 4.1 登录、注册与账号体系

#### 4.1.1 功能说明

系统应支持用户通过邮箱验证码完成注册和登录，并基于角色进入对应端。用户端未登录访问时应进入引导页，管理端未登录访问时应进入管理端登录页。

#### 4.1.2 需求要点

1. 支持发送邮箱验证码，验证码有效期应有明确限制。
2. 支持用户注册、登录、登录态校验和修改密码。
3. 用户端应支持公开引导页、登录页和受保护业务页面。
4. 管理端应根据角色跳转至第一个可访问页面。
5. 登录态过期、接口 401、无权限访问时，应给出清晰跳转或提示。

#### 4.1.3 验收口径

1. 未登录用户访问用户端业务页面时，系统返回引导页或登录入口。
2. 已登录用户访问登录页时，系统能自动跳转至首页或可访问页面。
3. 管理端不同角色只能看到并访问其权限范围内菜单。

### 4.2 首页与全局导航

#### 4.2.1 功能说明

用户端首页应作为学习、练习、准备、路演、提升和团队协作的统一入口，帮助用户判断当前最应该执行的下一步动作。

#### 4.2.2 需求要点

1. 首页展示用户当前阶段、待办事项、最近评分、学习进度、团队任务和快捷入口。
2. 顶部导航应覆盖学习、练习、准备、路演、提升和团队等主要业务模块。
3. 首页推荐事项应优先来源于真实业务数据，例如待完成课程、待处理工作项、最近扣分项、待审核资料、未完成练习等。
4. 首页不得只作为静态展示页，应承担业务分流和下一步引导作用。

### 4.3 课程学习模块

#### 4.3.1 功能说明

课程学习模块用于学生补充项目、路演、表达、专业知识等基础能力，教师和管理员可在管理端维护课程、章节、课时、视频和附件。

#### 4.3.2 用户端需求

1. 学生可查看课程列表、课程详情、章节目录和学习进度。
2. 学生可播放课时视频，系统应支持适配浏览器视频播放的分段请求。
3. 学生完成学习后，系统应记录课时完成状态和课程进度。
4. 学习页应能展示继续学习、最近学习、推荐课程等信息。

#### 4.3.3 管理端需求

1. 管理员、学校管理员和教师可创建、编辑、删除课程。
2. 支持上传课程封面、课时视频和课程附件。
3. 支持维护章节、课时、排序、状态和基础信息。
4. 支持批量删除课程或附件。

#### 4.3.4 验收口径

1. 管理端创建课程并上传视频后，用户端可以正常打开课程并播放视频。
2. 课程进度应基于真实学习记录计算，不应使用静态假数据。
3. 删除课程、章节、课时和附件时，应保持数据一致性并给出必要提示。

### 4.4 题库练习与考试模块

#### 4.4.1 功能说明

题库练习模块用于学生进行专项训练、模拟考试、错题复习和收藏题练习，为能力画像和竞赛选拔提供基础训练数据。

#### 4.4.2 用户端需求

1. 学生可查看可参与的试卷和练习。
2. 学生可开始考试、提交答卷并查看结果。
3. 系统应记录答题过程、答案、得分和提交时间。
4. 支持错题本、收藏题和专项复习。
5. 对考试过程中的异常行为，如切屏离开，应记录为过程数据。

#### 4.4.3 管理端需求

1. 支持题目新增、编辑、删除和批量删除。
2. 支持试卷新增、编辑、删除和题目组卷。
3. 支持查看待批阅记录、答卷详情和人工批阅。
4. 支持按课程、专业、班级或竞赛训练目标组织题库。

### 4.5 项目团队与协作模块

#### 4.5.1 功能说明

项目团队模块是路演训练闭环中的协作中枢，用于管理团队成员、岗位分工、项目阶段、任务、材料、提交、审核、路演绑定、成员能力证据和整改问题。

#### 4.5.2 需求要点

1. 支持创建项目团队并维护团队基本信息。
2. 支持查询候选成员、设置成员岗位和角色。
3. 支持创建、分配、更新和提交团队任务。
4. 支持项目材料上传、审核、反馈和关联任务。
5. 支持将团队与路演会议绑定，形成团队训练记录。
6. 支持基于评分报告、扣分项和复盘建议生成或关联团队整改任务。
7. 支持成员能力快照和证据记录，支撑学生能力画像。

#### 4.5.3 验收口径

1. 一个团队应能完整完成“建队、分工、任务、提交、审核、路演绑定、复盘整改”的闭环。
2. 路演后的问题和建议不应停留在报告页面，应能转化为团队可执行事项。

### 4.6 项目准备与材料生成模块

#### 4.6.1 功能说明

项目准备模块用于在正式路演前帮助团队完成选题分析、方向选择、任务生成、文档沉淀和材料准备。

#### 4.6.2 需求要点

1. 支持初始化项目准备工作台，返回团队、方向、材料和会话上下文。
2. 支持按准备会话进行 AI 对话和方向分析。
3. 支持选择项目方向，并围绕方向生成任务。
4. 支持生成、查看和沉淀项目准备文档。
5. 准备成果应可进入团队工作项、PPT 生成、讲稿编辑和路演训练流程。

### 4.7 PPT 生成、模板与讲稿模块

#### 4.7.1 功能说明

PPT 与讲稿模块用于支持参赛团队完成路演材料准备，包括模板管理、PPT 生成、页面历史、质量检查、讲稿编辑、讲稿模板和 PDF 导出。

#### 4.7.2 用户端需求

1. 支持 PPT 生成入口，用户可基于项目资料生成或编辑路演 PPT。
2. 支持查看 PPT 历史详情、页面内容、生成快照和页面质量报告。
3. 支持 PPT 编辑器或工作台，对生成内容进行预览、修复和下载准备检查。
4. 支持讲稿列表、讲稿编辑、从 PPT 生成讲稿、讲稿模板应用和讲稿 PDF 导出。
5. 支持 PPT 模板浏览、预览和下载。

#### 4.7.3 管理端需求

1. 支持 PPT 模板上传、分类、预览、下载和管理。
2. 支持 PPT 资源、生成任务和文件的后台管理。
3. 支持首页资源、轮播和内容素材配置。

#### 4.7.4 验收口径

1. 参赛团队应能从项目材料进入 PPT/讲稿准备流程，并把产物用于路演。
2. PPT、讲稿和路演评分之间应有可追踪关联，便于复盘材料质量对评分的影响。

### 4.8 在线路演会议模块

#### 4.8.1 功能说明

在线路演会议模块用于创建、管理和参与路演会议，支持实时音视频、参会记录、会议聊天、附件、开始结束控制和历史详情。

#### 4.8.2 需求要点

1. 教师或有权限用户可创建路演会议，生成会议编号或加入码。
2. 用户可通过列表、会议详情或加入码进入会议。
3. 会议应支持开始、结束、离开和参与者列表查看。
4. 会议过程中应支持聊天消息、附件上传或下载。
5. 系统应记录会议参与者、状态、时间、创建者、会议关联团队和评分上下文。
6. 会议历史详情应能展示会议基础信息、参与记录、聊天记录、录制和关联评分报告。

#### 4.8.3 实时通信需求

1. 系统应支持 LiveKit 或 WebRTC 信令能力，为在线会议提供音视频通信基础。
2. 后端应提供 LiveKit token 签发接口，确保用户以授权身份加入房间。
3. 信令服务应支持前端会议连接需要的基础消息转发。

### 4.9 会议录制与回看模块

#### 4.9.1 功能说明

会议录制用于保留路演过程证据，支撑赛后复盘、AI 评分、人工复核和训练对比。

#### 4.9.2 需求要点

1. 支持启动、停止会议录制并查询录制状态。
2. 支持录制机器人或 LiveKit 录制服务回调上传录制结果。
3. 支持用户查看“我的录制”和会议关联录制。
4. 支持播放和流式访问录制文件。
5. 支持上传本地录制视频，用于后续评分或补充证据。
6. 删除录制时应同时处理文件和业务记录的一致性。

#### 4.9.3 验收口径

1. 会议完成后，系统应能在对应会议或我的录制中找到录制结果。
2. 录制文件应能作为 AI 评分的视频输入或复盘证据。

### 4.10 人工评分模块

#### 4.10.1 功能说明

人工评分模块用于评委按照预设评分项对路演会议进行打分，系统汇总评分结果并支持导出。

#### 4.10.2 需求要点

1. 系统应维护评分模板和评分项。
2. 评委可按会议提交评分，评分应包括分值、维度和必要评语。
3. 系统应汇总评分结果，展示总分、维度分、评分人信息和明细。
4. 支持评分结果 PDF 导出。
5. 管理端应能查看评分记录和问题跟踪。

### 4.11 AI 评分模块

#### 4.11.1 功能说明

AI 评分模块是 OREP 的核心能力之一，用于基于路演音频、视频、转写文本、视觉帧、PPT 信息和赛道评分规则生成结构化评分报告。

#### 4.11.2 输入要求

系统应支持以下输入来源：

1. 实时会议产生的音频、视频、聊天、附件和录制。
2. 用户手动上传的路演视频或音频。
3. PPT、讲稿、项目材料、团队信息和赛道信息。
4. 系统内置或配置的赛道评分规则、证据字段和扣分规则。

#### 4.11.3 处理流程要求

1. 创建 AI 评分会话，记录会话编号、会议 ID、上传文件、赛道、团队、状态和进度。
2. 支持开始、取消、重启、状态查询和最新会话查询。
3. 支持音频转写、视觉帧提取、视频分析和证据包准备。
4. 支持回调机制，将 AI 服务处理状态、阶段、进度、错误信息和最终结果回写后端。
5. 支持结构化结果落库，包括观察点、扣分项、证据锚点、转写片段、视觉帧和媒体资产。
6. 支持按 sessionId、meetingId 或 reportId 查询评分报告。
7. 支持 PDF 报告导出，下载接口应保持认证保护。

#### 4.11.4 报告内容要求

AI 评分报告至少应包含：

1. 总分、等级、结论摘要和核心判断。
2. 评分维度明细、扣分项、原因和改进建议。
3. 证据锚点，包括文字转写、时间点、视觉帧和相关材料。
4. 表达能力、PPT 呈现、项目逻辑、团队配合、创新应用等专项分析。
5. “为什么不是满分”的解释，避免只给模糊评价。
6. 下一轮训练建议和可执行整改计划。
7. 必要时展示 AI 评审团复核结果。

#### 4.11.5 验收口径

1. 用户上传视频或完成会议后，可创建 AI 评分会话并看到处理进度。
2. 处理完成后，报告页面可按概览、维度、证据、表达、展示、行动、评审团等页面展示。
3. 报告中的分数、扣分项、证据和建议必须来自真实处理结果，不应使用静态模板冒充分析。
4. PDF 下载应与当前会话或报告匹配，不能出现会议 ID、会话 ID 和报告 ID 错配。

### 4.12 AI 评审团模块

#### 4.12.1 功能说明

AI 评审团模块用于在官方 AI 评分结果基础上，调用不同评审画像进行多视角复核，提升报告的解释力和可信度。

#### 4.12.2 需求要点

1. 系统应维护 AI 评委画像，包括评委代码、角色定位、关注维度、评分倾向和提示词配置。
2. 管理端支持查看、编辑和重置 AI 评委画像。
3. 用户可基于评分会话启动 AI 评审团复核。
4. AI 评审团应读取官方评分结果和证据快照，不应脱离证据凭空评价。
5. 系统应汇总多个评委的观点，形成共识问题、分歧点、优先整改项和行动建议。
6. 支持查看评审团结果和下载评审团报告。

#### 4.12.3 验收口径

1. AI 评审团启动后，应有明确的处理中、完成、失败等状态。
2. 评审结果应能对应到评委画像和证据来源。
3. 管理端修改评委画像后，新评审任务应能体现配置变化。

### 4.13 AI 复盘问答与训练建议模块

#### 4.13.1 功能说明

系统应支持围绕路演报告和评分结果进行 AI 问答，帮助学生和老师理解扣分原因、生成表达训练建议、展示改进建议和行动计划。

#### 4.13.2 需求要点

1. 支持创建复盘问答会话并发送问题。
2. 支持按会议或评分会话查看 AI 对话历史。
3. 支持生成表达训练、演示结构、行动计划等专项建议。
4. 问答内容应基于当前路演证据、报告结果和团队上下文，避免泛泛回答。

### 4.14 问题跟踪与整改闭环

#### 4.14.1 功能说明

问题跟踪模块用于承接人工评分、AI 评分、评审团复核和教师审核中产生的问题，形成可跟踪、可解决、可导出的整改闭环。

#### 4.14.2 需求要点

1. 支持问题列表、未解决问题查询和问题处理。
2. 支持问题关联会议、评分、团队、任务或材料。
3. 支持问题状态变更、处理人、处理时间和处理说明。
4. 支持导出问题 PDF，用于教学或竞赛复盘归档。
5. 高优先级扣分项应能进入团队工作项。

### 4.15 数据统计、监控与分析模块

#### 4.15.1 功能说明

统计和监控模块用于管理端查看系统运营、用户活动、在线状态、会议训练、评分结果、课程学习和问题趋势。

#### 4.15.2 需求要点

1. 支持统计概览，展示用户、会议、评分、问题、课程和训练等核心指标。
2. 支持用户行为埋点、心跳和在线状态监控。
3. 支持管理端查看用户列表、行为日志和监控看板。
4. 支持学校、学院、班级、团队等组织维度的数据过滤。
5. 统计数据应受角色和组织权限控制。

### 4.16 资源与文件中心

#### 4.16.1 功能说明

资源与文件中心用于统一管理课程附件、PPT 模板、项目材料、上传文件、录制文件和可预览文件。

#### 4.16.2 需求要点

1. 支持文件上传、下载、预览和权限校验。
2. 支持文件分类、资源管理和后台维护。
3. 支持 MinIO 或本地存储，并保留扩展能力。
4. 文件预览、录制播放、报告下载等操作必须校验访问权限。

### 4.17 组织、用户与租户管理

#### 4.17.1 功能说明

系统应支持学校级多租户和组织管理，满足不同学校、学院、专业、班级或用户组的数据管理需求。

#### 4.17.2 需求要点

1. 支持用户列表、新增用户、删除用户、批量删除用户。
2. 支持用户角色分配和组织分配。
3. 支持学校、学院等组织单元维护。
4. 支持用户组维护。
5. 支持按租户、学校、学院进行数据范围隔离。

## 6. 业务流程需求

### 6.1 学生日常学习与训练流程

```text
登录系统
→ 查看首页下一步建议
→ 进入课程学习或题库练习
→ 完成学习/练习
→ 系统记录进度、错题、收藏和成绩
→ 进入能力提升或团队备赛流程
```

### 6.2 项目备赛流程

```text
创建或加入项目团队
→ 分配成员岗位
→ 进行项目准备会话
→ 生成方向、任务和材料
→ 生成/编辑 PPT 和讲稿
→ 上传材料并审核
→ 进入模拟路演
```

### 6.3 在线路演与人工评分流程

```text
教师创建会议
→ 学生/评委加入会议
→ 团队进行在线路演
→ 会议聊天、附件和录制留痕
→ 评委提交人工评分
→ 系统汇总评分结果
→ 导出评分结果或进入问题整改
```

### 6.4 AI 评分流程

```text
会议录制或用户上传视频
→ 创建 AI 评分会话
→ 提取音频、转写文本、视觉帧和媒体证据
→ 按赛道规则生成评分结果
→ 生成结构化观察点、扣分项和证据链
→ 生成网页报告和 PDF 报告
→ 用户查看报告并进入复盘问答或整改任务
```

### 6.5 AI 评审团复核流程

```text
AI 评分报告完成
→ 用户启动 AI 评审团
→ 系统构建证据快照
→ 多个评委画像独立复核
→ 聚合分数、共识问题和分歧视角
→ 生成评审团报告
→ 输出优先整改项和行动路线
```

### 6.6 问题整改闭环流程

```text
人工评分/AI 评分/评审团产生问题
→ 系统形成问题或整改建议
→ 转入团队工作项
→ 指定负责人和截止时间
→ 成员提交整改材料
→ 教师或负责人审核
→ 下一轮路演验证改进效果
```

## 7. 非功能需求

### 7.1 性能需求

1. 常规列表、详情、统计接口应满足教学管理场景下的日常访问响应要求。
2. 视频播放和录制回看应支持分段读取，降低大文件播放失败概率。
3. AI 评分、PPT 生成、视频处理和 PDF 生成属于耗时任务，应采用异步处理、进度查询和回调机制。
4. 首页、报告页和管理端看板应避免一次性加载过多大文件或长文本。

### 7.2 可用性需求

1. 耗时任务必须展示处理中、完成、失败、可重试等状态。
2. AI 评分失败时应保留错误原因、当前阶段和可恢复入口。
3. 会议、录制、上传、下载和播放失败时应给出用户可理解的提示。
4. 用户端入口应清晰区分公开引导页、登录页和业务首页。

### 7.3 安全需求

1. 全部受保护接口必须校验 JWT。
2. 管理端写操作必须校验角色和组织范围。
3. 下载 PDF、播放录制、访问文件预览时应进行资源归属校验。
4. 邮件验证码、JWT 密钥、MinIO 密钥、LiveKit 密钥、大模型 API Key 等敏感配置不得写入前端代码。
5. 用户活动日志应避免记录密码、验证码、密钥等敏感信息。

### 7.4 数据隔离需求

1. 平台管理员具备全局视图。
2. 学校管理员、教师、评委、专家和学生仅能访问其学校、学院、团队或参与会议范围内的数据。
3. 评分报告、录制文件、团队材料和问题记录必须继承所属会议、团队或用户的数据范围。

### 7.5 可维护性需求

1. 后端业务模块应按 controller、service、mapper、entity、dto 分层维护。
2. AI 评分服务应保持音频处理、视频分析、评分规则、报告生成、评审团复核等能力边界清晰。
3. 前端应区分用户端和管理端，用户端按业务场景组织页面，管理端按后台模块组织页面。
4. 评分规则、赛道证据字段和 AI 评委画像应尽量配置化，减少硬编码。

### 7.6 部署与运维需求

1. 系统应支持 Docker Compose 部署。
2. 运行组件包括后端服务、用户端、管理端、AI 评分服务、MySQL、Redis、MinIO、LiveKit、录制机器人、信令服务和 Nginx。
3. 应提供健康检查、日志输出和基础监控入口。
4. 文件存储根目录、数据库连接、Redis 密码、LiveKit 参数、MinIO 参数、邮件参数和 AI 服务参数应通过环境变量配置。

## 8. 外部接口与系统集成需求

### 8.1 AI 评分服务集成

1. 后端应通过 HTTP 与 AI 评分服务交互，创建评分任务、上传媒体、接收状态回调和获取报告。
2. AI 评分服务应通过回调接口向后端同步处理状态和最终结果。
3. 系统应支持 AI 评分服务不可用、超时或返回异常时的失败记录和重试机制。

### 8.2 LiveKit 与录制服务集成

1. 后端负责签发会议 token。
2. LiveKit 提供实时音视频能力。
3. 录制机器人或 egress 服务负责录制会议并回传录制文件。
4. 录制结果应进入后端录制管理和文件播放流程。

### 8.3 文件存储集成

1. 系统应支持本地存储和 MinIO 对象存储。
2. 文件上传后应写入业务表或媒体资产表。
3. 文件访问应通过后端授权接口进行。

### 8.4 邮件服务集成

1. 系统应支持通过邮件发送注册和访问验证码。
2. 邮件发送失败时可提供兜底机制或明确错误提示。
3. 邮件内容应避免暴露敏感系统配置。

## 9. 质量与验收要求

### 9.1 功能验收

1. 学生可完成登录、学习、练习、组队、备赛、路演、查看报告和整改任务。
2. 教师可完成课程维护、题库维护、团队指导、会议创建、评分查看和问题跟踪。
3. 管理员可完成用户、组织、资源、课程、题库、PPT、AI 评审画像、监控和统计管理。
4. 评委和专家可参与路演评分、查看必要材料并给出反馈。
5. AI 评分从上传或录制到报告展示、PDF 下载应形成完整链路。
6. AI 评审团可基于评分报告和证据快照完成多视角复核。

### 9.2 数据验收

1. 会议、录制、评分、AI 报告、证据链、评审团和问题整改之间可追溯。
2. 不同组织和角色之间的数据访问符合权限要求。
3. 首页、学习页、报告页和团队页展示的数据来自真实后端接口。
4. PDF、视频、附件和报告下载与当前业务对象一致。

### 9.3 体验验收

1. 用户能明确知道当前下一步动作。
2. AI 评分等耗时任务有进度反馈。
3. 报告页面不只展示分数，还能解释原因、证据和改进路径。
4. 问题整改能回到团队任务，不造成“报告看完就结束”的断点。

## 10. 风险与约束

### 10.1 业务风险

1. AI 评分如果缺少证据链，容易被质疑为主观判断。
2. 评分报告如果只追求文字丰富而不能对应真实视频、文本和扣分依据，会影响可信度。
3. 团队整改如果没有落到工作项，系统闭环会停留在展示层。
4. 课程、题库、PPT、路演、评分如果数据不互通，用户会感到功能割裂。

### 10.2 技术风险

1. 音视频处理和大模型调用耗时较长，需要稳定的异步任务和状态恢复机制。
2. 视频文件、PDF 报告和视觉帧占用存储较大，需要合理清理和归档策略。
3. sessionId、meetingId、reportId 混用会导致报告查询或下载错误，需要在接口和前端路由中严格区分。
4. 第三方服务如邮件、LiveKit、MinIO、大模型 API 不稳定时，系统应有降级和明确提示。

### 10.3 管理风险

1. 多角色、多组织权限复杂，必须持续验证越权访问。
2. 赛道评分规则和 AI 评委画像更新频繁，需要配置化和版本管理。
3. 学校实际使用时可能存在多个学院、专业、班级、赛事并行，数据筛选和统计口径必须清晰。

## 11. 后续迭代建议

### 11.1 P0 优先级

1. 强化 AI 评分证据链，确保每个核心扣分项有转写、视觉帧或材料证据支撑。
2. 统一 AI 报告查询与下载的 ID 语义，避免 sessionId、meetingId、reportId 错配。
3. 将评分扣分项、复盘建议和评审团共识问题转化为团队工作项。
4. 完善用户端首页下一步推荐，使其基于真实任务和报告数据。

### 11.2 P1 优先级

1. 强化课程学习、题库练习与能力画像的联动。
2. 完善项目准备、PPT、讲稿和路演会议之间的素材流转。
3. 增强管理端统计看板，支持学校、学院、团队、赛事和时间维度分析。
4. 为 AI 评委画像、赛道规则和证据字段增加版本管理。

### 11.3 P2 优先级

1. 建立优秀路演案例库和标准化复盘模板。
2. 支持多轮路演对比，展示团队分数、表达、PPT 和整改质量变化趋势。
3. 支持导出学校级竞赛训练成果报告。
4. 支持更细粒度的学生能力画像和成长档案。

## 12. 结论

OREP 当前已具备较完整的在线路演评审平台基础：包括用户与权限体系、课程学习、题库练习、项目团队、PPT/讲稿、在线会议、录制回看、人工评分、AI 评分、AI 评审团、问题跟踪、数据监控和管理后台。

从需求角度看，OREP 的核心价值不在于单点功能，而在于把“学习准备、项目协作、路演展示、智能评分、证据复盘、任务整改、能力沉淀”连接成一个闭环。后续建设应优先围绕证据链可信度、报告到任务的闭环、跨模块数据贯通和组织权限安全持续完善，使系统真正成为学校开展职业技能竞赛训练和学生能力成长管理的基础平台。
