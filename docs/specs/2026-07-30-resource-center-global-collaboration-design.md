# 资源中心拆分与全局协作工作台设计

日期：2026-07-30  
适用端：学生端、教师端  
状态：分章节设计已确认，待书面规格复核  
实施状态：未开始

## 1. 背景

学生端当前将“任务管理”和“文件中心”共同放在 `/project-team` 的“团队协作”模块内，左侧主导航的“协作”实际上同时承担任务、文件与团队协同三类职责。

这带来四个问题：

1. 文件资料属于跨任务、跨阶段使用的长期资源，却被隐藏在协作模块的二级导航中。
2. “协作”表现为普通页面入口，不能在用户浏览其他模块时随时接收和处理任务。
3. 学生之间缺少正式的协调请求、接受、执行、提交和确认闭环。
4. 教师发布任务、学生提交与现有项目任务能力已经存在，但入口分散，无法形成统一待办工作台。

本次设计将现有文件能力独立为“资源中心”，同时把“协作”从普通页面入口升级为全局悬浮工作台。协作工作台复用现有项目任务、提交、审核、材料与实时通知能力，不重新建立另一套任务系统。

## 2. 已确认决策

### 2.1 产品结构

1. “文件中心”从协作模块拆出，更名为“资源中心”。
2. 学生端资源中心使用新主路由 `/resource-center`。
3. 旧地址 `/project-team/files` 保留兼容跳转，不中断旧链接。
4. 现有 `/project-team` 保留为“完整协作台”，继续承载复杂详情、历史记录和批量管理。
5. “协作”不再作为普通主导航页面项。
6. 桌面端将协作入口固定在左侧主导航底部。
7. 移动端将协作入口放在底部导航中央，并以轻度凸起的特殊品牌图标显示。
8. 点击协作入口后打开悬浮工作台；页面本身不跳转。
9. 悬浮工作台跨路由保持打开状态、当前标签、滚动位置和未提交草稿。

### 2.2 角色规则

1. 学生只能向同一竞赛团队的有效成员发起协调。
2. 学生协调必须由接收人接受，接收人可以婉拒。
3. 接受协调后才生成正式任务。
4. 接收人提交成果，协调发起人负责通过或退回。
5. 教师发布的是正式任务，不需要学生接受。
6. 教师可以选择自己管理的团队和一名或多名负责人。
7. 教师负责审核正式任务成果。

### 2.3 资源范围

资源中心首期只迁移当前文件中心已有能力：

- 团队材料；
- 任务成果；
- 文件版本；
- 外部链接；
- 预览与下载；
- 团队内共享。

首期不新增公共资源市场、模板商城、课程资料聚合或跨团队资源库。

## 3. 目标

- 让资源中心成为清晰、独立的长期资料入口。
- 让协作成为贯穿全平台的任务接收与处理工具。
- 建立学生之间完整、可追踪的协调闭环。
- 将教师正式任务统一汇总到全局待办工作台。
- 复用现有任务、提交、审核和通知基础设施。
- 保持旧路由、旧任务和旧文件链接兼容。
- 保持学生端与教师端视觉一致，教师端仅提高必要的信息密度。
- 支持分阶段上线和独立回滚。

## 4. 非目标

本次不包含：

- 跨团队、跨租户或陌生人协作。
- 即时聊天、群聊或音视频通话。
- 类似项目管理软件的自由看板、甘特图或工作流编辑器。
- 资源商城、公开模板市场或跨学校共享。
- 重新设计现有任务提交文件协议。
- 替换平台已有 WebSocket 通知系统。
- 一次性删除或重写 `/project-team`。
- 在协作模块单独设置不同的上传大小和文件类型限制。

## 5. 信息架构

### 5.1 学生端桌面导航

普通导航继续承载页面级模块：

- 首页；
- 集训营；
- 路演；
- 资源中心；
- AI 应用；
- 个人中心。

协作入口与普通导航分离，固定在左侧主导航底部。其位置表达“随时可用的跨模块工具”，而不是另一个业务页面。

### 5.2 教师端桌面导航

教师端保留现有业务导航与团队上下文选择。协作入口同样固定在左侧导航底部，不加入当前二级导航。

教师点击后可在悬浮工作台内：

- 切换自己管理的团队；
- 查看待审核成果；
- 查看进行中和已发布任务；
- 发布正式任务；
- 进入完整协作台。

### 5.3 移动端导航

协作使用底部导航中央的凸起入口，点击后打开底部抽屉。

约束：

- 底部导航包含协作后不得压缩为七个等宽小入口。
- 必须维持平台规定的可点按面积和可读标签。
- 低频入口应由移动端既有信息架构收纳，不通过缩小图标、字体或间距强行并列。
- 底部抽屉与桌面悬浮工作台使用同一信息顺序和状态模型。

### 5.4 路由兼容

| 路由 | 设计结果 |
| --- | --- |
| `/resource-center` | 学生端资源中心新主路由 |
| `/project-team/files` | 跳转到 `/resource-center`，保留必要查询参数 |
| `/project-team` | 保留为完整协作台 |
| `/project-team/details/:workItemId` | 保持现有任务详情地址兼容 |
| 教师端既有资源路由 | 不因学生端重命名而改变 |

## 6. 全局协作入口

### 6.1 图标

协作图标需要有区别于普通导航的品牌识别度，但不能形成另一套产品视觉。

采用四个小色块构成的协作标识：

- 品牌橙；
- 平台语义蓝；
- 平台语义绿；
- 平台路演紫。

约束：

- 不使用大面积渐变。
- 不使用霓虹、玻璃高光或重阴影。
- 彩色只集中在协作标识本身。
- 选中容器使用浅橙底、细边框和平台圆角。
- 数字徽标只统计需要当前用户操作的事项。

### 6.2 桌面浮窗

- 从左侧协作入口右侧展开。
- 默认宽度约 448px。
- 高度受视口限制，内部列表独立滚动。
- 页面内容保持可见、可操作，不增加全屏遮罩。
- 只允许一个协作浮窗实例。
- 关闭后再次打开可恢复未提交草稿。

### 6.3 移动底部抽屉

- 从底部展开。
- 顶部保留可识别的拖动柄和关闭方式。
- 支持向下关闭。
- 任务详情和表单在抽屉内部前进、返回。
- 不叠加第二层全屏弹窗。
- 需要大范围编辑或查看历史时进入完整协作台。

## 7. 协作工作台信息结构

### 7.1 学生端

顶部：

- 协作标识；
- “协作”标题；
- 当前需要处理的事项数量；
- “发起协调”主操作。

标签：

1. 收件箱；
2. 进行中；
3. 我发起的；
4. 已完成。

默认打开规则：

- 有待回应、被退回或其他必须操作事项时，打开“收件箱”。
- 没有必须操作事项时，打开“进行中”。

### 7.2 教师端

顶部：

- 协作标识；
- “协作”标题；
- 待审核数量；
- “发布任务”主操作。

团队范围：

- 可切换当前教师有管理权限的团队；
- 可进一步选择全部成员或指定成员；
- 不显示教师无权管理的团队。

标签：

1. 待审核；
2. 进行中；
3. 已发布；
4. 已完成。

默认打开规则：

- 有待审核成果时打开“待审核”。
- 没有待审核成果时打开“进行中”。

### 7.3 徽标统计

协作入口徽标只统计当前用户需要采取动作的事项：

- 等待本人接受或婉拒的请求；
- 被退回后等待本人重新提交的任务；
- 等待本人确认的同学成果；
- 等待教师审核的正式任务成果。

不统计：

- 全部进行中任务；
- 仅供查看的状态变化；
- 已读但仍在执行的普通任务；
- 平台顶部通知中心的其他通知。

## 9. 学生协调流程

### 9.1 发起

发起人填写：

- 接收人；
- 任务标题；
- 任务说明；
- 期望成果；
- 截止时间；
- 优先级；
- 可选附件或外部链接。

接收人必须是同一团队中的有效成员，不能选择自己。

### 9.2 等待回应

请求状态为 `PENDING`。

发起人可以：

- 查看；
- 撤回。

接收人可以：

- 接受；
- 婉拒。

### 9.3 接受

接受操作在一个事务内完成：

1. 锁定协调请求。
2. 验证请求仍为 `PENDING`。
3. 验证双方仍是同一团队有效成员。
4. 创建一条正式 `project_task`。
5. 将接收人写入任务负责人。
6. 将发起人写为默认审核人。
7. 将请求更新为 `ACCEPTED` 并关联任务。
8. 推送实时通知。

重复接受不生成第二个任务，而是返回已关联任务。

### 9.4 执行与提交

接受后复用现有任务状态与提交能力：

- 待处理；
- 进行中；
- 待审核；
- 已完成。

接收人可提交：

- 文件；
- 外部链接；
- 成果说明；
- 是否在通过后同步到资源中心。

### 9.5 确认与退回

发起人可以：

- 通过；
- 退回修改。

退回时必须填写原因。接收人收到通知后可再次提交新版本。

## 10. 教师正式任务流程

### 10.1 发布

教师选择：

- 管理范围内的团队；
- 一名或多名负责人；
- 标题与说明；
- 成果要求；
- 截止时间；
- 优先级；
- 可选任务附件。

发布后直接生成正式任务，不需要学生接受。

### 10.2 执行

负责人在学生协作工作台和完整任务页中查看、执行和提交。

多人任务沿用现有任务负责人和提交版本模型，不在本次引入新的子任务模型。

### 10.3 审核

教师可以：

- 查看最新成果和历史版本；
- 通过；
- 退回修改；
- 提醒负责人；
- 进入完整协作台处理复杂记录。

## 11. 数据模型

### 11.1 新增 `collaboration_request`

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `tenant_id` | 租户隔离 |
| `team_id` | 所属团队 |
| `requester_id` | 发起人 |
| `recipient_id` | 接收人 |
| `title` | 标题 |
| `description` | 说明 |
| `expected_output` | 期望成果 |
| `priority` | 优先级 |
| `due_at` | 截止时间 |
| `status` | 请求状态 |
| `linked_task_id` | 接受后关联的正式任务 |
| `responded_at` | 接受或婉拒时间 |
| `withdrawn_at` | 撤回时间 |
| `version` | 乐观并发版本 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

状态：

- `PENDING`；
- `ACCEPTED`；
- `DECLINED`；
- `WITHDRAWN`；
- `EXPIRED`。

索引：

- `tenant_id + team_id + status`；
- `recipient_id + status + updated_at`；
- `requester_id + status + updated_at`；
- `linked_task_id` 唯一索引。

### 11.2 扩展 `project_task`

建议新增：

| 字段 | 说明 |
| --- | --- |
| `source_type` | `TEACHER_ASSIGNMENT`、`PEER_COLLABORATION`、`TRAINING`、`OTHER`，兼容默认值为 `OTHER` |
| `reviewer_user_id` | 默认审核人；学生协调为发起人 |

既有任务迁移时使用兼容默认值，不要求回填精确历史来源。

继续复用：

- `created_by`；
- `owner_user_id`；
- `project_task_assignee`；
- `project_task_submission`；
- 任务要求与材料关联。

### 11.3 状态映射

协调请求只管理“是否建立任务”：

```text
PENDING → ACCEPTED
PENDING → DECLINED
PENDING → WITHDRAWN
PENDING → EXPIRED
```

接受后，执行状态全部由 `project_task` 与 `project_task_submission` 管理，不在请求表重复保存。

## 12. 权限模型

### 12.1 学生

| 操作 | 权限 |
| --- | --- |
| 发起协调 | 同一租户、同一团队的有效成员 |
| 接受或婉拒 | 仅请求接收人 |
| 撤回 | 仅发起人，且状态仍为 `PENDING` |
| 查看请求 | 发起人、接收人、团队管理者 |
| 提交成果 | 正式任务负责人 |
| 审核同学成果 | 协调发起人 |
| 查看完整任务 | 参与者或团队管理者 |

### 12.2 教师

| 操作 | 权限 |
| --- | --- |
| 发布任务 | 自己管理的团队 |
| 指定负责人 | 目标团队有效成员 |
| 审核成果 | 任务所属团队的管理教师 |
| 切换团队 | 仅返回有管理权限的团队 |
| 查看历史 | 管理范围内任务 |

### 12.3 强制校验

所有读写操作必须同时校验：

- 当前租户；
- 目标团队；
- 当前用户与团队关系；
- 任务或请求参与关系；
- 当前状态是否允许操作。

不能仅凭请求 ID、任务 ID 或提交 ID 访问数据。

## 13. API 边界

新增协作聚合与请求接口：

```text
GET  /api/collaboration/summary
GET  /api/collaboration/items
POST /api/collaboration/requests
GET  /api/collaboration/requests/{id}
POST /api/collaboration/requests/{id}/accept
POST /api/collaboration/requests/{id}/decline
POST /api/collaboration/requests/{id}/withdraw
```

`GET /api/collaboration/items` 支持：

- `view`：`ACTION_REQUIRED`、`IN_PROGRESS`、`CREATED_BY_ME`、`COMPLETED`；
- `teamId`：教师端团队范围；
- 游标或分页参数；
- 服务端稳定排序。

继续复用现有接口：

- `/api/project-teams/{teamId}/tasks/{taskId}`；
- `/api/project-teams/{teamId}/tasks`；
- `/api/project-teams/tasks/{taskId}/submissions`；
- `/api/project-teams/submissions/{submissionId}/review`；
- 教师端既有任务与审核接口。

原则：

- 协作接口负责聚合列表和学生协调请求。
- 项目任务接口负责正式任务、提交和审核。
- 教师浮窗调用既有任务能力，不复制发布和审核实现。

## 14. 并发与幂等

### 14.1 接受请求

- 使用数据库事务。
- 对请求行加锁，或使用带状态条件的原子更新。
- 只有 `PENDING` 可以进入 `ACCEPTED`。
- 任务创建和请求关联必须在同一事务中完成。
- 请求已接受时返回现有 `linked_task_id`。

### 14.2 其他动作

婉拒、撤回、审核和退回均使用“当前状态 + 版本号”条件更新。

状态已改变时：

- 返回明确的冲突响应；
- 前端刷新当前条目；
- 提示“该事项状态已由其他成员更新”；
- 不覆盖最新数据。

### 14.3 重试

- 创建请求支持客户端幂等键，避免网络重试产生重复邀请。
- 文件上传继续使用现有上传幂等与进度能力。
- 通知失败不能回滚核心业务事务，进入可重试队列或日志补偿。

## 15. 实时通知

复用现有通知服务、WebSocket 通道和：

```text
/user/queue/notifications
```

新增通知类型：

- 收到协调请求；
- 请求被接受；
- 请求被婉拒；
- 请求被撤回；
- 收到教师任务；
- 成果已提交；
- 成果被退回；
- 成果已通过。

收到协作相关通知后：

1. 顶部通知中心按现有规则更新。
2. 协作入口重新请求 `summary`。
3. 浮窗已打开时刷新对应标签。
4. 不直接覆盖用户正在编辑的草稿。

WebSocket 断开时，打开浮窗和重新获得页面焦点时主动刷新；不额外建立第二条实时连接。

## 16. 成果同步到资源中心

- 协作提交继续使用平台统一上传能力。
- 上传限制沿用平台已确认的 5GB 上限。
- 支持类型沿用平台统一扩展后的文件类型，不在协作模块另设白名单。
- 提交人可选择“通过后同步到资源中心”。
- 待审核和被退回版本不进入正式资源列表。
- 审核通过后同步最终版本。
- 同步资源记录任务、提交版本、提交人和审核人来源。
- 同步失败不改变审核结果，但必须记录并允许补偿重试。
- 延迟到审核通过后同步的规则首期只应用于新协作工作台创建的 `PEER_COLLABORATION` 和 `TEACHER_ASSIGNMENT` 任务；既有训练任务和历史任务保持当前同步语义，避免无关流程回归。

## 17. 前端状态管理

协作工作台使用全局状态，而不是页面局部状态。

需要保留：

- 是否打开；
- 当前角色视图；
- 当前团队；
- 当前标签；
- 当前详情或表单步骤；
- 各标签滚动位置；
- 未提交草稿；
- 汇总数量；
- 最近刷新时间。

清理规则：

- 用户退出登录时全部清理。
- 当前团队失效时清理该团队相关详情和草稿。
- 用户主动丢弃草稿时清理对应草稿。
- 普通路由切换不清理。

## 18. 页面状态与异常反馈

### 18.1 加载

- 首次加载使用与最终列表结构一致的轻量骨架。
- 不用全屏白色遮罩。
- 标签切换只更新内容区。

### 18.2 空状态

分别提供：

- 没有等待回应的请求；
- 暂无进行中任务；
- 尚未发起协调；
- 暂无已完成任务；
- 教师暂无待审核成果。

每个空状态只保留一个与当前情境相关的行动入口。

### 18.3 网络失败

- 浮窗保持打开。
- 保留当前标签和草稿。
- 列表区域显示行内错误和重试。
- 表单提交失败明确提示“尚未提交”。
- 不因失败自动关闭表单。

### 18.4 操作中

- 当前按钮进入加载状态。
- 同组冲突按钮同时禁用。
- 操作成功后局部更新条目并刷新汇总。
- 不连续弹出多条重复成功消息。

### 18.5 权限变化

成员被移出、团队被解散或教师管理权限被撤销时：

- 终止当前操作；
- 清理不可访问详情；
- 刷新团队范围；
- 提示权限已发生变化；
- 不泄露原任务或成员数据。

### 18.6 上传失败

- 显示具体文件名。
- 显示可理解的失败原因。
- 已成功文件保留。
- 提供单文件重试。
- 支持上传进度和取消。
- 不将上传失败误报为任务提交成功。

## 19. 可访问性

- 协作入口提供明确的可访问名称和待办数量说明。
- 桌面浮窗使用适当的补充区域或对话区域语义，但不错误阻塞页面。
- 移动底部抽屉提供可访问标题和关闭按钮。
- 标签支持键盘切换并暴露选中状态。
- 所有主要点击目标不低于平台规定尺寸。
- 聚焦环清晰可见。
- 待处理、成功、退回等状态同时包含文字或图标。
- 动态结果使用合适的 `aria-live`。
- `prefers-reduced-motion` 下关闭非必要位移动效。
- 打开浮窗后焦点进入标题或首个待处理项；关闭后返回协作入口。

## 20. 实施阶段

### 阶段一：导航与资源中心迁移

范围：

- 增加 `/resource-center`。
- 将现有文件中心能力迁移到资源中心入口。
- `/project-team/files` 增加兼容跳转。
- 从普通导航移除协作页面项。
- 增加桌面和移动端特殊协作入口外壳。
- `/project-team` 与历史任务链接保持不变。

验收：

- 现有文件、版本和链接全部可访问。
- 旧链接不出现 404。
- 新旧入口不会产生两套文件数据。
- 协作入口暂未启用的功能有清晰状态，不形成死按钮。

回滚：

- 恢复旧导航配置。
- 保留新路由但不对用户展示。
- 不涉及业务数据迁移回滚。

### 阶段二：学生协调闭环

范围：

- 新增协调请求表和接口。
- 增加发起、接受、婉拒和撤回。
- 接受后生成正式任务。
- 接入提交、确认、退回和通知。
- 完成学生端悬浮工作台。

验收：

- 完整学生协调端到端流程通过。
- 重复接受不会创建重复任务。
- 跨团队与跨租户访问被拒绝。
- 浮窗跨路由状态保持。

回滚：

- 关闭学生协调功能开关。
- 已生成的正式任务继续可在完整协作台处理。
- 不删除已创建的请求与任务。

### 阶段三：教师工作台与上线加固

范围：

- 教师团队切换。
- 教师正式任务发布。
- 待审核聚合。
- 提醒、通过和退回。
- 移动端完整适配。
- 性能、监控、灰度和权限回归。

验收：

- 教师只能操作管理范围内团队。
- 多团队数据不会串联。
- 待审核数量与真实提交一致。
- 学生、教师关键流程均在生产等价环境通过。

回滚：

- 关闭教师悬浮工作台入口。
- 继续使用既有教师任务页和审核页。
- 不影响阶段二学生协调任务。

## 22. 监控与上线

需要记录：

- 协调请求创建量；
- 接受率、婉拒率、过期率；
- 请求接受到任务创建失败数量；
- 重复操作冲突数量；
- 通知发送失败数量；
- 待办汇总接口耗时；
- 浮窗列表接口错误率；
- 审核通过后资源同步失败数量。

上线方式：

- 使用租户级或用户级功能开关。
- 先内部账号，再测试团队，再逐步扩大。
- 每个阶段独立开关。
- 发现异常时关闭入口，不删除业务数据。

## 23. 风险与取舍

### 23.1 复用现有任务模型

优点：

- 复用成熟的提交、审核和材料能力；
- 历史任务可继续展示；
- 降低双系统状态不一致风险。

代价：

- 需要扩展现有任务权限，使学生协调发起人能够审核特定来源任务；
- 必须严格限制该权限只对 `PEER_COLLABORATION` 生效。

### 23.2 保留完整协作台

优点：

- 悬浮工作台可以保持简单；
- 复杂历史和批量管理不挤入小窗口；
- 旧链接和现有用户习惯保留。

代价：

- 浮窗与完整页需要共享同一数据源和状态文案；
- 禁止各自实现不同的任务规则。

### 23.3 分阶段上线

优点：

- 每阶段可独立验证与回滚；
- 文件导航迁移不会与新业务状态同时发生；
- 教师多团队权限可以单独加固。

代价：

- 阶段一协作入口可能暂时只进入完整协作台或显示功能准备状态；
- 需要通过功能开关控制过渡体验。

## 24. 验收标准

### 信息架构

- 学生端主导航出现“资源中心”。
- 普通导航不再把“协作”当成页面入口。
- 桌面左下和移动底部中央存在特殊协作入口。
- `/project-team/files` 正确跳转到 `/resource-center`。
- `/project-team` 与历史任务地址继续可用。

### 学生协作

- 只能选择同团队有效成员。
- 接收人可以接受或婉拒。
- 接受后只创建一个正式任务。
- 接收人能够提交多个版本。
- 发起人能够通过或退回。
- 最终状态与通知、徽标一致。

### 教师任务

- 教师能切换管理范围内团队。
- 能指定一人或多人并直接发布任务。
- 学生无需接受即可收到正式任务。
- 教师能够审核、退回和提醒。
- 教师无法访问非管理团队数据。

### 资源

- 现有文件中心数据无损迁移到新入口。
- 上传限制与平台统一为 5GB。
- 文件类型与平台统一。
- 只有审核通过的选定成果同步为正式资源。

### 视觉与可用性

- 使用平台现有 token、间距、圆角、按钮和状态规范。
- 彩色只集中在协作标识和必要语义图标。
- 普通任务使用开放列表，不出现多层卡片堆叠。
- 1545×1071 下浮窗无裁切和溢出。
- 1024px 桌面宽度和 390px 手机宽度可完整操作。
- 键盘和减少动效模式可用。

### 质量

- 后端迁移可重复执行并有回滚说明。
- 后端专项测试通过。
- 学生端与教师端构建通过。
- 前端专项测试通过。
- 两条端到端流程通过。
- 线上灰度期间无跨租户、跨团队权限泄漏。
