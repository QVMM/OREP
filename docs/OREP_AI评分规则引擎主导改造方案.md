# OREP AI评分流水线改造方案：规则引擎主导 + LLM证据抽取

版本：v1.1  
日期：2026-07-04  
适用范围：OREP AI评分服务、AI评审团复核、评分报告、赛道规则、证据闭环  
首批试点赛道：人工智能赛道、新一代信息技术赛道  
最终目标：首批试点稳定后，必须扩展到全部42个赛道

## 一、改造目标

当前 OREP AI评分流水线已经具备多模态证据、ASR、视频抽帧、音视频融合、LLM评分、报告生成、评审团复核、评分会话、证据锚点、扣分项和追回分等基础能力。下一阶段的核心改造目标是：

> 将系统从“LLM主导评分”升级为“规则引擎主导评分，LLM负责证据抽取、证据解释和争议辅助”。

改造后，LLM 不再直接自由决定最终分数。LLM 负责从路演转写、视频帧、PPT/OCR、上传材料、历史评分记忆中抽取主张和证据，判断证据等级，提出扣分候选和修复建议。规则引擎根据赛道规则、证据等级、评分上限、扣分项、追回分和校准策略计算最终分数。

## 二、总体原则

1. 评分权力从 LLM 转移到规则引擎。
2. LLM 输出必须结构化，不能只输出自然语言报告。
3. 每个观测点必须绑定证据锚点。
4. 每个分数必须能解释“为什么给到这里、为什么不能更高”。
5. 首批只做 1-2 个赛道，优先人工智能赛道和新一代信息技术赛道。
6. 试点稳定后，必须逐步扩展到42个赛道，不能长期停留在两个赛道。
7. 保留旧评分报告兼容能力，避免现有用户页面、历史报告、评审团功能被一次性破坏。
8. 改造采用影子模式、灰度切换、正式接管三阶段，不直接切断现有主流程。

## 二点五、质量门槛与准入标准

本章是 v1.1 对 v1.0 的严谨性补强。后续所有开发任务不能只按“功能完成”验收，必须同时满足本章定义的质量门槛。没有达到门槛的模块只能进入实验、影子或内部试用状态，不能作为正式评分依据。

### 2.5.1 42份现有评分规则的可用性判断

当前 `42赛道梯度评分规则v1.2-证据审查版` 可以作为规则知识来源和赛道化草案，但不能直接作为生产级规则引擎规则使用。原因如下：

1. Markdown 是人读格式，不是机器执行格式。
2. 不同赛道的证据定义、扣分规则、反包装检查细致程度可能不完全一致。
3. E0-E5 证据等级虽然有总纲，但每个赛道、每个观测点仍需要硬条件。
4. 官方依据、赛道化推导、OREP 训练规则需要分层标注。
5. 每个赛道必须经过样本验证，不能因为已有 Markdown 文件就认为可上线。

因此，42份规则必须经过“规则准入审计”后，才能进入规则引擎正式规则库。

### 2.5.2 单个赛道规则准入标准

每个赛道上线前必须满足以下标准：

| 类别 | 最低准入标准 |
|---|---|
| 观测点完整性 | 必须覆盖官方5大维度、15个观测点、总分100分 |
| 观测点字段 | 每个观测点必须有代码、名称、所属维度、满分、赛道定义、必需信息、可接受证据 |
| 证据等级 | 每个观测点必须定义 E0-E5 的硬条件和分数上限 |
| 扣分规则 | 每个观测点至少有3类扣分规则：缺失证据、证据弱、证据矛盾或风险项 |
| 追回规则 | 每类扣分必须有可验收的修复条件和最高追回分 |
| 来源标记 | 每条规则必须标记为官方依据、赛道化推导或 OREP 训练规则 |
| 反包装检查 | 每个赛道必须有套壳、堆概念、第三方包装、虚假落地等风险识别项 |
| 样本验证 | 试点赛道至少20条样本，扩展赛道准入至少10条样本 |
| 人工抽查 | 每个赛道上线前至少完成2名人工复核者抽查 |

不满足以上任一项的赛道，只能标记为 `draft` 或 `pilot`，不能标记为 `active`。

### 2.5.3 E0-E5 证据等级硬条件

证据等级不能只由 LLM 自由判断，必须满足硬条件。

| 等级 | 硬条件 | 最高分档 |
|---|---|---:|
| E0 无证据 | 没有转写、画面、材料或历史记录能支撑该观测点 | 不超过观测点20% |
| E1 口号式主张 | 只有“先进、规范、落地、领先”等结论，无方法、数据或画面 | 不超过观测点30% |
| E2 解释性证据 | 有流程、架构、方法或口头解释，但缺少量化和现场验证 | 不超过观测点50% |
| E3 内部量化证据 | 有内部测试、成本测算、性能指标、样本数据，但缺少真实场景或第三方验证 | 不超过观测点70% |
| E4 场景验证证据 | 有现场演示、试点案例、用户反馈、前后对比或真实场景材料 | 不超过观测点85% |
| E5 独立可核验证据 | 有第三方报告、认证、审计、客户验收、公开 benchmark、可复现实验 | 可进入高分档 |

硬性禁止：

- 没有证据锚点时不得高于 E1。
- 没有量化结果时不得高于 E2，除非该观测点本身不要求量化。
- 没有真实演示或场景验证时不得高于 E3。
- 没有独立可核验证据时不得判为 E5。
- 低置信度 OCR、模糊视频帧、无法定位的材料页不能单独支撑 E4/E5。

### 2.5.4 稳定性量化标准

以下指标用于判断系统是否可以从影子模式进入正式接管：

| 指标 | 试点准入标准 | 成熟目标 |
|---|---:|---:|
| 同一证据快照下规则引擎分数一致率 | 100% | 100% |
| 15个观测点完整输出率 | 100% | 100% |
| LLM 证据抽取 JSON 解析成功率 | >= 98% | >= 99.5% |
| 无来源主张进入评分率 | 0% | 0% |
| E4/E5 硬条件违规率 | 0% | 0% |
| 证据锚点引用准确率 | >= 85% | >= 92% |
| 关键扣分项复现一致率 | >= 80% | >= 90% |
| 总分相对专家均分 MAE | <= 8分 | <= 5分 |
| 维度分相对专家均分 MAE | <= 维度满分12% | <= 维度满分8% |
| 报告核心字段生成成功率 | >= 98% | >= 99.5% |

如果任何核心指标未达标，规则引擎结果只能作为参考，不能成为正式分。

### 2.5.5 证据质量标准

| 证据通道 | 可用标准 | 不可正式使用的情况 |
|---|---|---|
| ASR转写 | 有效转写段 >= 3，覆盖率 >= 80%，关键时间戳可定位 | 转写严重缺失、说话人错乱严重、无时间戳 |
| 视频帧 | 有效帧比例 >= 60%，覆盖开场、方案、演示、总结等关键阶段 | 有效帧过低、关键演示阶段缺帧、画面无法识别 |
| OCR/PPT | 能识别标题、关键指标、图表或表格摘要，置信度可记录 | 模糊不可读、无法定位页码或帧、无法判断来源 |
| 上传材料 | 有文件 hash、材料类型、页码或段落定位、解析文本 | 无 hash、无法解析、无法定位证据页 |
| 融合时间线 | 能把 ASR 与画面按时间窗口关联 | 时间线为空、窗口数量为0、关键片段无法对应 |
| 历史记忆 | 扣分项、追回项和证据快照能按 session/team/track 追溯 | 只保存自然语言摘要，无法追溯原始证据 |

### 2.5.6 失败态、降级态和人工复核标准

系统必须明确区分以下状态：

| 状态 | 触发条件 | 处理方式 |
|---|---|---|
| `completed` | 证据、规则、评分、报告均达到准入标准 | 可作为正式结果 |
| `completed_with_warnings` | 主流程完成，但存在低置信度证据或非关键字段缺失 | 可展示，但必须显示警告 |
| `needs_human_review` | 关键证据低置信度、奖项边界、分差过大或争议严重 | 不建议自动定论，进入人工复核 |
| `degraded` | 某证据通道失败，但仍可基于剩余证据保守评分 | 分数必须受限，报告显示降级原因 |
| `failed` | 规则缺失、证据严重不足、JSON无法解析、规则引擎无法计算 | 不生成正式评分 |

人工复核触发条件：

- 规则引擎分与旧 LLM 分差异超过10分。
- 规则引擎分与评审团 trimmed average 差异超过8分。
- 总分处在奖项边界或晋级边界附近。
- E4/E5 证据锚点不足或来自低置信度 OCR。
- 关键观测点证据等级被评审团多人质疑。
- 用户申诉、教师标记或管理员手动要求复核。
- 规则文件、证据 schema 或评分指纹出现不一致。

### 2.5.7 上线准入与回滚标准

规则引擎正式接管某个赛道前必须满足：

1. 试点评测集全部跑通。
2. 核心稳定性指标达到 2.5.4 试点准入标准。
3. 连续7天无 P0 评分事故。
4. 新旧报告兼容测试通过。
5. PDF、用户端、管理端、后端 API、Python 服务全链路通过。
6. 失败态和降级态能在前端明确展示。
7. 可以一键回退到旧流水线主评分。
8. 回退后历史报告和新评分会话不丢失。

回滚触发条件：

- 规则引擎计算异常导致批量评分失败。
- 同一证据快照出现不一致分数。
- 正式分数出现系统性偏高或偏低。
- 证据等级硬条件被绕过。
- 历史报告或下载链路大面积异常。

## 三、目标架构

### 3.1 当前形态

```text
上传视频/会议录制
  -> 音频转码
  -> ASR转写
  -> 语音质量分析
  -> 视频抽帧与画面识别
  -> 音视频融合
  -> LLM五维十五点评分
  -> 技术校准
  -> 报告生成
  -> AI评审团复核
```

当前形态的问题是：LLM 同时承担“理解、证据判断、打分、解释、建议”多个职责，分数稳定性和可复现能力受模型输出影响较大。

### 3.2 改造后形态

```text
上传视频/会议录制/材料
  -> 证据预处理
  -> 主张抽取
  -> 证据绑定
  -> 证据等级判断
  -> 扣分项生成
  -> 规则引擎算分
  -> 报告解释生成
  -> 评审团争议复核
  -> 历史记忆与训练闭环
```

### 3.3 职责划分

| 模块 | 改造后职责 |
|---|---|
| ASR/视频/OCR/材料解析 | 提供原始证据 |
| LLM证据抽取器 | 抽取主张、证据、证据等级、缺失证据 |
| 赛道规则库 | 提供观测点、证据等级、评分上限、扣分规则 |
| 规则引擎 | 计算观测点分、维度分、总分、追回分 |
| 报告生成器 | 把结构化评分结果转成用户能看懂的报告 |
| AI评审团 | 复核争议点、证据等级、扣分合理性，不直接替代规则引擎 |
| 历史记忆 | 保存扣分项、补证任务、追回分、评分指纹 |

## 四、阶段一：规则与数据结构梳理

### 4.1 大步骤目标

先把首批试点赛道的规则从 Markdown 和 prompt 中抽离，整理成规则引擎可以读取、校验、执行的结构化规则。

### 4.2 小步骤

#### 4.2.1 盘点现有规则来源

需要梳理以下来源：

- `42赛道梯度评分规则v1.2-证据审查版/人工智能赛道.md`
- `42赛道梯度评分规则v1.2-证据审查版/新一代信息技术赛道.md`
- `ai-scoring/app/services/llm_scoring_service.py` 中的五维十五点评分 prompt
- `backend/src/main/java/com/orep/backend/service/AiScoreRuleEngine.java`
- `backend/src/main/java/com/orep/backend/service/AiScoreStructuredResultValidator.java`
- `backend/src/main/java/com/orep/backend/service/RubricResolverService.java`
- `track_rubric_config`
- `track_evidence_schema`

小步骤验证：

- 能列出两个试点赛道的15个观测点。
- 能列出每个观测点的满分、证据等级、评分上限和典型扣分项。
- 能明确哪些规则已经在代码里，哪些只存在于 Markdown，哪些只存在于 prompt。

#### 4.2.2 定义试点赛道规则 JSON Schema

建议先定义 `track_rule_v2.json` 结构，核心字段包括：

```json
{
  "trackId": "42",
  "trackName": "人工智能赛道",
  "ruleVersion": "v1.2-engine-pilot",
  "dimensions": [],
  "observations": [],
  "evidenceLevels": [],
  "deductionRules": [],
  "recoveryRules": [],
  "riskPatterns": []
}
```

每个观测点至少包含：

- `observationCode`
- `observationName`
- `dimensionCode`
- `maxScore`
- `trackDefinition`
- `requiredInfo`
- `acceptableEvidence`
- `evidenceCaps`
- `deductionRules`
- `recoveryRules`
- `reviewTriggers`

小步骤验证：

- JSON Schema 能表达人工智能赛道所有15个观测点。
- JSON Schema 能表达新一代信息技术赛道所有15个观测点。
- 同一个观测点在不同赛道下可以有不同“赛道定义”和“可接受证据”。

#### 4.2.3 建立规则版本与 hash 机制

每次评分必须绑定：

- 赛道 ID
- 赛道名称
- 规则版本
- 规则 hash
- 证据 schema 版本
- 证据 schema hash
- 规则引擎版本

小步骤验证：

- 创建评分会话时可以记录规则版本和 hash。
- 同一规则文件内容变化后 hash 必须变化。
- 旧报告仍能查到当时使用的规则版本。

#### 4.2.4 建立规则准入审计表

每个赛道必须生成一份规则准入审计表，审计表至少包含：

- 赛道名称和赛道 ID。
- 规则版本和 hash。
- 15个观测点完整性检查。
- 每个观测点的 E0-E5 硬条件。
- 每个观测点的评分上限。
- 每个观测点的扣分规则数量。
- 每个扣分规则的修复验收标准。
- 官方依据、赛道化推导、OREP 训练规则的来源标记。
- 反包装、反作弊、风险识别项。
- 样本测试结果。
- 人工复核结论。

小步骤验证：

- 人工智能赛道和新一代信息技术赛道都生成规则准入审计表。
- 审计表中不得出现空白观测点。
- 审计表中不得出现“仅见 Markdown 描述、无结构化字段”的规则项。
- 审计表能明确给出：可进入 `pilot`、可进入 `active` 或需要返工。

#### 4.2.5 区分官方依据、赛道化推导和产品训练规则

每条规则必须标记来源类型：

| 来源类型 | 说明 | 对外表达方式 |
|---|---|---|
| `official` | 来自官方评分要素或官方赛道说明 | 可称为官方评分依据 |
| `track_inference` | OREP 根据赛道岗位任务推导 | 必须标注为赛道化推导 |
| `orep_training` | 为训练复盘、证据补齐、扣分追回设计 | 只能称为平台训练规则 |

小步骤验证：

- 结构化规则中每条扣分项和证据要求都有来源类型。
- 报告对外展示时不把 `track_inference` 或 `orep_training` 写成官方原文。
- 管理端可以查看规则来源和版本变更记录。

### 4.3 大步骤验证

阶段一完成时必须满足：

1. 人工智能赛道和新一代信息技术赛道都有结构化规则文件。
2. 每个赛道都有15个观测点配置。
3. 每个观测点都有证据等级上限。
4. 每个观测点至少有基础扣分规则。
5. 创建评分会话时能绑定结构化规则版本。
6. 旧 Markdown 规则仍保留，但系统运行不再依赖人工阅读 Markdown。
7. 两个试点赛道都通过规则准入审计。
8. 每条规则都标记来源类型。
9. 未通过审计的赛道不能进入正式评分，只能进入 draft 或 pilot。

## 五、阶段二：LLM证据抽取器改造

### 5.1 大步骤目标

把 LLM 从“直接评分员”改成“证据审查员”。LLM 的第一职责是抽取主张、绑定证据、判断证据等级、指出缺失和风险。

### 5.2 小步骤

#### 5.2.1 定义 LLM 证据抽取输出格式

LLM 输出不再以 `overall_score` 为核心，而是以证据对象为核心。

建议输出结构：

```json
{
  "claims": [],
  "evidenceItems": [],
  "observationEvidence": [],
  "deductionCandidates": [],
  "recoveryCandidates": [],
  "riskFlags": [],
  "extractionQuality": {}
}
```

其中 `observationEvidence` 至少包含：

- `observationCode`
- `claimIds`
- `evidenceIds`
- `evidenceLevel`
- `confidence`
- `supportSummary`
- `missingEvidence`
- `suggestedScoreCap`
- `validityStatus`

小步骤验证：

- LLM 可以对同一份路演材料输出15个观测点的证据判断。
- 每个观测点都有 `evidenceLevel`。
- 每个观测点都有至少一个证据锚点，若没有则必须显式标记为 E0。
- 输出 JSON 能被后端 validator 校验。

#### 5.2.2 限制 LLM 不直接决定最终分

Prompt 中明确约束：

- 不输出最终总分。
- 不自由给维度分。
- 可以输出建议扣分项。
- 可以输出建议评分上限。
- 最终分数由规则引擎计算。

小步骤验证：

- LLM 输出中不再出现直接可用的最终总分字段。
- 若模型输出总分，解析层应忽略该字段。
- 规则引擎输入只接收证据、上限、扣分项和追回分。

#### 5.2.3 建立证据锚点映射

所有证据必须映射到：

- ASR 片段
- 视频帧
- OCR/PPT 内容
- 上传材料页码
- 融合时间线
- 历史扣分项

小步骤验证：

- 报告中的每个核心结论能点回证据来源。
- 观测点扣分项能绑定证据锚点。
- 证据锚点缺失时不能进入中高分档。

#### 5.2.4 增加证据抽取质量检查

检查项包括：

- 15个观测点是否齐全。
- 是否存在无来源主张。
- 是否存在证据等级与证据内容不匹配。
- 是否存在 E4/E5 但没有场景验证或独立证明。
- 是否存在高置信度但证据为空。

小步骤验证：

- 构造无证据样本，系统应大量输出 E0/E1。
- 构造有内部数据但无第三方证明样本，系统不应输出 E5。
- 构造只有口号的样本，系统不得给出高证据等级。

### 5.3 大步骤验证

阶段二完成时必须满足：

1. LLM 可以稳定输出结构化证据抽取结果。
2. LLM 不再作为最终分数裁决者。
3. 每个观测点都有证据等级、置信度、证据锚点和缺失证据。
4. 证据抽取失败时，系统进入明确失败态或降级态，不生成伪高质量报告。
5. 现有报告生成仍可兼容读取新结构。

## 六、阶段三：规则引擎接管观测点分数

### 6.1 大步骤目标

让规则引擎根据证据等级、评分上限、扣分项和追回分计算每个观测点分数，并汇总维度分和总分。

### 6.2 小步骤

#### 6.2.1 扩展规则引擎输入

规则引擎输入应包含：

- 评分会话 ID
- 赛道规则版本
- 15个观测点证据结果
- 证据等级
- 评分上限
- 扣分项
- 历史追回分候选
- 当前有效补证结果

小步骤验证：

- `AiScoreStructuredResultValidator` 能校验新输入。
- 每个 observation 都必须有 `observationCode`、`evidenceLevel`、`confidence`、`scoreCap`。
- 无证据观测点不能绕过校验。

#### 6.2.2 实现观测点得分公式

建议公式：

```text
observationFinalScore = min(scoreCap, baseScore - activeDeductions + verifiedRecoveries)
```

其中：

- `scoreCap` 来自证据等级和赛道规则。
- `baseScore` 可由证据等级档位、完整度和置信度计算。
- `activeDeductions` 来自当前证据缺口。
- `verifiedRecoveries` 来自已验收的历史修复。

小步骤验证：

- E0 观测点最高不超过该点20%。
- E1 观测点最高不超过该点30%。
- E2 观测点最高不超过该点50%。
- E3 观测点最高不超过该点70%。
- E4 观测点最高不超过该点85%。
- E5 才允许进入高分档。
- 追回分不能突破当前证据上限。

#### 6.2.3 汇总维度分与总分

按官方结构汇总：

- 技能水平 60
- 职业素养 10
- 应用价值 10
- 团队合作 10
- 创新创意 10

小步骤验证：

- 总分必须等于15个观测点分数之和。
- 每个维度分必须等于该维度观测点分数之和。
- 分数保留两位小数。
- 任意观测点不得超过自身满分。
- 任意维度不得超过官方满分。

#### 6.2.4 保留旧 LLM 分数作为影子对照

在灰度期保留：

- `llm_raw_score`
- `rule_engine_score`
- `score_diff`
- `diff_reasons`

小步骤验证：

- 同一报告能看到旧 LLM 分和新规则引擎分的差异。
- 差异超过阈值时生成复核提示。
- 旧前端页面不因新增字段崩溃。

### 6.3 大步骤验证

阶段三完成时必须满足：

1. 人工智能赛道和新一代信息技术赛道可由规则引擎计算总分。
2. 分数不再依赖 LLM 自由输出。
3. 15个观测点分数可追溯、可复算。
4. 同一输入、同一规则版本、同一证据快照应返回同一规则引擎分。
5. 旧评分结果与新规则引擎结果可并行对照。

## 七、阶段四：报告与前端展示改造

### 7.1 大步骤目标

让用户看到的不只是“AI给了多少分”，而是“系统为什么给这个分、证据在哪里、怎么补回来”。

### 7.2 小步骤

#### 7.2.1 改造报告数据结构

报告应展示：

- 总分
- 维度分
- 15个观测点分
- 证据等级
- 评分上限
- 命中证据
- 缺失证据
- 扣分项
- 可追回分
- 下一轮训练任务

小步骤验证：

- 每个观测点卡片都能展示证据等级。
- 每个扣分项都能展示 requiredFix 和 acceptanceCriteria。
- 每个高分限制都能解释来源。

#### 7.2.2 增加“为什么不是满分”视图

该视图用于回答：

- 哪些观测点被证据等级封顶？
- 哪些扣分项正在生效？
- 哪些历史问题已修复？
- 哪些问题仍未达到验收条件？

小步骤验证：

- 用户能清楚看到总分不是100的原因。
- 追回分与扣分项一一对应。
- 不允许出现“泛泛建议”，每条建议都有验收标准。

#### 7.2.3 增加证据链视图

证据链按观测点组织：

```text
观测点 -> 主张 -> 证据 -> 证据等级 -> 扣分/加分影响
```

小步骤验证：

- 点开一个观测点能看到对应转写片段、关键帧或材料来源。
- 无证据项要明确显示“当前无可核验证据”。
- 证据不充分项要说明缺哪类证据。

#### 7.2.4 兼容旧报告

旧报告没有完整证据等级时，前端应显示：

- 历史评分结果
- 旧评分模式标识
- 不强行显示新结构字段

小步骤验证：

- 历史报告页面可正常打开。
- 新旧报告列表不混乱。
- 旧报告不参与新规则引擎复算，除非用户主动重新评分。

### 7.3 大步骤验证

阶段四完成时必须满足：

1. 用户能看懂分数来源。
2. 用户能看懂扣分项和补证任务。
3. 用户能看到证据链，而不是只看到自然语言评价。
4. 新旧报告兼容。
5. PDF 和用户端页面均能展示核心新字段。

## 八、阶段五：AI评审团改造为争议复核层

### 8.1 大步骤目标

评审团不再重复完整自由评分，而是围绕规则引擎结果进行争议复核。

### 8.2 小步骤

#### 8.2.1 调整评审团输入

评审团输入应包含：

- 规则引擎分数
- 观测点证据等级
- 证据锚点
- 扣分项
- 高分封顶原因
- LLM 原始抽取结果
- 规则引擎与旧 LLM 分差异

小步骤验证：

- 评审团成员能看到规则引擎结果。
- 评审团不能直接覆盖最终分。
- 评审团输出只能产生复核意见、争议点、人工复核建议。

#### 8.2.2 评审团输出改造

评审团输出应聚焦：

- 证据等级是否过高或过低。
- 扣分项是否合理。
- 是否存在证据误配。
- 哪些观测点争议最大。
- 哪些问题需要人工复核。

小步骤验证：

- 评审团报告中减少重复评分，增加争议解释。
- 评审团能指出“可能误判的证据等级”。
- 评审团能生成面向教师/教练的复核建议。

#### 8.2.3 建立争议阈值

触发复核的情况：

- 规则引擎分与旧 LLM 分差异超过10分。
- 单个观测点证据等级为 E4/E5 但证据锚点少于要求。
- 多个评审团成员认为扣分过重或过轻。
- 同一证据被绑定到多个不相关观测点。
- 关键证据来自低置信度 OCR 或低质量 ASR。

小步骤验证：

- 构造高分差样本，系统能触发复核。
- 构造证据误配样本，系统能标记风险。
- 构造低置信度证据样本，系统能降低置信度或触发人工复核。

### 8.3 大步骤验证

阶段五完成时必须满足：

1. 评审团定位从“再打一遍分”变成“复核争议”。
2. 评审团不破坏规则引擎最终分。
3. 评审团能提高报告可信度和训练价值。
4. 争议点可以进入后台复核任务或训练任务。

## 九、阶段六：历史记忆、扣分追回与训练闭环

### 9.1 大步骤目标

把评分结果变成可持续训练循环。系统不仅告诉用户本轮扣了什么，还要在下一轮判断是否修复，并按规则返还分数。

### 9.2 小步骤

#### 9.2.1 结构化保存扣分项

每个扣分项保存：

- `deductionId`
- `sessionId`
- `trackId`
- `observationCode`
- `reason`
- `deductedPoints`
- `requiredFix`
- `acceptanceCriteria`
- `maxRecoverablePoints`
- `evidenceAnchorIds`
- `status`

小步骤验证：

- 每个扣分项都有唯一 ID。
- 每个扣分项能追溯到观测点。
- 每个扣分项能追溯到证据缺口。

#### 9.2.2 下一轮评分自动匹配历史扣分

下一轮评分时系统应检查：

- 是否补充了要求的证据。
- 是否满足验收标准。
- 是否允许返还部分或全部分数。
- 是否仍受当前证据等级上限限制。

小步骤验证：

- 已补证样本能产生 `verifiedRecoveries`。
- 未补证样本不能追回分。
- 补证不足样本只能部分追回或不追回。
- 追回分不能超过原扣分。

#### 9.2.3 生成训练任务

每个训练任务包含：

- 任务标题
- 对应扣分项
- 训练动作
- 负责人角色
- 时间建议
- 验收标准
- 预期提升分

小步骤验证：

- 每个 P0 问题都有训练任务。
- 训练任务不能只写“优化表达”“加强展示”。
- 训练任务必须能被下一轮系统验收。

### 9.3 大步骤验证

阶段六完成时必须满足：

1. 扣分项可以跨轮次追踪。
2. 下一轮评分能判断是否修复。
3. 分数追回有证据、有上限、有记录。
4. 系统形成 Loop Engineering 闭环：评分、扣分、训练、补证、复评、追回。

## 十、阶段七：稳定性评测与人工样本校准

### 10.1 大步骤目标

用真实样本证明新流水线比旧流水线更稳定、更可解释、更接近专家评分。

### 10.2 小步骤

#### 10.2.1 建立试点评测集

首批至少准备：

- 人工智能赛道样本 20-50 条。
- 新一代信息技术赛道样本 20-50 条。
- 每条样本包含视频、转写、材料、人工参考分、人工扣分说明。
- 每个赛道必须覆盖高分、中分、低分、证据不足、现场演示失败、材料充分、口号包装、争议边界等样本类型。

小步骤验证：

- 每条样本都能完整跑通新流水线。
- 每条样本都有人工参考分。
- 每条样本都有至少一个可核验证据点。
- 每个赛道不得只使用高质量样本，必须包含失败样本和低证据样本。
- 样本必须冻结输入文件、证据快照、规则版本和人工参考结果。

#### 10.2.2 做同输入多次复评

同一输入连续跑3次，比较：

- 总分波动
- 维度分波动
- 观测点波动
- 证据等级波动
- 扣分项一致性
- 证据引用一致性

小步骤验证：

- 规则引擎最终分在同一证据快照下必须一致。
- LLM 证据抽取如有波动，应通过证据快照锁定和规则引擎稳定最终分。
- 波动超过阈值的样本进入问题清单。
- 同一证据快照下规则引擎总分波动必须为0。
- 同一证据快照下维度分波动必须为0。
- LLM 证据抽取波动不得导致正式分波动。

#### 10.2.3 和旧流水线对比

对比指标：

- 总分稳定性
- 观测点可解释性
- 证据引用准确率
- 人工专家分差
- 报告可追问程度
- 训练任务可执行性
- 低证据高分拦截率
- E4/E5 硬条件违规率
- 人工复核触发准确性

小步骤验证：

- 新流水线总分波动低于旧流水线。
- 新流水线能解释每个观测点分数。
- 新流水线能指出旧流水线高分但证据不足的情况。
- 新流水线必须拦截“只有口号但高分”的样本。
- E4/E5 违规样本必须被降级或触发复核。

#### 10.2.4 建立专家校准机制

专家可以标记：

- 证据等级判高。
- 证据等级判低。
- 扣分过重。
- 扣分过轻。
- 证据绑定错误。
- 规则需要调整。

小步骤验证：

- 专家修正可以记录到样本库。
- 修正结果不直接污染历史报告。
- 修正结果可以用于下一版规则优化。
- 专家修正必须记录修正人、修正时间、修正理由、影响观测点和规则版本。
- 专家修正必须区分“样本标注修正”和“规则变更建议”。

#### 10.2.5 建立评分质量报告

每轮评测必须生成评分质量报告，报告至少包含：

- 样本数量和赛道分布。
- 总分 MAE、维度分 MAE、观测点误差分布。
- 证据等级准确率。
- 扣分项一致率。
- 证据锚点准确率。
- JSON 解析失败率。
- 降级态和人工复核触发数量。
- 新旧流水线分差分布。
- 不达标样本清单和原因。

小步骤验证：

- 质量报告能定位到具体样本、具体观测点和具体规则版本。
- 未达标指标必须生成整改任务。
- 质量报告必须作为是否进入下一阶段的依据。

### 10.3 大步骤验证

阶段七完成时必须满足：

1. 有可重复运行的试点评测集。
2. 有新旧流水线对比报告。
3. 有人工专家校准入口或校准记录表。
4. 能证明规则引擎主导方案比旧方案更稳定。
5. 能明确哪些问题阻止系统进入更大范围推广。
6. 试点赛道达到 2.5.4 定义的试点准入标准。
7. 每轮评测都有评分质量报告。
8. 未达标指标有明确整改归属和复测要求。

## 十一、阶段八：从2个赛道扩展到42个赛道

### 11.1 大步骤目标

首批两个赛道稳定后，必须扩展到全部42个赛道，形成完整的赛道化证据评分系统。

### 11.2 扩展前置条件

只有满足以下条件，才允许从2个试点赛道扩展：

1. 两个试点赛道的规则引擎分数稳定。
2. 同一证据快照下复评分数一致。
3. 每个观测点都有证据等级和证据锚点。
4. 报告可解释“为什么不是满分”。
5. 扣分追回闭环可运行。
6. 评审团争议复核不破坏主评分。
7. 新旧流水线对比完成。
8. 两个试点赛道都达到 2.5.4 试点准入标准。
9. 两个试点赛道的规则准入审计结论为可进入 `active`。
10. 失败态、降级态、人工复核态在前端和后台均可见。

### 11.3 扩展批次建议

#### 第一批：技术类赛道

建议扩展：

- 人工智能赛道
- 新一代信息技术赛道
- 电子电器与集成电路赛道
- 智能装备应用赛道
- 机械设计与制造赛道
- 机电设备安装与运维赛道

验证重点：

- 技术演示证据。
- 系统运行结果。
- 测试数据。
- 工程复杂度。
- 标准与安全边界。

#### 第二批：工程与制造类赛道

建议扩展：

- 土木建筑设计与管理赛道
- 土木建筑施工赛道
- 水利赛道
- 能源动力赛道
- 材料赛道
- 化工技术赛道
- 汽车制造与维修赛道
- 轨道交通运输赛道
- 航空交通运输赛道
- 船舶交通运输赛道
- 道路与管道运输赛道

验证重点：

- 规范流程。
- 安全风险。
- 工艺过程。
- 设备或工程证据。
- 质量检测结果。

#### 第三批：农林牧渔、生态与资源类赛道

建议扩展：

- 现代农业赛道
- 林业赛道
- 畜牧与水产赛道
- 地质勘察与地理测绘赛道
- 资源开采赛道
- 生态保护与环境治理赛道

验证重点：

- 场景真实性。
- 数据采集。
- 环境或生产证据。
- 可持续性。
- 现场操作和安全。

- 生物技术赛道

- 医药生产与经营赛道
- 医学技术赛道
- 康复治疗与护理赛道

验证重点：

- 合规边界。
- 伦理安全。
- 操作规范。
- 服务对象。
- 风险提示。

#### 第五批：服务、财经、商贸与文体类赛道

### 11.4 每个新赛道的扩展步骤

每扩展一个赛道，都必须执行：

1. 从 v1.2 Markdown 提取结构化规则。
2. 配置15个观测点。
3. 配置 E0-E5 证据上限。
4. 配置可接受证据类型。
5. 配置扣分规则和追回规则。
6. 准备至少5条测试样本。
7. 跑通证据抽取。
8. 跑通规则引擎算分。
9. 生成报告。
10. 做人工抽查。

小步骤验证：

- 新赛道不能只配置赛道名称。
- 新赛道必须有赛道专属证据定义。
- 新赛道必须通过样本测试。
- 新赛道必须能生成扣分项和补证任务。
- 新赛道必须完成规则准入审计表。
- 新赛道必须至少准备10条准入样本，其中至少包含2条低证据样本、2条中等样本、2条高证据样本、1条演示失败或材料缺失样本。
- 新赛道正式 active 前，建议持续积累到30条以上样本。
- 新赛道不得把通用观测点文案直接复制为赛道专属规则，必须补充本赛道岗位任务和证据类型。

### 11.5 42赛道完成验收

全部42赛道完成时必须满足：

1. 每个赛道都有结构化规则文件。
2. 每个赛道都有15个观测点配置。
3. 每个赛道都有证据等级上限。
4. 每个赛道都有至少10条准入样本，并持续积累到30条以上样本。
5. 每个赛道都能完成证据抽取、规则算分、报告生成。
6. 系统可以按赛道自动加载对应规则。
7. 报告能显示当前赛道规则版本。
8. 后台能统计各赛道评分稳定性。
9. 每个赛道都有规则准入审计表。
10. 每个赛道都有人工抽查记录。
11. 每个赛道都能区分官方依据、赛道化推导和 OREP 训练规则。
12. 每个赛道都有至少一轮评分质量报告。

## 十二、灰度上线策略

### 12.1 影子模式

旧流水线继续作为主结果，新规则引擎只生成影子结果。

验证：

- 不影响用户现有评分。
- 新旧结果可以对比。
- 差异可记录。

### 12.2 双结果模式

用户页面展示：

- 当前正式分。
- 规则引擎试算分。
- 差异说明。

验证：

- 用户能理解两种分数差异。
- 教师或管理员可以查看差异原因。
- 差异过大时触发复核。

### 12.3 规则引擎正式接管

当试点赛道稳定后：

- 规则引擎分成为正式分。
- LLM 原始分仅作为参考。
- 评审团只做争议复核。

验证：

- 新报告以规则引擎分为准。
- 历史报告不被自动改写。
- 重新评分才使用新规则。
- 满足 2.5.7 上线准入标准。
- 保留旧流水线回退开关。

### 12.4 灰度范围控制

灰度必须按范围逐步扩大：

1. 内部样本。
2. 管理员可见影子评分。
3. 教师端可见双结果。
4. 试点赛道正式接管。
5. 扩展到更多赛道。

验证：

- 每个灰度阶段都有开始时间、结束时间、负责人、样本量、异常记录。
- 灰度阶段不得跳过质量报告。
- 任何阶段出现 P0 事故必须暂停扩展。

## 十二点五、运维监控、安全权限与审计

规则引擎主导后，系统必须具备持续监控能力。否则即使单次样本跑通，也无法证明长期稳定。

### 12.5.1 评分质量看板

后台至少展示：

- 每赛道评分次数。
- 每赛道平均分、分数分布、异常高分/低分。
- E0-E5 分布。
- 扣分项 Top N。
- 证据锚点缺失率。
- LLM 证据抽取失败率。
- JSON 解析失败率。
- 人工复核触发率。
- 用户申诉率。
- 新旧规则分差分布。
- 规则版本使用分布。

验证：

- 管理员能按赛道、规则版本、时间范围筛选。
- 异常指标能定位到具体 session 和 report。
- 看板数据不依赖手工导表。

### 12.5.2 告警指标

以下情况必须告警：

- 某赛道 JSON 解析失败率超过2%。
- 某赛道证据锚点缺失率超过10%。
- 同一证据快照下出现不同规则引擎分。
- E4/E5 硬条件违规。
- 单日评分失败率超过3%。
- PDF 报告生成失败率超过3%。
- 人工复核触发率异常升高。

验证：

- 告警能记录时间、赛道、规则版本、样本 ID 和错误类型。
- 告警有处理状态：未处理、处理中、已修复、误报。
- 告警必须进入复盘记录。

### 12.5.3 安全、权限与数据保护

评分证据包含视频、语音、团队材料、项目文档、评审结果，必须纳入权限控制。

最低要求：

- 用户只能访问自己或有授权团队的评分报告。
- 教师只能访问其管理范围内团队。
- 管理员操作必须记录审计日志。
- 原始视频、转写、材料下载必须走鉴权接口。
- 对外报告不得泄露 API key、内部路径、模型调用日志。
- 人工复核记录必须记录操作人和修改理由。

验证：

- 未授权用户无法访问报告、证据文件和 PDF。
- 下载接口携带鉴权。
- 审计日志能追踪评分、复核、规则变更、报告下载。

### 12.5.4 规则变更审计

每次规则变更必须记录：

- 变更人。
- 变更时间。
- 变更赛道。
- 变更前后 hash。
- 变更原因。
- 影响观测点。
- 是否需要重跑样本集。
- 是否影响历史报告。

验证：

- 规则变更后必须生成新版本，不覆盖旧版本。
- 历史报告保持旧规则版本。
- 新规则上线前必须通过回归样本。

## 十三、风险与控制

### 13.1 规则过硬导致误伤

风险：优秀项目因为规则没有覆盖而被低估。  
控制：保留人工复核入口和评审团争议复核，规则版本定期校准。

### 13.2 LLM 证据等级误判

风险：LLM 把弱证据判成强证据。  
控制：E4/E5 必须满足硬性证据条件，低证据锚点数量不能进入高等级。

### 13.3 抽帧漏掉关键演示

风险：系统没有看到关键画面，导致低估。  
控制：增加关键帧选择策略，允许用户补充材料或人工标记关键时间段。

### 13.4 旧报告兼容失败

风险：历史报告页面或 PDF 生成异常。  
控制：新旧报告 schema 分离，旧报告只读展示。

### 13.5 42赛道扩展变成形式覆盖

风险：每个赛道只改名字，没有真实赛道化证据规则。  
控制：每赛道必须有专属证据定义、测试样本和人工抽查记录。

## 十四、建议里程碑

### M1：试点规则结构化

周期：1-2周  
范围：人工智能赛道、新一代信息技术赛道  
交付：

- 两个赛道结构化规则。
- 规则 hash。
- 规则加载接口。
- 初步 validator。

验收：

- 两个赛道15个观测点完整。
- 每个观测点有证据等级上限。
- 评分会话能绑定规则版本。
- 两个赛道均通过规则准入审计。
- 每条规则均标记来源类型。

### M2：LLM证据抽取器

周期：2-3周  
交付：

- 主张抽取。
- 证据绑定。
- 证据等级判断。
- 扣分候选。
- 抽取质量检查。

验收：

- 两个赛道样本可输出完整结构化证据。
- 无证据样本不会得到高证据等级。
- 输出能被后端校验。
- JSON 解析成功率达到98%以上。
- 15个观测点完整输出率达到100%。
- 无来源主张进入评分率为0。

### M3：规则引擎影子评分

周期：2-3周  
交付：

- 观测点算分。
- 维度汇总。
- 新旧分数对比。
- 差异原因。

验收：

- 同一证据快照下规则引擎分稳定一致。
- 旧评分流程不受影响。
- 差异超过阈值可触发复核。
- 规则引擎分数一致率达到100%。
- E4/E5 硬条件违规率为0。
- 新旧分差报告可定位到观测点和证据。

### M4：报告与评审团改造

周期：2-3周  
交付：

- 证据链报告。
- 为什么不是满分视图。
- 扣分追回展示。
- 评审团争议复核。

验收：

- 用户能看懂分数来源。
- 评审团不再覆盖最终分。
- 每条训练建议都有验收标准。
- 每个核心扣分项都能回到证据锚点。
- 旧报告页面和 PDF 下载链路不受影响。
- 争议复核输出不直接改写正式分。

### M5：试点稳定与扩展准备

周期：2-4周  
交付：

- 两个赛道评测集。
- 新旧流水线对比报告。
- 专家校准记录。
- 扩展到42赛道的规则模板。

验收：

- 试点赛道稳定。
- 规则引擎分数可复现。
- 明确进入42赛道扩展阶段。
- 两个试点赛道达到 2.5.4 试点准入标准。
- 每个试点赛道至少20条样本完成评测，建议达到50条。
- 评分质量报告显示未达标项均有整改任务。
- 满足 2.5.7 上线准入标准后，才允许正式接管。

### M6：42赛道分批扩展

周期：持续迭代  
交付：

- 全42赛道结构化规则。
- 每赛道测试样本。
- 每赛道证据规则。
- 全赛道评分稳定性看板。

验收：

- 42赛道全部可由规则引擎主导评分。
- 每个赛道都能生成可追溯报告。
- 系统可按赛道自动加载规则。
- 每个赛道都有规则准入审计表。
- 每个赛道至少10条准入样本，长期目标30条以上。
- 每个赛道至少一轮评分质量报告。
- 每个赛道均能显示规则版本、证据 schema 版本和评分指纹。

## 十五、最终完成标准

本改造完成后，OREP AI评分系统应达到以下状态：

1. LLM 不再直接决定最终分。
2. 规则引擎是最终评分裁决者。
3. 每个观测点都有证据等级和评分上限。
4. 每个扣分项都有修复任务和验收标准。
5. 每次评分都有规则版本、证据快照和评分指纹。
6. 同一输入、同一规则、同一证据快照可复现同一分数。
7. 评审团成为争议复核层。
8. 首批两个赛道稳定后，必须扩展到42赛道。
9. 用户能看懂分数、证据、扣分、补证和追回分。
10. 系统从“AI生成评分报告”升级为“证据驱动的竞赛评分基础设施”。
11. 42份 Markdown 规则全部完成结构化转换、规则准入审计和样本验证。
12. 每个赛道都能区分官方依据、赛道化推导和 OREP 训练规则。
13. 规则引擎在同一证据快照下分数一致率达到100%。
14. LLM 证据抽取 JSON 解析成功率成熟目标达到99.5%以上。
15. 无来源主张进入评分率为0。
16. E4/E5 证据硬条件违规率为0。
17. 证据锚点引用准确率成熟目标达到92%以上。
18. 总分相对专家均分 MAE 成熟目标不高于5分。
19. 所有正式规则变更均有版本、hash、变更记录和回归样本结果。
20. 系统具备评分质量看板、异常告警、权限控制和审计日志。
