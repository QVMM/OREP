# OREP AI 生成 PPT 式 HTML

## 前端主路径整改文档

> 目标：把当前前端从“分析平台 + 多工作区并列”继续收口成“任务会话 + 当前页工作台 + 下载前处理流”，重点解决：
>
> - 状态源分散
> - 页面和 store 双向控制
> - tab 太多
> - 动作编排太重
> - 下载流程与普通修复流程混用

---

## 1. 当前前端最核心的问题

## 1.1 `ppt.js` 仍然承担过多职责

当前 [ppt.js](/Users/liuyixing/项目/OREP/frontend/user/src/stores/ppt.js) 同时负责：

- 问卷
- 任务
- 大纲
- 风格
- 生成轮询
- 预览
- 下载
- 恢复

这会导致：

- 旧流程和新流程共存
- 新人难以判断真实主路径
- 状态很难完全一致

## 1.2 `PptEditor.vue` 仍然有双状态源

当前：

- 页面本地维护一套
- store 里维护一套

这会导致：

- 恢复逻辑复杂
- 轮询结果来回同步
- 生成过程容易出现“看起来卡住，其实状态不一致”

## 1.3 `PptHistoryDetail.vue` 虽然拆了组件，但动作编排仍然很重

现在已经拆了很多展示组件和 composable，这是正确方向。  
但仍然存在：

- 下载流程
- 一键修复
- 跳转焦点
- 工作台动作

这些 mutation 编排仍然集中在详情页容器里。

## 1.4 主路径仍然被太多 tab 切碎

当前用户要理解：

- HTML 预览
- 质量报告
- 路演结构
- 评分覆盖
- 实操演示
- 素材证据（高级）
- 总报告
- 终稿总审

这对普通用户过重。

---

## 2. 前端重构目标

## 2.1 建立 `task session` 主模型

前端应该明确：

> 用户现在不是在某个页面里，而是在处理“一个 PPT 任务会话”。

这个会话应统一承载：

- 当前任务
- 当前阶段
- 当前主动作
- 当前优先问题
- 当前下载状态

## 2.2 建立“主视图 + 高级视图”两层结构

### 主视图

- 预览调整
- 下载与交付

### 高级视图

- 质量分析
- 路演结构
- 评分覆盖
- 实操演示
- 素材证据（高级）
- 总报告

让普通用户只围绕主视图工作。

## 2.3 建立“当前页工作台”唯一主动作

对当前页来说，系统应该始终清楚告诉用户：

- 这页当前最该干什么
- 为什么
- 处理完后会发生什么

不要让用户自己在多个按钮里猜。

---

## 3. 第一批重构动作

## 3.1 拆 `ppt.js`

### 目标

按领域拆成多个 store/composable。

### 建议拆分

#### `usePptTaskSessionStore`

负责：

- 当前任务
- 阶段切换
- 轮询
- 恢复
- 下载状态

#### `usePptOutlineEditorStore`

负责：

- 大纲页编辑
- 顺序调整
- 风格选择
- P0 结构检查

#### `usePptPreviewStore`

负责：

- 当前 HTML 页
- 缩放
- 已生成页
- 导出可用性

### 验收标准

- `ppt.js` 不再同时管问卷 + 大纲 + 预览 + 下载

## 3.2 把 `PptEditor` 流程控制抽成 composable

### 目标

页面只负责展示，不再自己承担流程控制。

### 建议新增

#### `usePptGenerationFlow()`

负责：

- 任务创建
- 等待阶段
- 恢复逻辑
- 轮询
- 继续等待 / 先看预览 / 重试

#### `usePptOutlineStep()`

负责：

- Step 1 编辑态
- 大纲页保存
- 风格预览联动

### 验收标准

- `PptEditor.vue` 不再直接维护复杂的轮询/恢复主逻辑

## 3.3 把 `PptHistoryDetail` 的动作层再下沉

### 目标

让详情页真正成为容器，不继续做超级控制器。

### 建议新增

#### `usePptMutationActions()`

负责：

- 一键补评分点
- 一键清占位词
- 一键重做模板页
- 一键处理 P0

#### `usePptDownloadFlow()`

负责：

- 被拦下载
- 先处理并继续下载
- warning 下载当前版
- ready 最终下载

### 验收标准

- `PptHistoryDetail.vue` 不再直接承载下载与修复的主要 mutation 逻辑

---

## 4. 主路径收口方案

## 4.1 预览页成为唯一主工作台

### 当前方向是对的

现在已经在往这条路上走：

- 当前页讲稿
- 当前页补图
- 当前页主动作
- 当前页风险

### 下一步要继续收

1. 当前页补评分点也应尽量内联
2. 当前页修复结果应在右侧立即回显
3. 当前页相关下载建议应直接显示，不强依赖切 tab

## 4.2 素材证据页继续降级

### 目标

让它只剩高级管理意义。

普通用户路径：

- 在 HTML 预览右侧补当前页图

高级用户路径：

- 去素材证据（高级）集中管理

## 4.3 下载条件卡进一步减负

### 目标

下载条件卡负责：

- 决定下一类问题
- 给出进度
- 保持下载语境

不负责：

- 承担所有真实修复动作编排

真实修复动作尽量回当前页工作台。

---

## 5. 交互层收口建议

## 5.1 统一系统语言

用户侧尽量少出现：

- blocker
- route reason
- evidence plan
- template risk
- visual review

改成人话：

- 这页缺图
- 这页像模板
- 这页评分点不够
- 这页需要重做

## 5.2 统一当前语境

系统始终明确用户当前处于：

- 生成中
- 预览调整
- 修复中
- 下载前处理

不要让用户在这些语境中来回跳。

## 5.3 统一“为什么推荐这个动作”

每个主动作上方都应该显示：

- 当前为什么推荐这个动作
- 处理后会解除什么问题

---

## 6. 建议的实施顺序

### 第一优先级

1. 拆 `ppt.js`
2. 抽 `usePptGenerationFlow()`
3. 抽 `usePptDownloadFlow()`

### 第二优先级

4. 顶部 tab 降级成主视图 + 高级视图
5. 当前页补评分点、补图、修复继续内联
6. 下载条件卡进一步减负

### 第三优先级

7. 系统语言继续人话化
8. 高级视图再做减法

---

## 7. 开工建议

如果下一步开始改前端，我建议先不要再加新交互，先做：

1. `ppt.js` 拆分
2. `PptEditor` 流程控制抽离
3. `PptHistoryDetail` mutation/download flow 抽离

因为这三件事决定后面继续迭代时，前端是：

- 越做越顺

还是：

- 继续把复杂度摊开但不消化
