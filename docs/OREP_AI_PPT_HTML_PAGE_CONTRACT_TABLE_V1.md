# OREP AI 生成 PPT 式 HTML

## 页面契约表 V1

> 目标：把“这一页应该长成什么样”从隐性经验，升级成系统可以执行的显性规则。

> 这份文档是后续 4 类工作的统一基础：
>
> 1. Round 2 / Round 3 的页面策划
> 2. Round 4 的 HTML 生成
> 3. 单页重设计（Single-page Redesign）
> 4. 视觉审查与交付门禁

---

## 1. 什么是页面契约

页面契约不是“页面模板”那么简单。

它的本质是：

> **明确这一页在比赛路演中承担什么职责、必须回答什么问题、必须以什么信息结构出现、必须如何承载证据、哪些结构绝对不允许出现。**

页面契约要解决的，就是现在系统最常见的几个问题：

- 页面像网页，不像 PPT
- 页面有内容，但没有主焦点
- 页面逻辑没错，但没有路演感
- 页面修很多次，还是回到模板化
- 页面缺图后只能事后硬塞

换句话说，页面契约的作用是：

> 让系统在“生成前”就知道一页应该怎么长，而不是等“生成后”才不断补救。

## 2. 页面契约的统一字段结构

每个页面契约至少应该包含下面这些字段。

## 2.1 基础字段

| 字段 | 含义 |
|---|---|
| `contract_id` | 契约唯一标识 |
| `page_type` | 页面类型 |
| `act_phase` | 章节所属幕次 |
| `page_goal` | 这一页最核心的任务 |
| `transition_role` | 与前后页的承接关系 |
| `served_scoring_dimensions` | 主要服务的评分项 |
| `must_answer` | 这一页必须回答的关键问题 |

## 2.2 内容结构字段

| 字段 | 含义 |
|---|---|
| `required_blocks` | 必须出现的内容块 |
| `optional_blocks` | 可选内容块 |
| `forbidden_blocks` | 禁止出现的内容块 |
| `max_key_messages` | 主结论数量上限 |
| `max_support_points` | 支撑点数量上限 |
| `tone` | 表达语气 |

## 2.3 视觉结构字段

| 字段 | 含义 |
|---|---|
| `primary_visual_type` | 主视觉类型 |
| `max_primary_visuals` | 主视觉数量上限 |
| `layout_intent` | 版式意图 |
| `density_level` | 信息密度等级 |
| `visual_focus_rule` | 焦点规则 |
| `whitespace_rule` | 留白规则 |

## 2.4 证据字段

| 字段 | 含义 |
|---|---|
| `evidence_priority` | 是否证据优先 |
| `required_evidence_types` | 所需证据类型 |
| `evidence_slot_count` | 最少证据槽位数量 |
| `evidence_position_rule` | 证据位置规则 |
| `fallback_when_missing_evidence` | 证据缺失时允许的降级方案 |

## 2.5 质量与修复字段

| 字段 | 含义 |
|---|---|
| `common_failure_modes` | 典型失败模式 |
| `repair_strategy_hint` | 推荐修复策略 |
| `delivery_gate_level` | 与交付门禁关系 |

## 3. 比赛路演的四幕结构映射

为了让页面契约不只是单页规则，而是服务整套比赛叙事，先定义四幕。

## 3.1 第一幕：立题

目标：

- 建立问题感
- 建立项目可信度
- 让评委知道这件事值得听

典型页：

- 封面页
- 目录/赛程页
- 政策背景页
- 项目定义页
- 痛点总览页

## 3.2 第二幕：立解法

目标：

- 让评委知道方案是完整的
- 建立“问题 -> 方案”的逻辑闭环

典型页：

- 痛点深挖页
- 方案总览页
- 价值闭环页
- 技术架构总览页

## 3.3 第三幕：立能力

目标：

- 让评委相信团队真的做出来了
- 展示技术难度、实操能力、工程规范

典型页：

- 核心技术页
- 实操步骤页
- 结果证据页
- 异常处理页
- 安全与规范页

## 3.4 第四幕：立价值与收束

目标：

- 建立应用价值、创新点和团队印象
- 完成收束

典型页：

- 创新点页
- 应用价值页
- 团队分工页
- 总结收束页

## 4. 页面契约总表 V1

当前建议先固化 10 类页面契约。

## 4.1 封面页契约

### 核心定义

| 字段 | 内容 |
|---|---|
| `contract_id` | `cover_opening_v1` |
| `page_type` | 封面页 |
| `act_phase` | 第一幕：立题 |
| `page_goal` | 用 5 秒建立项目身份、专业度和开场气质 |
| `served_scoring_dimensions` | 讲解效果、团队形象 |

### 必须回答

- 这是什么项目
- 这个项目属于什么方向
- 团队/学校/赛项身份是什么

### 必须块

- 项目名称
- 一句话定位
- 团队/学校/赛项信息

### 禁止块

- 复杂流程图
- 多组并列卡片
- 大段说明文字

### 视觉规则

- `primary_visual_type`: 大标题 + 氛围背景
- `max_primary_visuals`: 1
- 标题必须是唯一焦点
- 不允许同时出现多个大数字、大卡片争抢焦点

### 证据规则

- 不要求证据优先
- 允许无证据

### 常见失败模式

- 像网页首页 hero banner
- 卡片堆太多
- 项目名不够突出

### 修复策略

- `structure_rebuild`

## 4.2 目录 / 赛程页契约

### 核心定义

| 字段 | 内容 |
|---|---|
| `contract_id` | `agenda_timeline_v1` |
| `page_type` | 目录 / 赛程页 |
| `act_phase` | 第一幕：立题 |
| `page_goal` | 让评委在一眼内理解 60 分钟的整体结构 |
| `served_scoring_dimensions` | 讲解效果 |

### 必须回答

- 今天这 60 分钟怎么分配
- 哪些环节是汇报，哪些环节是实操

### 必须块

- 章节列表
- 时间分配
- 汇报 / 实操分段

### 禁止块

- 长段落说明
- 无时间信息的普通目录

### 视觉规则

- `primary_visual_type`: 时间结构 / 进程条 / 章节时间轴
- 必须有整体时间感
- 不允许只是一列普通目录文本

### 证据规则

- 不要求证据位

### 常见失败模式

- 变成普通目录页
- 没有 60 分钟时间结构

### 修复策略

- `structure_rebuild`

## 4.3 政策 / 背景证据页契约

### 核心定义

| 字段 | 内容 |
|---|---|
| `contract_id` | `policy_context_evidence_v1` |
| `page_type` | 政策 / 背景证据页 |
| `act_phase` | 第一幕：立题 |
| `page_goal` | 用真实政策或行业背景证明项目“有必要做” |
| `served_scoring_dimensions` | 应用价值、讲解效果 |

### 必须回答

- 为什么这件事符合政策 / 行业趋势
- 项目与国家/地方方向如何对齐

### 必须块

- 政策/背景结论
- 证据图或证据截图
- 来源说明

### 禁止块

- 只有纯文字没有证据
- 只有截图没有结论

### 视觉规则

- `primary_visual_type`: 政策截图 / 行业证据图
- `max_primary_visuals`: 1
- 页面应围绕证据解释，不应反过来

### 证据规则

- `evidence_priority`: 高
- `required_evidence_types`: 政策截图 / 官方来源 / 行业图表
- `evidence_slot_count`: 至少 1
- 测试阶段允许临时演示图，但正式版必须有真实来源信息

### 常见失败模式

- 待补充/待核实进入正文
- 没有来源
- 证据图很小，文字太多

### 修复策略

- `evidence_attach_or_wait`

### 必须回答

- 项目是什么

### 必须块

### 视觉规则

- `primary_visual_type`: 核心定义卡 / 中心结论
- 不允许页面被大量并列信息稀释

### 证据规则

- 证据可选

### 常见失败模式

- 页面太空但没有主结论重量
- 变成普通介绍页

### 修复策略

- `structure_rebuild`

| `page_type` | 痛点洞察页 |
| `act_phase` | 第一幕 / 第二幕过渡 |
| `page_goal` | 让评委相信问题真实存在，而且值得解决 |
| `served_scoring_dimensions` | 应用价值、讲解效果 |

### 证据规则

- 建议有图表或现象证据

### 常见失败模式

## 5. 页面契约如何接入系统

## 5.1 Round 2 接入

Round 2 不只输出 `outline pages`，还要输出：

- `page_type`
- `act_phase`
- `transition_role`
- `served_scoring_dimensions`

## 5.2 Round 3 接入

Round 3 要围绕契约输出页面设计元数据：

- `page_goal`
- `must_answer`
- `required_blocks`
- `primary_visual_type`
- `required_evidence_types`

## 5.3 Round 4 接入

Round 4 不自由生成页面，而是：

- 依据页面契约渲染 HTML
- 若契约要求证据优先，则版式先留证据位

## 5.4 修复系统接入

修复阶段优先读取页面契约，决定：

- 是 HTML polish
- 还是 structure rebuild
- 还是 evidence attach

## 5.5 视觉审查接入

视觉审查不仅判断页面问题，还要比对：

- 是否违反了该契约的焦点规则
- 是否违反了证据位规则
- 是否违反了内容密度规则

---

## 6. 第一批最值得落地的契约

如果第一批不能一次做完全部 10 类，我建议先做这 6 类：

1. 目录 / 赛程页
2. 政策 / 背景证据页
3. 方案总览 / 价值闭环页
4. 技术架构 / 核心技术页
5. 实操步骤页
6. 团队 / 总结收束页

原因：

- 这 6 类最能直接解决“比赛味不够、PPT 味不够、HTML 味太重”的问题

## 7. 实施顺序建议

### 第一步

先把这份契约表变成一份机器可读结构：

- JSON / YAML / Python dict

### 第二步

把 Round 2 / 3 / 4 的 prompt 和 service 逻辑接上这些字段

### 第三步

让视觉审查和单页重设计也读取同一份契约

### 第四步

基于这份契约再去做“页系样张”

## 8. 最终原则

这份页面契约表 V1 的核心原则只有一句：

> 不是让模型“自由发挥去做一页 PPT”，而是先告诉系统“这页在比赛里到底该怎么长、该回答什么、该突出什么、该证明什么”，再让模型去生成。

只有先把这件事定清楚，后面的：

- prompt
- html generator
- visual review
- repair
- scoring
- deliverability

才会真正围绕“专业路演页”而不是“普通 HTML 页”来工作。
