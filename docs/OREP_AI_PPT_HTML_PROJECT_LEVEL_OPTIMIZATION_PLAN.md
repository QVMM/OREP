# OREP AI 生成 PPT 式 HTML 项目级功能优化方案

版本：v1.0  
日期：2026-04-20  
适用对象：OREP 产品、前端、后端、AI/Pipeline、数据平台、测试团队  
目标场景：职业院校技能大赛 60 分钟“项目路演 + 技术实操”备赛与交付

---

## 1. 文档目标

本方案不是针对某一份 HTML 成品做页面修修补补，而是针对 OREP 当前“AI 生成 PPT 式 HTML”这一整套功能，提出项目级、系统级的优化设计。

本方案要解决的问题是：

1. 为什么系统已经能生成 HTML，但仍然经常无法直接拿去比赛。
2. 如何把当前功能从“AI 出一套页面”升级成“可稳定交付比赛级路演作品”的产品能力。
3. 产品、后端、数据库、前端、研发节奏分别应该如何调整。

最终目标不是做一个普通 AI PPT 工具，而是做一个：

- 面向职业院校技能大赛的路演作品生产系统
- 以评分标准为约束的比赛级内容生成系统
- 可审查、可修复、可追溯、可持续优化的工程化能力

---

## 2. 现状判断

### 2.1 当前系统已有能力

当前 OREP 已经具备以下基础闭环：

1. 用户提交问卷或 JSON 项目资料。
2. 后端通过 Round1/2/3/4 多阶段 Pipeline 完成结构化、大纲、内容、HTML 生成。
3. 前端支持大纲确认、预览、重试、部分状态恢复。
4. 后端已初步具备质量检查、视觉审查、单页修复、风格预览、多模型切换等能力。
5. 系统已经能够生成一套“可浏览、可导出、可继续修”的 HTML 路演稿。

### 2.2 当前系统的核心短板

当前短板不再是“能不能生成”，而是“生成结果是否真的适合比赛直接使用”。

主要问题有五类：

1. 输入问题：资料完整度不稳定，系统过去要么误杀，要么带病生成。
2. 结构问题：故事线有时像商业 BP，有时像技术说明书，不够稳定对齐比赛。
3. 证据问题：政策、数据、实操、团队协作等页面常缺真实证据链。
4. 质量问题：模板页、占位词、跨行业语义污染、视觉焦点不足等问题仍会漏出。
5. 交付问题：用户看到的是“生成了一套页面”，而不是“这套材料已经达到比赛可交付标准”。

### 2.3 功能升级的核心判断

OREP 下一阶段不应该继续停留在“优化 prompt，让 AI 写得更好”。

应该升级为：

```text
输入资料
→ 资料体检
→ 比赛导向策划
→ 页面级评分点绑定
→ 页面级证据绑定
→ HTML 生成
→ 质量门禁
→ 单页修复
→ 用户精修
→ 比赛交付
```

也就是说，系统需要从“生成器”升级成“路演作品生产链”。

## 3. 产品方案

### 3.1 产品定位升级

当前定位：

- AI 生成 PPT 式 HTML

建议升级后的定位：

- 面向职业院校技能大赛的比赛级路演作品生成与打磨系统

这意味着产品必须同时服务两个目标：

1. 帮用户快速生成初稿。
2. 帮用户把初稿打磨成真正能上赛场的最终稿。

### 3.2 产品核心模块重构

建议把整条产品链路拆成 8 个模块：

#### M1. 资料体检

目标：

- 在生成前判断用户资料是否足以支撑比赛级路演。

输出：

- 完整度分数
- 六维体检报告
- 缺失项列表
- 风险提示
- 推荐补充素材清单

用户动作：

- 补充后再生成
- 先生成草稿

#### M2. 比赛策划

目标：

- 把自由资料转换成比赛导向故事线，而不是直接吐大纲。

输出：

- 60 分钟时间结构
- 章节划分
- 页面职责
- 每页讲述目标
- 每页评分点映射

#### M3. 证据规划

目标：

- 在页面生成前就明确“这页需要什么证据”。

输出：

- 政策页所需证据
- 技术页所需证据
- 实操页所需证据
- 团队与规范页所需证据

#### M4. 页面生成

目标：

- 生成的不只是文案，而是“可比赛展示的页面元数据 + HTML”。

输出：

- 页面标题
- 内容要点
- 讲稿
- 视觉焦点
- 布局类型
- HTML 页面

#### M5. 质量门禁

目标：

- 页面生成后先审，再交付。

门禁内容：

- 占位词/待补充
- 评分点覆盖
- 页面结构完整性
- 行业语义一致性
- 视觉风险
- 证据缺失

#### M6. 单页修复

目标：

- 某一页有问题时不重跑整套，只修这页。

支持：

- 单页 HTML 修复
- 单页内容重生成
- 单页证据替换
- 单页讲稿重写

#### M7. 用户精修台

目标：

- 让用户能看懂每页风险、评分点、证据需求，并手动微调。

支持：

- 讲稿编辑
- 页面排序
- 证据替换
- 单页重生成
- 风险清单查看

#### M8. 最终交付

目标：

- 输出“可参赛版本”，而不是单纯“生成完成版本”。

交付标准：

- 通过质量门禁
- 通过证据检查
- 无占位词
- 无跨行业污染
- 可预览、可讲解、可导出

### 3.3 产品成功标准

产品层面建议使用以下北极星指标：

1. 比赛可交付率：生成结果中通过质量门禁并可直接用于路演的任务比例。
2. 单页修复成功率：问题页修复后通过复检的比例。
3. 资料体检采纳率：用户看到体检报告后主动补资料的比例。
4. 证据完备率：关键页面中含真实证据素材的比例。
5. 用户最终采纳率：用户导出/使用最终 HTML 或 PPTX 的比例。

## 4. 后端架构方案

### 4.1 架构升级目标

后端要从“多阶段 AI 调用器”升级成“可控的比赛作品生成引擎”。

建议架构分为 7 层：

```text
输入层
→ 理解层
→ 策划层
→ 内容层
→ 渲染层
→ 审查层
→ 修复层
```

### 4.2 输入层

职责：

- 接收问卷、JSON、素材、历史任务恢复数据。
- 做字段归一化、空值清洗、格式转换。

建议增加：

- 输入标准化器
- 行业词表归一化器
- 用户资料版本号
- 素材接入入口

### 4.3 理解层

职责：

- 将输入数据转换为统一的项目画像。

建议统一输出 `project_profile`：

```json
{
  "project": {},
  "industry": {},
  "team": {},
  "technology": {},
  "evidence": {},
  "competition": {},
  "readiness": {}
}
```

建议新增能力：

1. 行业语义一致性检查
2. 核心字段识别
3. 禁混词检测
4. 资料完整度评估

### 4.4 策划层

职责：

- 先策划，再生成。

建议从当前大纲生成中进一步拆出：

1. 比赛故事线规划器
2. 页面职责规划器
3. 页面评分点规划器
4. 页面证据需求规划器
5. 页面视觉类型规划器

每页建议新增以下元数据：

```json
{
  "page_role": "policy_context",
  "story_goal": "建立政策依据与行业必要性",
  "primary_scoring_dimension": "应用价值",
  "secondary_scoring_dimensions": ["现场讲解效果"],
  "required_evidence_types": ["policy_screenshot", "official_source"],
  "visual_type": "policy_board"
}
```

### 4.5 内容层

职责：

- 生成页面内容元数据，而不是只生成自然语言。

建议 Round3 输出结构至少包含：

- title
- section
- page_role
- core_argument
- content_points
- speaker_script
- evidence_requirements
- visual_focus
- risk_flags

要求：

- 页面必须有比赛目的
- 页面必须有评分服务对象
- 页面必须有证据需求

### 4.6 渲染层

职责：

- 按页面类型渲染成 HTML，而不是自由生成任意页面。

建议建立页面类型契约库：

1. `cover`
2. `agenda`
3. `policy_context`
4. `project_definition`
5. `pain_solution`
6. `technical_architecture`
7. `practice_demo`
8. `evidence_board`
9. `application_value`
10. `innovation`
11. `rd_timeline`
12. `industry_education`
13. `team_collaboration`
14. `closing`

每种契约定义：

- 必要区域
- 最低内容数量
- 允许的视觉组件
- 字号下限
- 安全区要求

### 4.7 审查层

这是后端最关键的一层，建议建立“多门禁审查体系”。

#### A. 文本门禁

检查：

- 是否含占位词
- 是否含待补充/待核实
- 是否含跨行业污染
- 是否含无意义模板句

#### B. 结构门禁

检查：

- 是否有目录
- 是否有政策页
- 是否有痛点-方案闭环
- 是否有实操页
- 是否有应用价值/创新/团队页

#### C. 评分门禁

检查：

- 5 大评分指标是否都有强支撑页
- 是否存在某项评分覆盖明显不足

#### D. 视觉门禁

检查：

- 是否拥挤
- 是否空洞
- 是否重叠
- 是否无焦点
- 是否超出 16:9 安全区

#### E. 证据门禁

检查：

- 政策页是否有政策证据
- 技术页是否有技术证据
- 实操页是否有实操证据
- 团队页是否有协作/职责证据

### 4.8 修复层

建议固定闭环：

```text
HTML 页面
→ 截图渲染
→ 视觉检察官输出 JSON 问题
→ 修复模型按 repair_context 修单页
→ 再审查
→ 通过后替换
```

建议修复优先级：

1. 占位词/错误内容
2. 跨行业污染
3. 模板页
4. 视觉错位/空洞
5. 证据缺失提示

### 4.9 多模型角色建议

建议模型职责分离：

1. 策划模型：负责理解、结构、评分映射
2. 页面模型：负责内容元数据与 HTML 生成
3. 视觉检察官：负责审查截图并输出严格 JSON
4. 修复模型：负责按问题 JSON 修单页 HTML

不建议让一个模型从头写到尾。

## 6. 前端交互方案

### 6.1 前端角色升级

前端不应只承担“展示和轮询”角色，而应成为“用户理解生成质量、介入修复、控制最终交付”的工作台。

### 6.2 推荐交互链路

建议把用户生成链路改造成 7 步：

1. 填写/导入资料
2. 资料完整度体检
3. 确认比赛故事线
4. 选择视觉风格
5. 生成并审查 HTML
6. 单页修复与讲稿调整
7. 最终交付确认

### 6.3 核心交互模块

#### A. 资料体检弹窗/面板

应展示：

- 完整度总分
- 六维评分卡
- 必补项
- 建议项
- 对比赛评分的影响

用户动作：

- 返回补充
- 先生成草稿

#### B. 生成流程看板

建议替换单一进度条，显示：

- 资料体检
- 大纲策划
- 内容生成
- 证据绑定
- HTML 生成
- 质量审查
- 单页修复
- 最终完成

#### C. 页面工作台

每页至少展示：

- 页面截图/预览
- 页面标题
- 页面类型
- 主评分点
- 风险标签
- 证据需求
- 讲稿区

#### D. 讲稿区

建议在预览调整页固定显示当前页讲稿。

支持：

- 手动编辑讲稿
- 自动重写讲稿
- 切换“精简版 / 评委版 / 选手提示版”

#### E. 风险面板

集中展示：

- 哪些页缺证据
- 哪些页是模板页
- 哪些页视觉风险高
- 哪些页评分支撑弱

#### F. 单页操作

每页支持：

- 重新生成内容
- 重新生成 HTML
- 替换证据素材
- 编辑讲稿
- 标记已确认

### 6.4 前端视觉建议

前端工作台本身也要有“专业路演工具”气质：

1. 资料体检用仪表盘/评分卡，而不是普通弹窗。
2. 页面风险要有强弱分级，不是统一红字提示。
3. 讲稿区、证据区、预览区应形成稳定三栏关系。
4. 用户一眼能看出“当前最需要处理哪几页”。

### 6.5 前端验收标准

1. 用户知道系统现在在做什么。
2. 用户知道哪些页有风险。
3. 用户知道为什么某页不能直接交付。
4. 用户可以只修一页，不必整套重来。
5. 用户可以在最终交付前做讲稿、证据、页面级确认。

## 7. 分阶段开发计划

### 7.1 总体策略

遵循“先止血，再提质，再闭环”的顺序。

不建议一口气重构整套系统，而应按 P0-P4 渐进推进。

---

### P0：生成前体检 + 终稿硬门禁

目标：

- 先防止明显不合格内容进入“可交付”状态。

范围：

1. 资料完整度报告
2. 占位词/待补充扫描
3. 跨行业污染扫描
4. 模板页识别
5. 终稿可交付状态判断

完成标准：

1. 有体检报告接口和前端展示。
2. 生成结果中出现占位词时不能标记为可交付。
3. 出现明显跨行业语义污染时能被识别。
4. 模板页可被标红和进入修复队列。

---

### P1：比赛故事线与评分点规划

目标：

- 让系统从“通用生成”升级为“比赛型生成”。

范围：

1. 60 分钟比赛故事线模板
2. 页面级评分点绑定
3. 页面级讲述目标生成
4. 页面顺序合理性检查

完成标准：

1. 所有页面都具备明确页面职责。
2. 评分 5 大项均可映射到对应页面。
3. 前后页故事线连贯性明显提升。

---

### P2：证据驱动生成

目标：

- 让关键页面从“说得对”升级为“拿得出证据”。

范围：

1. 页面证据需求生成
2. 素材池
3. 页面与素材绑定
4. 证据缺失检查

完成标准：

1. 关键页都能显示需要什么证据。
2. 用户能上传/查看素材。
3. 系统能把证据素材挂到对应页面。
4. 缺证据页面会被风险提示。

---

### P3：视觉检察官 + 单页修复闭环

目标：

- 把页面质量控制从“人工看”升级成“自动审查 + 自动修复”。

范围：

1. 视觉截图渲染
2. 视觉检察官 JSON 问题输出
3. 单页 HTML 修复
4. 修复后自动复检

完成标准：

1. 单页审查结果结构化。
2. 单页可自动修复并替换。
3. 修复前后可追踪。
4. 修复成功率可统计。

---

### P4：用户精修工作台与最终交付

目标：

- 让用户不只是看结果，而是能掌控结果。

范围：

1. 讲稿区
2. 页面风险面板
3. 单页操作台
4. 最终交付确认流程

完成标准：

1. 用户能对单页做内容、讲稿、素材级调整。
2. 用户能知道当前版本是否达到比赛交付标准。
3. 最终导出前有明确交付确认。

## 8. 研发优先级建议

如果资源有限，建议按以下顺序投入：

### 第一优先级

1. 资料体检
2. 占位词/跨行业/模板页硬门禁
3. 页面级评分点绑定

### 第二优先级

1. 页面级证据需求
2. 素材池与素材绑定
3. 讲稿区

### 第三优先级

1. 视觉检察官
2. 单页修复闭环
3. 风险工作台

### 第四优先级

1. 历史分析
2. 质量趋势统计
3. 行业模板与赛项变体

## 9. 最终验收标准

当以下条件成立时，可以认为 OREP 的 AI 生成 PPT 式 HTML 功能完成了项目级升级：

1. 用户提交资料后，系统先体检，不再盲目生成。
2. 系统按比赛导向组织内容，而不是通用商业 BP。
3. 每页都有明确评分点、页面职责和证据需求。
4. 关键页具备真实政策/技术/实操/团队证据。
5. 生成后会先审查，再交付。
6. 问题页支持单页修复与复检。
7. 用户可以在预览页直接调整讲稿、素材、页面。
8. 最终输出的是“可参赛版本”，而不是“生成完成版本”。

- 有质量门禁
- 有单页修复
- 有用户精修
- 有最终交付标准

只有做到这一点，OREP 的 AI PPT 式 HTML 功能才真正称得上“职业院校技能大赛路演作品生产系统”。
