# 职业院校技能大赛路演PPT智能生成母稿：智能温室作物生长环境监测与安全作业辅助系统

> 本文是一份面向 PPT Agent 的高质量生成母稿，用于生成职业院校技能大赛现场路演 PPT。本文不是参赛正式材料，不包含真实姓名、学校、电话、邮箱等个人信息。全文涉及的指标、截图编号、日志编号、设备编号、测试记录和成果数据均为模拟测试数据，仅用于 PPT Agent 生成能力测试；正式参赛版本必须替换为真实采集数据、真实系统截图、真实测试报告、真实设备照片、真实演示日志和可核验证据。

## 0. 母稿使用规则

本母稿的目标是让 PPT Agent 生成一套符合职业院校技能大赛现场路演节奏的演示型 PPT，而不是生成一套普通项目介绍 PPT。页面数量锁定为 38 页，适配 35-45 页的 roadshow 分支要求。整体讲解按 55 分钟准备，保留 5 分钟机动时间，用于评委追问、设备恢复或现场切换。PPT 必须围绕五大板块展开：项目介绍、总体思路、技能要点、主要成果、项目创新。

PPT Agent 生成时必须遵守以下硬约束：

- 每一页都必须有 `primary_visual`，并且该主视觉要承担页面理解任务，不能只是装饰图。
- 技术页、实操页、证据页、成果页不得以纯卡片堆叠作为主布局，应优先使用系统架构图、数据流图、现场操作板、代码解释板、证据链图、测试仪表盘、故障恢复流程图、团队交接泳道图。
- 所有涉及成果数字的位置都必须标记为模拟测试数据；正式版必须由真实证据替换。没有证据编号的成果不得作为正式结论展示。
- 不出现真实姓名、学校、电话、邮箱、身份证号、精确地址等隐私信息。团队成员仅用匿名岗位角色表示，例如讲解A、操作B、记录C、保障D。
- 现场演示必须体现 55 分钟讲解与实操安排，必须写清讲解角色、操作角色、操作动作、预期屏幕状态、成功信号、故障兜底和导出口令。
- 正式导出门禁必须作为内容的一部分：当 evidence_assets 中存在“待替换”“模拟截图”“未核验数据”时，正式导出状态为“草稿态”，不得输出为参赛正式版。

## 2. 一句话定位

本项目面向设施农业温室作业现场，构建“环境采集、风险预警、作业辅助、设备联动、证据留痕”的一体化系统，让参赛团队在 55 分钟现场路演中可连续展示硬件接入、数据解析、阈值预警、智能排风、AI 农事问答、后台审计和证据导出的完整技能闭环。

项目要回答的不是“我们做了一个看板”，而是“温室环境变化怎样被可靠采集、怎样被判定为风险、怎样转化为作业建议、怎样触发设备动作、怎样留下可追溯证据、怎样在现场故障中恢复演示”。因此 PPT 的叙事要从评委视角出发：先看到农业场景问题，再看到系统闭环，再看实操能力，最后用证据链证明成果可靠。

## 4. 行业痛点与用户场景

设施农业温室的核心矛盾是环境变化快、人工巡检慢、设备控制分散、经验判断不稳定、作业证据难留存。温室作物对温度、湿度、光照、空气质量和通风状态敏感，尤其在高湿、闷棚、烟雾或粉尘异常时，如果操作人员只依靠定时巡查和经验判断，容易出现发现晚、处置慢、责任不清的问题。

本项目设定三个典型场景，供 PPT Agent 生成可视化场景页：

1. 早间巡检场景：管理人员进入温室前，先查看系统看板，确认温湿度、光照、烟雾、PM2.5 和排风设备状态。若环境正常，记录“可进入作业”；若出现高湿或烟雾预警，先执行通风或人工复核。
2. 午间高温高湿场景：棚内温湿度快速变化，系统根据阈值模板触发 warning 或 danger，生成排风建议并记录 event_id。操作人员按提示执行排风或调整作业计划。
3. 比赛现场演示场景：讲解A负责叙事和评分点回扣，操作B在系统中完成连接设备、阈值触发、智能排风、AI问答、证据导出，记录C记录每次成功信号，保障D负责备用网络、演示数据和故障切换。

注意：这些场景中的设备编号、棚室编号和数据均为模拟。正式参赛时必须替换为真实项目场地、真实设备照片、真实运行日志和真实测试记录。

## 5. 需求分析

项目需求分为业务需求、技术需求、展示需求和证据需求四类。

业务需求要求系统能够帮助温室作业人员快速掌握环境状态，识别高温、高湿、烟雾、粉尘、排风异常等风险，并把风险转化为可执行的作业建议。技术需求要求系统支持传感器数据接入、数据帧解析、异常判定、设备控制、AI问答、日志审计和证据导出。展示需求要求比赛现场能够连续演示，而不是只展示静态截图。证据需求要求每一次现场操作都能追溯到截图、日志、接口返回、测试表和导出记录。

## 6. 总体技术思路

系统采用“端、边、智、用、审”五层结构：

- 端：温湿度、光照、烟雾、PM2.5、排风设备状态等模拟设备或真实传感器终端。
- 边：网关或本地模拟网关负责数据接入、原始帧缓存、断点续传和离线回放。
- 智：规则引擎和 AI 问答模块负责风险识别、建议生成和安全边界提示。
- 用：前端看板、阈值配置、排风控制、农事问答、测试面板面向现场使用。
- 审：后台日志、证据链、测试报告、导出门禁负责留痕与核验。

数据流从传感器开始，经由网关生成原始数据帧，进入解析模块后转为标准读数，再进入规则引擎产生风险等级。风险等级可触发排风计划和 AI 农事建议，系统同时把每一步绑定同一个 event_id，形成“采集证据、处理证据、输出证据、复测证据”的链路。PPT 中的架构图要让评委一眼看见：数据不是孤立展示，而是在闭环中被使用和验证。

## 8. 核心模块详稿

以下五个核心模块必须在 PPT 中展开。每个模块都按“功能价值说明 -> 关键技术/代码还原 -> 产品效果测试 -> 模块小结”组织，并且明确输入、处理、输出、证据和失败兜底。PPT Agent 应把每个模块拆成 3-4 页，其中至少一页是现场实操页，至少一页是代码或实现解释页，至少一页是证据或小结页。

### 模块一：设备接入与环境数据解析

#### 1. 功能价值说明

设备接入模块解决“数据从哪里来、是否可信、是否可追溯”的问题。温室现场的温湿度、光照、烟雾、PM2.5、排风设备状态如果只是显示在设备小屏或人工记录表中，就无法参与后续预警、控制和证据导出。本模块把原始数据帧转化为标准环境读数，并为每次采集生成 event_id，使现场演示中的看板刷新、后台日志、证据链导出能够对应到同一次数据事件。

- 输入：模拟网关或真实设备发送的原始数据帧，例如 `T=31.8;H=78.4;SMK=16;PM=42;LUX=480;FAN=0;END`。该样例为模拟测试数据。
- 处理：校验帧格式、解析字段、转换单位、检查范围、生成 event_id、写入缓存与日志。
- 输出：标准读数对象、前端看板刷新、后台采集日志、证据编号。
- 证据：EV-101 设备连接截图，EV-102 原始帧日志，EV-103 解析后 JSON，EV-104 看板刷新截图。
- 失败兜底：蓝牙或串口连接失败时切换本地模拟网关回放；数据帧异常时展示异常帧、校验失败原因和重新采集结果。

#### 2. 关键技术/代码还原

代码还原不需要在 PPT 中粘贴大段代码，而要用“函数链路图 + 关键判断点 + 输入输出样例”解释实现。建议展示 `connectDevice -> receiveFrame -> validateFrame -> parseMetrics -> normalizeReading -> appendEvidence` 的链路。讲解重点是三点：第一，系统不会把任意字符串当作有效读数；第二，字段解析后会进行范围校验，例如湿度不能小于 0 或大于 100；第三，解析成功后生成 event_id，使前端、后台和导出证据能够对齐。

示例解释文本：当模拟网关发送一帧数据后，系统先检查结束标记与字段完整性，再按字段名提取温度、湿度、烟雾、粉尘、光照和排风状态。若字段缺失或范围异常，系统把该帧标记为 invalid，并生成错误日志；若解析成功，系统把读数写入当前棚室状态表，同时记录采集时间、设备编号、原始帧和解析结果。正式版应使用真实设备通信日志替换本示例。

#### 3. 产品效果测试

现场演示时，操作B点击“连接设备/启动模拟网关”，讲解A说明此时不是展示静态截图，而是在触发一次新采集。屏幕应出现四个变化：连接状态由“未连接”变为“已连接”，看板数值刷新，后台日志出现同一 event_id，证据链中新增采集记录。记录C记下本轮 event_id，后续模块都使用同一编号串联。

模拟测试口径：连续发送 20 组模拟数据帧，解析成功 20 组，异常帧拦截 2 组，前端刷新延迟显示为模拟均值 0.8 秒。以上数据仅用于 PPT Agent 测试，正式版必须替换真实测试表。

#### 4. 模块小结

本模块证明团队具备设备接入、数据解析、异常校验和日志留痕能力。评委应看到的不是“有几个传感器”，而是“数据能被系统可靠接收、解释、显示和追溯”。如果现场设备连接失败，团队仍可用本地回放展示完整解析逻辑，但必须在页面和讲解中说明这是备用演示，不得伪装成真实在线设备数据。

### 模块二：阈值预警与异常分级

#### 1. 功能价值说明

阈值预警模块解决“数字怎样变成风险判断”的问题。温室看板只显示温度 31.8、湿度 78.4 并不等于管理有效，作业人员需要知道这些数值对当前作物生长阶段意味着什么、是否需要处理、处理优先级是什么。本模块通过作物阈值模板和多指标组合判断，把环境读数转化为 normal、warning、danger 三类状态，并给出原因与建议。

- 输入：当前环境读数、作物类型、作物阶段、阈值配置、最近三次趋势。
- 处理：读取阈值模板，判断单指标状态，组合风险等级，生成告警原因和建议。
- 输出：告警条、风险等级、处理建议、告警事件日志。
- 证据：EV-201 阈值配置截图，EV-202 告警弹窗截图，EV-203 告警事件表，EV-204 复测截图。
- 失败兜底：前端未刷新时展示接口返回和数据库事件；阈值误配时恢复默认模板并复测。

#### 2. 关键技术/代码还原

实现解释应使用规则树主视觉，不要使用四个并列卡片。函数链路建议为 `loadThresholdProfile -> compareMetric -> mergeRiskLevel -> buildAlert -> persistAlert -> notifyFrontEnd`。讲解重点是“规则可解释”：系统必须能说出为什么触发 warning，是湿度超过上限，还是温湿度组合导致病害风险上升。评委追问时，团队应能指向阈值配置页、告警事件表和复测记录。

规则样例为模拟：番茄苗期湿度建议区间 55%-75%，当前湿度 78.4%，超过上限 3.4 个百分点，状态为 warning；若烟雾值超过 danger 阈值，则组合风险直接升级为 danger。正式版应依据赛项任务书、农业技术资料或现场老师确认的阈值口径替换。

#### 3. 产品效果测试

现场演示选择棚室 GH-01，将湿度 warning 阈值临时调低到 70%，再触发一次数据刷新。屏幕应出现 warning 告警条，告警原因显示“湿度超出设定上限”，后台告警事件表新增记录。随后恢复阈值并重新发送正常数据，页面状态回到 normal。这个复测动作很关键，因为它证明系统不是只会报错，还能在条件恢复后解除告警。

模拟测试口径：使用 30 组模拟环境数据，其中 normal 18 组、warning 9 组、danger 3 组；规则判断与人工标注一致率显示为模拟值 96.7%。该数字仅供生成测试，不可作为正式成果。

#### 4. 模块小结

本模块证明团队具备规则配置、异常识别、风险解释和复测验证能力。它把“数据展示”推进到“作业判断”，为后续智能排风和 AI 问答提供依据。失败时的重点不是隐藏错误，而是展示系统如何记录误配、恢复默认模板、重新触发复测。

### 模块三：智能排风计划与设备控制

#### 1. 功能价值说明

智能排风模块解决“发现风险后怎样形成动作”的问题。温室高温高湿如果只停留在告警层面，仍需要人工判断和手动操作，响应速度不稳定。本模块根据当前风险等级、设备状态和作物阶段生成排风计划，并支持人工确认后下发控制指令。系统记录 command_id、设备状态回执和执行结果，形成从风险到动作的闭环。

- 输入：当前风险等级、温湿度读数、排风设备状态、作物阶段、控制模式。
- 处理：判断排风条件，生成排风计划，执行人工确认，下发控制指令，监听 ack 回执。
- 输出：排风计划、控制命令、设备状态变化、执行日志。
- 证据：EV-301 排风计划页面，EV-302 控制接口返回，EV-303 设备状态变化截图，EV-304 失败重试日志。
- 失败兜底：执行器未响应时切换手动模式，展示失败原因、重试次数和最终登记；若实体设备不可用，使用模拟执行器并明确标注。

#### 2. 关键技术/代码还原

实现解释建议使用“风险输入 -> 策略判断 -> 人工确认 -> 指令下发 -> 回执校验 -> 日志归档”的操作流。函数链路为 `buildVentilationPlan -> requireHumanConfirm -> sendDeviceCommand -> waitAck -> verifyDeviceState -> recordOperation`。讲解重点是系统保留人工确认，不把 AI 或规则判断直接变成不可控动作，体现安全作业意识。

排风策略样例：当湿度 warning 且排风设备 off 时，系统建议开启排风 3 分钟；当烟雾 danger 时，系统建议优先通风并提示人员离开棚室，由现场负责人复核。正式版本必须根据真实设备控制协议、继电器状态、作业安全规范替换。

#### 3. 产品效果测试

现场演示时，操作B选择 GH-01，点击“生成排风计划”，再点击“确认执行”。预期屏幕状态为：计划表新增一条待执行任务，执行后状态由 pending 变 success，设备状态由 off 变 on，后台出现 command_id 与 ack 成功记录。讲解A同步说明人工确认、设备回执和日志留痕分别对应职业安全、技术实现和证据可信。

模拟测试口径：10 次模拟排风指令中 9 次成功回执，1 次模拟超时并通过重试成功。该口径仅用于演示，不得替代真实硬件稳定性测试。

#### 4. 模块小结

本模块证明团队不仅能识别问题，还能把问题转化为规范作业动作。评委需要看到控制链路中的安全边界：系统建议不等于无人监管，所有高风险动作必须有人工确认、回执校验和失败记录。若现场控制设备失败，团队应主动展示兜底方案，而不是跳过该环节。

### 模块四：AI 农事问答与安全作业辅助

#### 1. 功能价值说明

AI 农事问答模块解决“作业人员怎样理解系统建议”的问题。不同选手、农户或维护人员对温室环境指标的理解程度不同，单纯显示告警可能无法指导具体处理。本模块把当前环境摘要、风险等级、作物类型和知识库片段组合起来，生成带安全边界的作业建议。AI 回答必须引用当前数据，不能泛泛给建议。

- 输入：用户问题、当前环境摘要、风险等级、作物类型、知识库片段。
- 处理：构造问题上下文，检索知识依据，生成建议，添加安全提示，保存问答审计记录。
- 输出：问答结果、引用依据、操作建议、审计日志。
- 证据：EV-401 AI 问答截图，EV-402 当前环境摘要，EV-403 知识库片段，EV-404 问答审计记录。
- 失败兜底：在线模型超时则切换本地知识库模板回答；敏感或不确定问题必须提示人工复核。

#### 2. 关键技术/代码还原

实现解释建议用“输入上下文拼装图”，而不是把提示词整段贴在 PPT 上。函数链路为 `collectCurrentContext -> retrieveKnowledge -> composePrompt -> generateAnswer -> addSafetyBoundary -> auditQARecord`。讲解重点是三条约束：回答必须带当前读数，建议必须带边界条件，记录必须可审计。

示例问题为“当前湿度偏高应该怎么处理？”模拟回答应包含：当前湿度 78.4% 为模拟读数，超过设定上限；建议先开启排风并观察 3 分钟；若烟雾或人员不适，应停止棚内作业并人工复核；该建议不替代现场安全负责人判断。正式版应替换为真实知识库和真实问答截图。

#### 3. 产品效果测试

现场演示时，操作B在问答框输入湿度偏高相关问题。预期屏幕状态为：回答中出现当前棚室编号、当前湿度、风险等级、建议动作和安全边界；后台问答审计表出现同一 event_id。讲解A强调 AI 不是独立决策者，而是把监测数据转化为可理解的辅助说明。

模拟测试口径：准备 8 个常见问题，覆盖高湿、高温、烟雾、排风失败、光照不足、作业安全、数据异常、证据导出。PPT 中可展示其中 3 个问答摘要，但必须标注为模拟。

#### 4. 模块小结

本模块证明团队能把智能技术与职业作业场景结合，既提升解释效率，也保留安全边界。评分表达时要避免夸大 AI 能力，不说“自动替代专家”，而说“辅助作业理解、提升响应一致性、形成可审计记录”。

### 模块五：后台审计、测试报告与证据导出

#### 1. 功能价值说明

后台审计模块解决“现场展示是否可核验”的问题。很多比赛作品能演示功能，但评委很难判断它是否真实运行、是否有测试过程、是否具备质量记录。本模块按 event_id 串联采集日志、规则判断、控制指令、AI 问答、截图和导出记录，使每次现场操作都能形成证据链。

- 输入：设备日志、告警事件、控制记录、问答记录、截图、测试用例、导出任务。
- 处理：按 event_id 聚合，绑定截图，检查证据缺口，生成测试摘要，执行导出门禁。
- 输出：证据链总览、测试报告、导出记录、缺口清单。
- 证据：EV-501 证据链总览，EV-502 测试报告，EV-503 导出记录，EV-504 证据缺口登记表。
- 失败兜底：导出失败时展示本地证据目录、错误日志和复测计划；证据不足时只允许草稿导出。

#### 2. 关键技术/代码还原

实现解释建议用证据链主视觉。函数链路为 `collectEvidence -> bindScreenshot -> checkEvidenceGap -> generateTestSummary -> exportEvidencePack -> applyFormalGate`。讲解重点是正式导出门禁：如果成果指标没有对应 evidence_id，或者截图仍是模拟占位，系统必须把导出状态标为草稿，提醒参赛团队替换真实证据。

正式导出门禁的判断口径包括：数据来源是否真实、截图是否为本轮系统生成、日志 event_id 是否一致、测试表是否完整、结论是否有证据编号、是否存在个人隐私信息。PPT Agent 应在第 26 页或第 30 页把门禁画成“可导出/不可导出”的检查流。

#### 3. 产品效果测试

现场演示时，操作B按本轮 event_id 查询证据链。预期屏幕状态为：同一 event_id 下出现采集、预警、控制、问答、审计五类记录；若点击导出，系统显示“测试草稿版导出成功”或“正式导出被拦截，原因：模拟数据未替换”。讲解A说明这种拦截不是系统失败，而是质量管理机制，防止把模拟数据当成正式成果。

模拟测试口径：一轮完整演示生成 5 类记录、12 个证据项、1 份测试摘要和 1 条导出日志。正式版必须替换为真实导出文件和真实测试报告。

#### 4. 模块小结

本模块证明团队具备工程质量意识和比赛材料交付意识。它把现场操作从“说得清”推进到“查得到、导得出、验得过”。如果证据缺失，团队应主动承认并展示缺口清单，而不是用漂亮页面掩盖证据不足。

### 11.1 项目介绍板块，第 1-6 页

项目介绍板块要建立“这是一个职业技能展示项目”的气质。封面不应只放项目名和抽象背景，应出现智能温室、传感器、手机或电脑看板、排风设备、证据链编号等要素。第 2 页必须是 55 分钟路线图，不能只是目录。第 3 页必须把评分关注与证据绑定，避免泛泛引用政策。第 4-6 页要从行业背景、痛点和用户场景逐步收束到项目任务，不能写成农业行业论文。

视觉要求：第 4 页使用“现场问题地图”，可以将温室区域分为采集盲区、人工巡检路线、排风设备、风险点和证据缺口。第 5 页使用“痛点因果链”，表现看不见导致判不准、判不准导致动不快、动不快导致损失或风险、证据散导致复盘困难。第 6 页使用“三视角泳道”，分别显示种植管理人员、技术维护人员和比赛评委如何使用或观察系统。

### 11.2 总体思路板块，第 7-11 页

总体思路板块的任务是让评委理解系统不是几个功能拼接，而是完整闭环。第 8 页的架构图必须清楚表达“端、边、智、用、审”五层，其中“审”层要作为正式组成部分出现，不要只把日志放在角落。第 9 页的 event_id 是全场关键，应在视觉上作为贯穿线。第 10 页要体现现场布置和安全规范：主屏展示 PPT，副屏或同屏嵌入系统，操作席负责点击，记录席记录 event_id，保障席负责备用网络、预录屏和证据包。

视觉要求：架构图中的箭头要区分数据流和控制流。数据流从设备到看板和审计，控制流从规则与人工确认到排风设备，证据流从每个模块回到后台审计。不要把架构做成五个孤立横条。

### 11.3 技能要点板块，第 12-27 页

技能要点是全套 PPT 的核心，应占最多页数和最长时间。五个模块都要遵守“功能价值说明 -> 关键技术/代码还原 -> 产品效果测试 -> 模块小结”的结构，但页面上不一定写这四个标题，可以通过主视觉体现。技术页必须展示输入、处理、输出、证据和失败兜底；实操页必须展示操作角色、操作动作、预期屏幕状态、成功信号和 command_cue。

代码还原页不应粘贴难读的大段代码，而应把代码逻辑翻译成可讲解的结构图。示例函数名可以出现，但不要生成可执行脚本。每页的讲解文本应围绕“我为什么这么做、这一步验证了什么、失败时怎么处理”展开。

实操页建议采用“现场操作板”布局：左侧为操作步骤，中间为系统屏幕或放大截图，右侧为评委观察点和成功信号，底部为 fallback_plan。这样既能指导现场团队，也能让评委知道该看哪里。

### 11.4 主要成果板块，第 28-34 页

成果页必须清楚标注数据来源。由于本母稿用于生成测试，所有成果数字必须带“模拟测试数据”标识。正式参赛时，如果没有真实证据，不得把模拟成功率、模拟响应时间、模拟完整率画成正式结果。

第 28 页讲测试环境和样本口径，第 29 页讲核心指标，第 30 页讲证据链，第 31 页讲应用价值，第 32 页讲职业素养，第 33 页讲团队协作，第 34 页讲故障恢复。成果板块不要变成一堆漂亮大数字，而要体现“指标、方法、证据、边界”四件事。

### 11.5 项目创新板块，第 35-38 页

创新板块要具体、克制、可验证。不要写“国内领先”“首创”等无法证明的表述。建议创新表达为：

- 流程创新：把温室环境监测、风险判断、作业控制、AI 解释、证据导出连成闭环。
- 技术创新：通过 event_id 贯穿采集、预警、控制、问答和审计，降低现场展示与证据脱节。
- 应用创新：把职业技能比赛中的实操要求转化为可演示、可复盘的系统流程。
- 教学创新：支持学生按模块训练设备接入、规则配置、接口控制、AI 边界和质量记录。
- 安全创新：通过人工确认、失败兜底和正式导出门禁，避免自动化误操作和材料误用。

## 12. 团队匿名分工与现场口令

团队角色一律匿名，不出现真实姓名和学校。

| 匿名角色 | 职责 | 关键动作 | 补位机制 |
|---|---|---|---|
| 讲解A | 主讲叙事、评分点回扣、评委追问初答 | 按 PPT 节奏讲解，发出操作口令 | 若卡顿，由记录C提示当前页目标 |
| 操作B | 系统实操、设备连接、阈值调整、控制执行 | 按 command_cue 点击系统并保持屏幕可见 | 若操作失败，由保障D切换备用演示 |
| 记录C | 记录 event_id、成功信号、异常现象 | 记录每次实操的编号与结果 | 若讲解A遗忘编号，及时提示 |
| 保障D | 网络、设备、备用包、预录屏和导出文件 | 处理断网、设备失败、模型超时等情况 | 若系统不可恢复，启动备用材料并标注 |

口令规则：

- 讲解A说“请操作席准备进入某页面”时，操作B只打开页面，不点击关键按钮。
- 讲解A说“执行某动作”时，操作B再点击关键按钮。
- 记录C在每个模块成功后记录成功信号，例如“看板刷新”“warning 出现”“ack 成功”“回答生成”“证据链完整”。
- 保障D只有在讲解A说“启动备用方案”或系统超过 10 秒无响应时介入。

这套口令要在第 2 页、第 33 页和每个实操页的 `command_cue` 中体现。PPT Agent 生成时不要把口令藏在备注里，应在实操页底部用小型“现场口令条”显示。

## 13. 风险应急与故障恢复

现场故障不是扣分点的必然来源，处理不规范才是风险。PPT 应主动准备第 34 页故障恢复演练，并在每个实操页写入 fallback_plan。

| 故障类型 | 触发信号 | 现场处理 | 证据记录 | 恢复成功信号 |
|---|---|---|---|---|
| 网络断开 | 系统接口超时、页面加载失败 | 切换本地模拟网关和离线演示数据 | EV-601 断网记录 | 离线看板可继续刷新 |
| 设备连接失败 | 连接按钮超时或串口无数据 | 展示连接失败日志，切换数据回放 | EV-602 连接失败日志 | 回放数据生成 event_id |
| 模型超时 | AI 问答超过 10 秒无返回 | 切换本地知识库模板回答 | EV-603 模型超时记录 | 回答带“本地兜底”标识 |
| 控制执行失败 | command 无 ack 或设备状态不变 | 重试一次，失败则切手动模式并登记 | EV-304 重试日志 | 日志显示失败原因和处理 |
| 导出失败 | 导出任务报错或文件缺失 | 展示证据目录和错误日志，登记复测 | EV-604 导出错误记录 | 缺口表出现复测计划 |

故障页的讲解重点是：我们不把失败藏起来，而是把失败变成可记录、可解释、可复测的质量管理过程。这个表达能同时回应职业素养、团队协作和工程能力。

## 14. 正式导出门禁

正式导出门禁是本项目材料质量的最后防线。PPT Agent 生成出的测试稿可以使用模拟数据，但正式参赛版必须满足以下条件：

| 门禁项 | 通过条件 | 未通过时处理 |
|---|---|---|
| 数据真实性 | 核心指标来自真实测试表或真实日志 | 保留“模拟测试数据”标识，只能导出草稿 |
| 截图真实性 | 截图来自本项目系统真实运行，不是示意图 | 替换真实截图或标记为占位 |
| event_id 一致 | 采集、预警、控制、问答、审计能按同一事件查询 | 重新演示并补齐链路 |
| 隐私合规 | 无真实姓名、学校、电话、邮箱、身份证号等 | 脱敏后再导出 |
| 成果可核验 | 每个成果数字有 evidence_id | 删除数字或补充证据 |
| 故障有记录 | 演示中发生的异常有日志和复测计划 | 补写故障登记 |

建议 PPT 在第 26 页用流程图表达门禁：收集证据 -> 检查真实性 -> 检查隐私 -> 检查 event_id -> 检查成果证据 -> 允许正式导出或仅允许草稿导出。当前母稿由于全部数据为模拟测试数据，默认只能生成“测试草稿版”。

## 16. 逐页讲解备注建议

PPT Agent 可把以下内容转化为演讲者备注。备注不一定全部显示在页面上，但必须服务现场讲解。

第 1 页：开场时只用一句话定位项目，不要急于讲技术细节。强调本项目围绕温室环境监测和安全作业辅助。

第 2 页：告诉评委全程有五段实操，后续每段都会给出操作、屏幕状态和证据编号。

第 3 页：把评分点与页面证据绑定，说明团队不是堆功能，而是按比赛评价逻辑组织展示。

第 4-6 页：控制背景讲解时长，不要泛泛讲农业现代化。重点是温室现场环境变化快、人工判断不稳定、证据难留存。

第 7-11 页：讲清系统闭环，特别是 event_id。后续如果评委追问“怎么证明是同一次操作”，就回到第 9 页。

第 12-15 页：模块一要讲数据可信。现场成功后，记录C必须记下 event_id。

第 16-18 页：模块二要讲规则可解释和可复测。触发告警后一定要恢复阈值，证明系统可回到 normal。

第 19-21 页：模块三要讲人工确认和回执校验。不要把控制说成完全自动化，避免安全风险。

第 22-24 页：模块四要讲 AI 的边界。回答必须引用当前数据，不应给绝对化结论。

第 25-27 页：模块五要讲证据链和导出门禁。正式导出被拦截不是坏事，而是质量控制。

第 28-34 页：成果板块所有数字都是模拟测试数据。正式版必须替换真实证据。这里要体现专业诚实。

第 35-38 页：创新要回到闭环、证据、安全和教学价值，不要夸张宣传。

## 17. 禁止生成内容清单

PPT Agent 不得生成以下内容：

- 真实姓名、真实学校、真实电话、真实邮箱、真实身份证、精确住址。
- 未经证据支持的“行业第一”“国内领先”“完全替代人工”“零故障”等夸大表述。
- 把模拟测试数据写成正式成果。
- 大量纯文字卡片堆叠，尤其是技术页、实操页、证据页、成果页。
- 无 primary_visual 的页面。
- 没有 fallback_plan 的实操页。
- 没有 command_cue 的实操页。
- 没有 evidence_assets 的成果页。
- 将 AI 回答描述为最终安全决策。
- 将设备控制描述为无需人工确认的自动执行。

## 19. 可直接给 PPT Agent 的摘要提示

请根据本文生成一套 38 页职业院校技能大赛路演 PPT，主题为“智能温室作物生长环境监测与安全作业辅助系统”。PPT 必须面向现场比赛讲解，不是普通项目汇报。必须包含五大板块：项目介绍、总体思路、技能要点、主要成果、项目创新。必须体现 55 分钟讲解与实操安排、匿名团队分工、设备接入、阈值预警、智能排风、AI 问答、后台审计、证据链、故障恢复和正式导出门禁。

每一页都必须使用本文第 10 节的页面蓝图字段：`page_role`、`judge_focus`、`primary_visual`、`evidence_assets`、`speaker_goal`、`stage_mode`、`display_target`、`time_budget_sec`、`speaker_role`、`operator_role`、`operator_action`、`expected_screen_state`、`fallback_plan`、`acceptance_signal`、`command_cue`。每一页都必须有主视觉。技术页、实操页、证据页、成果页不得使用纯卡片主布局。

全部成果数据、日志编号、截图编号均为模拟测试数据，正式版必须替换真实证据。生成的页面中不得出现真实姓名、学校、电话、邮箱等个人信息。若证据资产仍为模拟或占位，导出状态必须显示为“测试草稿版”，不得显示为正式参赛版。
