# OREP 单页重设计闭环开发方案

## 1. 目标

把当前“单页反复修补 HTML”的链路，升级为“带失败记忆、带视觉约束、带证据判断的单页重设计闭环”。

目标结果：

1. 页面尽量在一次重设计后达到可用状态，而不是连续修复 3-6 次。
2. 同一页的缺陷、失败历史、视觉问题、证据缺口要可追踪、可复用。
3. 页面问题要先分流，再进入对应处理路径：HTML 修复、结构重做、证据补充。
4. 修复不再是盲目重试，而是“问题档案 -> 设计约束 -> 定向生成 -> 复检 -> 决策”。

---

## 2. 问题定义

当前单页修复体验差，根因主要有：

1. 每次修复对历史失败记忆不足。
2. 视觉模型结果没有沉淀成强设计约束。
3. 证据型问题和结构型问题经常被误当成 HTML 型问题。
4. 修复后的收益没有被及时判断，导致“重复修复未收敛”。
5. 当前页面工作台给用户的出口不够强，经常把问题转回用户自己判断。

---

## 3. 新闭环总体流程

```text
页面当前状态
-> 生成页面缺陷档案（page_issue_profile）
-> 判定修复路由（html / structure / evidence）
-> 组装重设计上下文（design_context）
-> 单页重设计/单页修复
-> 本地质检 + 视觉复检
-> 评估收益（是否比当前页更好）
-> 给出唯一推荐动作
```

---

## 4. 核心对象设计

### 4.1 页面缺陷档案 `page_issue_profile`

每页一份，至少包含：

- `page_index`
- `title`
- `page_role`
- `repair_route`
- `priority`
- `current_score`
- `failed_checks`
- `primary_problem_type`
- `repair_strategy`
- `repair_route_reason`
- `repair_attempts`
- `confirmed_attempts`
- `consecutive_same_result`
- `recent_no_effect_attempts`
- `auto_fix_suspended`
- `quality_messages`
- `visual_problems`
- `high_priority_visual_problems`
- `evidence_gaps`
- `scoring_gaps`
- `story_sequence_warnings`
- `history_summary`
- `must_not_repeat`
- `recommended_action`

### 4.2 重设计上下文 `design_context`

用于喂给单页重设计模型，至少包括：

- 当前页大纲元数据
- 前一页/后一页标题与职责
- 页面缺陷档案摘要
- 当前评分点目标
- 当前证据需求
- 当前视觉问题约束
- 当前必须消除的问题列表
- 设计模式：`html_fix` / `structure_rebuild` / `evidence_first`

---

## 5. 三类修复路径

### 5.1 HTML 型问题

适用问题：

- 布局重叠
- 焦点弱
- 图表漂移
- 视口问题
- 视觉层级不稳

处理方式：

- 沿用当前 HTML 修复入口
- 但带上页面缺陷档案和视觉约束
- 修完后必须做收益判断

进入下一步标准：

- 页面分数提升 >= 6 分，或高风险失败项减少 >= 1 个
- 若连续 2 次收益不足，升级为结构重做或托底模板

### 5.2 结构型问题

适用问题：

- 页面模板化
- 标题/核心论点不清
- 评分点不对齐
- 实操闭环不足
- 页内叙事职责不清

处理方式：

- 不再修原 HTML
- 改为单页重设计
- 模型必须按“标题区 + 主体区 + 证据/评分区”整页重做
- 明确要求服务当前页角色和评分目标

进入下一步标准：

- 模板页风险解除
- 页面可讲性通过
- 评分点对齐通过或明显改善

### 5.3 证据型问题

适用问题：

- 缺政策官方截图/来源
- 缺实操截图/设备图/数据图
- 缺素材绑定

处理方式：

- 不允许继续空修 HTML
- 直接引导证据补充
- 如果必须预览，则生成“证据承载版式”而不是继续编造内容

进入下一步标准：

- 至少补齐 1 个关键证据位
- 页面缺口从 `evidence_first` 降到 `html_fix` 或 `structure_rebuild`

---

## 6. 收益判断机制

每次修复后必须比较：

- `score_delta`
- `failed_check_delta`
- `high_risk_problem_delta`
- `repaired_hash 是否变化`
- `repair_route 是否变化`

决策规则：

1. 如果 `repaired_hash == original_hash`，直接判定为无效修复。
2. 如果连续 2 次 `score_delta < 4` 且失败项不减少，进入熔断。
3. 熔断后不再继续同路径修复，改为：
   - `restore_best_repaired`
   - `structure_rebuild`
   - `attach_evidence`
   - `fallback_rebuild`

---

## 7. 后端开发步骤

### M1：页面缺陷档案落库

做什么：

1. 基于现有 `quality_report + vision_review_report + page_repair history + roadshow/scoring/materials` 生成 `page_issue_profile`。
2. 保存到 `ppt_generation_snapshot`，类型建议为 `page_issue_profiles`。
3. 历史详情读取时优先加载最新缺陷档案。

做到什么程度：

- 每页都能看到结构化问题摘要。
- 至少能区分 `html / structure / evidence` 三种路线。

验证：

- 用任务 `107` 检查页面 11/18/19/22 是否生成正确的档案。
- 检查连续失败页是否带出 `auto_fix_suspended` 与 `recommended_action`。

进入下一步标准：

- 历史详情页能稳定拿到每页缺陷档案。

### M2：单页重设计上下文生成

做什么：

1. 新增 `design_context` 组装逻辑。
2. 把缺陷档案、视觉问题、前后页上下文、评分点目标一起喂给单页修复模型。
3. 对结构型问题统一走 `structure_rebuild` 模式。

做到什么程度：

- 修复 prompt 不再只看当前 HTML 和当前失败项。
- 明确包含“历史失败记忆”和“必须消除的问题”。

验证：

- 抽样查看 prompt 生成内容，确认包含失败历史和视觉问题。
- 结构型页面点击修复时，策略不再只是 `rewrite_page_argument`，而是带 `upgrade_mode=structure_rebuild`。

进入下一步标准：

- 结构型页面能稳定走新路径。

### M3：修复收益判断与熔断

做什么：

1. 在每次修复后计算收益。
2. 连续低收益时自动熔断。
3. 自动给出唯一推荐动作。

做到什么程度：

- 用户不会再看到同一页可无限重复修复。
- 系统知道什么时候该“恢复推荐版本”、什么时候该“升级重做”、什么时候该“去补证据”。

验证：

- 对任务 `107` 的重复失败页，触发熔断后不再出现继续空修。

进入下一步标准：

- 重复失败页的下一步动作唯一且可执行。

### M4：前端推荐动作工作台

做什么：

1. 页面卡片展示缺陷档案摘要。
2. 修复历史弹窗顶部展示系统推荐动作。
3. 不再让用户自己判断“恢复哪一版/继续修哪一条路”。

做到什么程度：

- 用户从一个弹窗或一个卡片就能执行下一步。
- 没有“让用户理解系统内部机制”的负担。

验证：

- 随机抽 3 个失败页，用户都能在 1 次点击内进入正确动作。

进入下一步标准：

- 前端工作台已经具备闭环能力。

### M5：视觉复检闭环

做什么：

1. 单页重设计完成后自动发视觉复检。
2. 把复检结果写回缺陷档案。
3. 若仍不通过，走下一策略而不是原路重试。

做到什么程度：

- 页面修复后的决策是自动的，不靠用户反复点。

验证：

- 观察修复日志，确认不会连续多次执行相同策略。

进入下一步标准：

- 单页从修复到决策能自动闭环。

---

## 8. 前端交互优化点

1. HTML 预览页显示：
- 当前修复路线
- 当前页问题类型
- 推荐动作

2. 修复历史弹窗：
- 顶部固定系统推荐动作
- 历史版本仅作为次要参考

3. 质量页按钮文案统一：
- `生成修复预览`
- `升级重做此页`
- `去补素材证据`
- `恢复推荐版本`

4. 对连续失败页增加明显状态：
- `重复修复未收敛`
- `当前不建议继续同路径修复`

---

## 9. 数据结构建议

短期先用现有 `ppt_generation_snapshot` 落地：

- `snapshot_type = page_issue_profiles`
- `payload = { generated_at, pages: [...] }`

中期可独立成表：

- `ppt_page_issue_profile`
  - `task_id`
  - `page_index`
  - `repair_route`
  - `priority`
  - `issue_payload`
  - `recommended_action`
  - `attempt_count`
  - `updated_at`

---

## 10. 验收标准

达到以下标准，才算“单页重设计闭环”第一阶段可用：

1. 同一页不会再无上限重复修复。
2. 每页都有结构化缺陷档案。
3. 结构型问题不会再走普通 HTML 修补。
4. 证据型问题不会再继续空修。
5. 修复历史弹窗会给出系统推荐动作，而不是让用户自己判断。
6. 修复失败后会自动切换下一策略，而不是继续原路重试。

---

## 11. 当前建议实施顺序

1. M1 页面缺陷档案落库
2. M2 单页重设计上下文
3. M3 收益判断与熔断
4. M4 前端推荐动作工作台
5. M5 视觉复检闭环
